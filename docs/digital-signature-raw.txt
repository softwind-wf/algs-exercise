【2】数学原形：教科书 RSA 的签名就是一次指数运算
==================================================================
p = 61, q = 53
n = p*q = 3233
φ(n) = (p-1)(q-1) = 3120
e = 17（公钥指数）
d = e^-1 mod φ(n) = 2753（私钥指数）
e*d mod φ(n) = 1（验证：确实等于 1）
公钥 (n, e) = (3233, 17)；私钥 (n, d) = (3233, 2753)

消息整数 m = 65（'A'，必须小于 n=3233，所以 RSA 一次只能处理很短的数据）
签名 σ = m^d mod n = 588
验签（任何人都能做）：σ^e mod n = 65
  [通过] 教科书验证公式 σ^e mod n == m 成立

—— 漏洞 1：可乘性伪造（教科书 RSA / 无填充签名的经典攻击）——
截获两条合法签名：σ(65) = 588，σ(66) = 2215
攻击者把两个签名相乘：σ(65)*σ(66) mod n = 2754
它对应的消息：m3 = 65*66 mod n = 1057
用公钥验伪造签名：σ^e mod n = 1057
  [通过] 不需要私钥，伪造的签名被验证器接受（这就是漏洞）

—— 漏洞 2：存在性伪造（先选签名，再反推消息）——
攻击者任意挑一个数当签名：s = 7
反推消息：m = s^e mod n = 2369
于是 (m=2369, 签名 s=7) 天然通过验证
  [通过] (m, s=7) 通过验证，但这条 m 是攻击者算出来的乱码，冒充不了真实内容

—— 修正：签名对象是 hash，并且要先过带结构的填充 ——
1) 消息先 hash 成固定长度（SHA-256 -> 32 字节）再当成整数，
   攻击者无法控制 hash 的取值，可乘性伪造和目标 hash 对不上；
2) PKCS#1 v1.5 把 hash 装进 00 01 FF...FF 00 || DigestInfo 的固定结构，
   多乘一个 σ 就会把填充结构弄乱，验签端直接拒绝；DigestInfo 还防跨算法替换；
3) RSA-PSS 更进一步：随机盐 + MGF1 掩码，同一消息每次签名都不同；
4) hash 必须抗碰撞、抗第二原像 —— SHA-1 已被实际碰撞（2017 SHAttered），
   今天签名一律 SHA-256 起步。

【3】四种签名算法实测：长度、确定性、耗时
==================================================================
算法                        密钥长度     签名长度  同一消息签两次  签名 ms  验签 ms
--------------------------  -----------  --------  --------------  -------  -------  
RSA-2048 / PKCS#1 v1.5      2048 位模数  256 字节  完全相同        1.289    0.078  
RSA-2048 / RSASSA-PSS       2048 位模数  256 字节  不同（随机盐）  1.228    0.097  
EC P-256 / SHA256withECDSA  256 位曲线   71 字节   不同（随机 k）  0.960    1.793  
Ed25519                     256 位       64 字节   完全相同        1.907    1.162  
（毫秒数是每次新建 Signature 对象后测的 20 次均值，只看量级，不要当基准测试。）

表中三个要点：
· RSA 签名长度 = 模数长度（2048 位 -> 256 字节），ECDSA/Ed25519 短得多；
  ECDSA 的 DER 编码长度在 70~72 字节间浮动，验签端不能假定固定长度。
· "同一消息签两次是否相同"不能当安全性判据：
  PKCS#1 v1.5 和 Ed25519 都是确定性的（Ed25519 的随机量由私钥+消息派生，
  所以永不复用、也不会撞车），ECDSA/PSS 才需要随机数。
  真正危险的是"随机数被复用"，不是"签名确定性"（见第 6 段）。
· 速度方向不一样：RSA 验签极快（验签只做一次 e=65537 的幂运算，签名要算私钥指数），
  ECDSA 验签要做两次标量乘、比签名贵；Ed25519 两者接近。
  这里的绝对值主要反映 JCA 每次新建 Signature 的开销，判断趋势就好。

—— 签名长度与消息长度无关 ——
签 1 字节的消息：签名 256 字节，耗时 1 ms
签 1 MB 的消息：签名 256 字节，耗时 5 ms
  [通过] 1 字节与 1 MB 的签名长度相同，且 1 MB 的签名仍可验签

【4】"用私钥加密"到底算不算签名？
==================================================================
尝试：Cipher.getInstance("RSA/ECB/PKCS1Padding").init(ENCRYPT_MODE, 私钥)
结果：JCE 允许，密文 256 字节
公钥还原出的明文: 这条消息用私钥"加密"，任何人都能用公钥解开。
  [通过] 用私钥做的这步"加密"，公钥可以完整还原（所以它不提供机密性）
→ 结论：方向虽然反过来，但这只是"私钥做幂运算"，不是签名：

签名和"私钥加密"差在四处，缺一不可：
1) 签名对象是 hash：σ 作用在 H(M) 上，不是作用在 M 上；
2) 结构化填充：PKCS#1 v1.5 的类型 1 填充 / PSS 的随机盐，让"乘法"彻底失效；
3) 验证是布尔判定：验签要么 true 要么抛异常，不存在"解出乱码"的中间态；
4) 幂运算本身在数学上双向可逆，安全性全靠"构造不出合法填充"这一点，
   所以绝不能自己拼填充，必须用标准库/标准算法名。

【5】签名 vs MAC：能证明"有密钥"，还是能证明"是谁"
==================================================================
HMAC-SHA256(K, M) = f04e19eb61fc9b41ebe5924dbcd70443340764a452d2ab5597b8fd5475a044ed
检查：
  [通过] 持有 K 的人算出来的 MAC 完全相同
  [通过] MAC 长度固定 32 字节，与消息长度无关

→ 同一把对称密钥，签名者和"任何一个拿到 K 的人"（服务器、运维、攻击者）
  产生的结果一模一样，事后无法向法官证明"这条是 A 发的"。
→ 数字签名用私钥：只有私钥持有者能生成，公钥只能验证，
  所以才有不可否认性（Non-repudiation）。
→ 现实里两者都在用：TLS 1.2 记录用 HMAC、TLS 1.3 用 HMAC 构造的 HKDF 派生密钥；
  JAR 签名、代码签名、电子合同用公私钥签名（需要第三方可验证）。

【6】攻击面：随机数复用、公钥替换、重放
==================================================================
—— 6.1 DSA/ECDSA 随机数复用 -> 私钥被完整算出来 ——
玩具参数：p=23, q=11, g=2（真实 ECDSA 用 256 位曲线）
签名者私钥 d = 7，公钥 y = g^d mod p = 13
两次签名用了同一个随机数 k = 6（复用！）
签名 1：(r, s1) = (7, 5)，消息摘要 z1 = 3
签名 2：(r, s2) = (7, 9)，消息摘要 z2 = 5
  [通过] 签名 1 本身是合法的（不是伪造，因此泄漏是真的）
攻击者只看到 (z1, r, s1) 和 (z2, r, s2)，因为 r 相同，直接解方程：
  k = (z1 - z2) / (s1 - s2) mod q = 6
  d = (s1*k - z1) / r mod q = 7
检查：
  [通过] 复用掉的随机数 k 被还原
  [通过] 私钥 d 被完整还原 -> 从此可以伪造任何签名
→ 现实案例：索尼 PS3（2010）因 ECDSA 的 k 恒定被破解；Android 比特币钱包（2013）
  因 SecureRandom 缺陷导致 k 重复，私钥批量泄漏。
→ 修复：每个签名都用新的随机 k（RFC 6979 用确定性方式从 私钥+消息 派生 k，
  既不复用也不依赖随机数质量）。Ed25519 天生这样做。

—— 6.2 公钥替换：签名对不对，取决于你手上是谁的公钥 ——
真实公钥指纹: 11ef72a79913e071...
攻击者公钥指纹: d41ec198e6639512...
攻击者用自己的私钥签了一条"转 900 元给 C"的指令。
  [通过] 用攻击者的公钥验：通过（这条签名确实是攻击者的）
  [通过] 用真实公钥验：拒绝
→ 签名本身没被攻破，被替换的是"公钥"。所以公钥来源必须可信：
  证书链（CA）、预置指纹、公钥固定（pinning）、密钥透明日志（CT）。

—— 6.3 重放：签名只证明"这条消息没被改"，不证明"只发了一次" ——
  [通过] 同一条 (消息, 签名) 提交两次，两次都验签通过
→ 转账、下单这类动作必须在协议层加一次性 nonce / 时间戳 / 流水号去重；
  例如消息里带 "流水号 T-0001"，服务端记录已处理的流水号。

【7】小结
==================================================================
· 数字签名 = 用私钥对"消息摘要 + 结构化填充"做运算，公钥验算，结果只有 是/否。
· 它同时给出三件事：完整性（改一个 bit 就验不过）、身份认证（私钥持有者）、
  不可否认性（只有私钥能生成）——但不提供机密性，也不防重放。
· 必须先 hash 再签：不然可乘性伪造、存在性伪造都能绕开私钥。
· 算法选择：Ed25519 / ECDSA P-256 / RSA-PSS 优先，RSA 至少 2048 位；
  PKCS#1 v1.5 只用于兼容旧系统；SHA-1 已死。
· 实现上只用标准库的标准算法名；随机数复用会直接泄漏私钥。
· 工程上还要解决：公钥来源（证书）、消息覆盖范围（所有可变量）、
  重放（nonce/时间戳）、密钥轮换与吊销。
