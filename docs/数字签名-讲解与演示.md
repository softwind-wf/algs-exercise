## 0. 三十秒版

```text
发送方                                         接收方
  消息 M ──> SHA-256 ──> h ──> 填充 + 私钥运算 ──> 签名 σ
                                                    │
                          M, σ ─────────────────────┘
                                                    │
  消息 M' ──> SHA-256 ──> h' ──> 同一种填充 + 公钥运算 ──> 比对 h'？
                                                    是 → 接受；否 → 拒绝
```

数字签名 = **用私钥对"消息摘要 + 结构化填充"做一次运算，公钥能验算，结果只有 是/否**。

| 签名能保证 | 签名不能保证 |
|---|---|
| 完整性：改一个 bit 就验不过 | 机密性：消息仍然是明文，签名不是加密 |
| 身份：只有私钥持有者能生成 | 防重放：同一条 (消息, 签名) 可以再提交一次 |
| 不可否认：第三方拿着公钥也能验证 | 内容合法/意图真实：签名不保证你读懂了合同 |

再补一句最容易被忽略的：**签名保护的是"消息字节"，不是"消息含义"**。
哪些字段被签、编码是否唯一、上下文有没有绑定，全看协议怎么设计——这是第 6.4 节的主题。

### 0.5 签名不加密——但它也不只是"防伪"

"签名不加密"是对的：签名是**附在消息旁边的一段数据**，消息本身一个字节都不变。
用火漆印类比最准：印章盖在信封外面，谁封的、封口有没有破都能证明，但信纸仍然是明文。

实跑输出就是证据：消息 87 字节原样打印，签名另外 256 字节。

| 签名的"防伪"具体指 | 它不保证 |
|---|---|
| **防篡改**：改一个 bit 就拒绝 | 机密性：消息明文，谁都能读 |
| **防冒充**：没有私钥签不出 | 防重放：同一签名可再提交一次 |
| **可追责**：第三方拿着公钥也能验证 | 时效/可用性：不防删除、不防过期后继续用 |

三个最常见的误会：

1. **"JWT 的 payload 是加密的"**——不是。JWS（`alg: RS256` 那类）只做签名，payload 是 Base64URL，
   任何人复制到解码器就能读；JWE 才是加密。把手机号、密码放进 JWS 的 payload 等于明文发布。
2. **"代码签名会把 jar 加密"**——不会。`jarsigner` 只往 `META-INF/` 加摘要和签名块，
   类文件原样躺在 jar 里，解压即得（本仓库 `docs/digital-signature-jar-raw.txt` 就是实测）。
3. **"用私钥加密就是加密"**——方向反了。公钥公开发布，私钥"加密"的结果人人都能还原，
   所以它不提供机密性（JDK 实测：私钥加密 256 字节，公钥能完整解出原文）。

那"防伪"这个词准确吗？它其实混了两件事：**防篡改**（改了就验不过）和**防冒充**（没有私钥签不出）。
两者都成立，但都只针对"这一条消息"，不针对"消息内容该不该被别人看到"。

### 0.6 想同时保密怎么办：加密和签名是两个零件

| 需求 | 用什么 | 缺什么 |
|---|---|---|
| 只保密 | 加密（AES-GCM / RSA-OAEP / ECIES） | 不知道是谁发的 |
| 只防伪 | 签名（Ed25519 / RSA-PSS / ECDSA） | 消息明文 |
| 两者都要 | 签名 + 加密，两套密钥 | 顺序与密钥用途要设计对 |

**顺序不是随便选的**：`sign-then-encrypt`（先签后加）接收方解密后才能验签；
把签名密钥和加密密钥混用，可能出现"把发给 A 的签名重放给 B""用加密密钥冒充签名密钥"。
工程共识：**签名密钥与加密密钥分开**，加密用 AEAD，签名只负责"谁发的、改没改"。

现实里的组合：TLS 1.3 握手签名 + 记录层 AEAD；S/MIME、PGP 签名与加密是两个独立步骤；
代码签名（jar/APK/驱动）只签不加密，因为内容本来就要公开。

一句话：**签名回答"是谁、改没改"，加密回答"谁能看"。**

```text
  [通过] 只把金额 100.00 改成 900.00 -> 验签拒绝
  [通过] 只改签名的最后一个 bit -> 验签拒绝
  [通过] 换成另一对密钥的公钥 -> 验签拒绝
```

把这段输出翻成三句话：

1. **签名长度是 256 字节，和消息长度无关**——因为签的是 hash（32 字节）再套 RSA，长度只由密钥决定；
2. **改消息、改签名、换公钥，三种篡改全部被拒**——完整性、身份、绑定公钥这三件事一次到位；
3. **验证只需要"消息 + 签名 + 签名者公钥"**——消息本身可以明文传输，签名不提供机密性。

值得注意的细节：改签名最后 1 个 bit 之后，JDK 的 PSS 验签**返回 false 而不是抛异常**；
而如果签名长度都不对，可能会抛 `SignatureException`。所以生产代码里"验签失败"必须同时处理
"返回 false"和"抛异常"两种情况，后者也是拒绝，不能当成程序错误吞掉。

## 2. 拆开看：一次签名到底算了什么

### 2.1 教科书 RSA：签名就是一次指数运算

```text
p = 61, q = 53
n = p*q = 3233
φ(n) = (p-1)(q-1) = 3120
e = 17（公钥指数）
d = e^-1 mod φ(n) = 2753（私钥指数）
e*d mod φ(n) = 1（验证：确实等于 1）
公钥 (n, e) = (3233, 17)；私钥 (n, d) = (3233, 2753)

消息整数 m = 65（'A'，必须小于 n=3233，所以 RSA 一次只能处理很短的数据）
签名 σ = m^d mod n = 588
验签（任何人都能做）：σ^e mod n = 65
  [通过] 教科书验证公式 σ^e mod n == m 成立
```

数学上只有两件事：

- **私钥**是 `d`，签名为 `σ = m^d mod n`；
- **公钥**是 `(n, e)`，验签为 `σ^e mod n` 是否等于 `m`。

因为 `e·d ≡ 1 (mod φ(n))`，两次幂运算正好抵消。**不需要私钥也能验**，这就是"公钥验签"的全部秘密。
（真实实现当然不是这样直接算：`n` 是 2048 位，`m` 要先 hash 再填充，见 2.3。）

这里已经暴露第一个限制：`m` 必须小于 `n`。 3233 只能装下 12 bit，2048 位 RSA 也只能装
256 字节——而消息可以是任意长度。光这一条就决定了"必须先 hash 压缩"。

### 2.2 直接签消息的两个致命问题

下面的数字全部来自实跑（`docs/digital-signature-raw.txt` 第 2 段）：

**漏洞 1：可乘性伪造——不用私钥，拿两条签名就能伪造第三条。**

```text
截获两条合法签名：σ(65) = 588，σ(66) = 2215
攻击者把两个签名相乘：σ(65)*σ(66) mod n = 2754
它对应的消息：m3 = 65*66 mod n = 1057
用公钥验伪造签名：σ^e mod n = 1057
  [通过] 不需要私钥，伪造的签名被验证器接受（这就是漏洞）
```

为什么成立？因为 RSA 运算保持乘法：`(m1^d)(m2^d) = (m1·m2)^d (mod n)`。
攻击者只要**见过两条合法签名**（比如两个合法文件的签名），相乘就得到"第三个消息"的合法签名。
注意这条伪造消息是 1057 这个整数——攻击者不能选择它，但这个攻击已经足够证明"签名不等于私钥独占"。

**漏洞 2：存在性伪造——先挑签名，再反推消息。**

```text
攻击者任意挑一个数当签名：s = 7
反推消息：m = s^e mod n = 2369
于是 (m=2369, 签名 s=7) 天然通过验证
  [通过] (m, s=7) 通过验证，但这条 m 是攻击者算出来的乱码，冒充不了真实内容
```

教科书 RSA 的验证公式本身就是"拿公钥算一遍看等不等"，所以攻击者从签名反推消息是恒成立的。
好在反推出来的"消息"是随机整数，冒充不了有意义的文本；但一旦协议允许"消息就是一段二进制"，
这类伪造就有实际危害（早期不少协议踩过）。

### 2.3 三道补丁：hash、填充、随机盐

**补丁 1：先 hash，签摘要。**

- 消息任意长 → 固定 32 字节（SHA-256），一次性解决 RSA 的长度限制；
- 攻击者**无法控制 hash 的输出**：想用可乘性伪造，需要 `H(m1)·H(m2) ≡ H(目标) (mod n)`，
  这要求攻击者能构造出指定 hash 的原像，做不到；
- 想用存在性伪造，反推出来的是"某个整数"，但那不是任何消息的 hash。

hash 的强度直接决定签名强度：

| hash 状态 | 对签名的影响 |
|---|---|
| 抗碰撞（collision resistance）失效 | 两份不同文件共用一份签名（SHA-1 已被实际碰撞：2017 年 SHAttered） |
| 抗第二原像失效 | 拿到"正常文件+签名"后，能换出另一份内容但验证仍通过（伪造场景更贴近真实攻击） |
| 抗原像正常 | 由 hash 推不回消息 |

所以"用 SHA-1 签名的 PDF/证书/代码"今天一律视为不可信；SHA-256 起步，能选 SHA-384/SHA-512 更好。

**补丁 2：结构化填充（PKCS#1 v1.5 签名）。**

真实签名不是直接算 `H(M)^d mod n`，而是先把 hash 装进固定结构，再对结构做 RSA：

```text
EM = 00 || 01 || FF FF ... FF || 00 || DigestInfo(SHA-256, H)
     1B   1B    PS：202 字节 0xFF   1B   |<---- 51 字节：算法 OID + 长度 + 32 字节 hash ---->|
总长 256 字节（RSA-2048），PS 至少 8 字节
```

这一步把"可乘性"废掉了：随手乘一个 σ 会把 `FF...FF 00` 的边界弄乱，验签端重新按结构解析时直接拒绝。
`DigestInfo` 里还带 hash 算法标识，防止"用 MD5 的签名冒充 SHA-256 的签名"这类跨算法替换。

> 反面教材：Bleichenbacher 2006 指出，如果验签实现**不严格检查填充结构**（只找 hash 子串），
> e=3 时能伪造签名；2014 年的 BERserk（CVE-2014-1568，影响 NSS/Firefox）就是这类解析漏洞。
> 结论：填充检查必须严格，且必须用标准库。

**补丁 3：随机盐（RSA-PSS）与"确定性签名"。**

PSS 的编码是 `EM = maskedDB || H || 0xbc`，盐随机，所以**同一消息每次签名都不同**，但都能验过。
它把"签名值本身"和"消息"彻底解耦，安全性证明也更强（RSA-PSS 是当前 RSA 签名的首选）。

反过来，**确定性本身不是缺陷**：

- PKCS#1 v1.5 是确定性的（同一消息永远同一签名），但它有严格填充保护，依然安全（只是不再推荐新用）；
- Ed25519 也是确定性的，但它的随机量由"私钥前缀 + 消息"派生，**永不复用、也不依赖随机数质量**。

真正致命的是**随机数被复用**，而不是"签名确定性"。这一点第 6.1 节会用真实数字演示。

## 3. 四种签名算法实测：长度、确定性、耗时

```text
算法                        密钥长度     签名长度  同一消息签两次  签名 ms  验签 ms
--------------------------  -----------  --------  --------------  -------  -------
RSA-2048 / PKCS#1 v1.5      2048 位模数  256 字节  完全相同        1.155    0.084
RSA-2048 / RSASSA-PSS       2048 位模数  256 字节  不同（随机盐）  1.299    0.080
EC P-256 / SHA256withECDSA  256 位曲线   71 字节   不同（随机 k）  1.007    1.850
Ed25519                     256 位       64 字节   完全相同        1.412    1.395
```

（计时含每次新建 `Signature` 对象的开销，只看量级；每次运行的耗时有波动，EC 签名长度也会在 70~72 之间变。）

读法：

- **RSA 签名长度 = 模数长度**：2048 位 → 256 字节。想缩短签名就换曲线算法；
- **ECDSA 的签名长度是浮动的**：DER 编码下 r、s 各可能多一个前导 0，P-256 实测 70~72 字节。
  验签端**不能**假定固定长度（很多手写协议在这里出错）；
- **"签两次一样不一样"不是安全指标**：PKCS#1 v1.5 和 Ed25519 都确定性，ECDSA/PSS 都随机化；
- **速度方向不同**：RSA 验签极快（`e=65537` 只做一次小指数幂运算），签名要算私钥指数；
  ECDSA 验签要做两次标量乘、比签名贵；Ed25519 两者接近。

签名长度和消息长度无关，这一点也实跑了：

```text
签 1 字节的消息：签名 256 字节，耗时 1 ms
签 1 MB 的消息：签名 256 字节，耗时 5 ms
  [通过] 1 字节与 1 MB 的签名长度相同，且 1 MB 的签名仍可验签
```

选型建议：

| 场景 | 推荐 | 备注 |
|---|---|---|
| 新系统、两端自己可控 | **Ed25519** | 64 字节、快、无随机数陷阱、API 最简单 |
| 需要 ECDSA 生态 / 硬件支持 | ECDSA P-256 + SHA-256 | 注意 DER 长度浮动与 nonce 处理 |
| 与 RSA 生态互通（证书、旧系统） | RSA-PSS（3072 位更稳） | 必须兼容旧验签方时才用 PKCS#1 v1.5 + SHA-256 |
| 合规/遗留要求 | PKCS#1 v1.5 + SHA-256 | 只当互操作手段，别当新设计 |
| **不要用** | RSA-1024、SHA-1、MD5、自定义填充 | 已不具备现代安全性 |

## 4. "签名 = 用私钥加密"？半对半错

先看实测：JDK 的 JCE **允许**用私钥做 `ENCRYPT_MODE`，然后公钥能"解密"还原：

```text
【4】"用私钥加密"到底算不算签名？
尝试：Cipher.getInstance("RSA/ECB/PKCS1Padding").init(ENCRYPT_MODE, 私钥)
结果：JCE 允许，密文 256 字节
公钥还原出的明文: 这条消息用私钥"加密"，任何人都能用公钥解开。
  [通过] 用私钥做的这步"加密"，公钥可以完整还原（所以它不提供机密性）
```

这正好暴露这句话的问题：**方向反过来 ≠ 提供了签名**。公钥是公开的，所以"私钥加密"的结果
任何人都能还原——它不提供机密性；它也不等于签名，因为签名该做的四件事它一件也没做。

| 对比项 | 公钥加密（RSA-OAEP） | 数字签名（RSA-PSS） |
|---|---|---|
| 用哪个钥运算 | 公钥加密、私钥解密 | 私钥签名、公钥验签 |
| 目标 | 机密性 | 完整性 + 身份 + 不可否认 |
| 输入 | 任意长数据（实际是混合加密里的密钥） | 固定长度 hash |
| 失败表现 | 解密出乱码 / 抛异常 | 验签返回 false / 抛异常 |
| 可逆性 | 可逆（能拿回明文） | 不可逆（只能判定"是不是"） |

签名和"私钥加密"真正的四点差别：

1. **签名对象是 hash**，不是消息本身；
2. **有结构化填充**（PKCS#1 v1.5 的类型 1 / PSS 的随机盐），让"乘法伪造"失效；
3. **验证是布尔判定**，不存在"解出乱七八糟的东西"这个中间态，失败就是拒绝；
4. **幂运算在数学上双向可逆**，安全性全靠"攻击者构造不出合法填充"，所以填充绝不能手写。

最后一句最实用的结论：**永远不要自己拼 RSA 填充，永远用标准库的标准算法名**
（`RSASSA-PSS`、`SHA256withRSA`、`Ed25519`、`SHA256withECDSA`），
也不要接受调用方传来的"算法名"（防止 `none`/降级攻击）。

## 5. 签名 vs MAC：能证明"有密钥"，还是能证明"是谁"

```text
【5】签名 vs MAC：能证明"有密钥"，还是能证明"是谁"
HMAC-SHA256(K, M) = b8162f0da8ac21ab951d2fb2685f16f6936f633b724d9a308f6a88a27dd3a694
  [通过] 持有 K 的人算出来的 MAC 完全相同
  [通过] MAC 长度固定 32 字节，与消息长度无关
```

HMAC 的问题不在强度（HMAC-SHA256 很安全），而在**密钥是共享的**：
服务器、运维、拿到密钥的攻击者都能算出**一模一样**的 MAC，事后无法向第三方证明"这条是 A 发的"。
这就是"数字签名有不可否认性，MAC 没有"的具体含义。

| | HMAC（对称） | 数字签名（非对称） |
|---|---|---|
| 谁能生成 | 所有持有同一把密钥的人 | 只有私钥持有者 |
| 谁能验证 | 持有密钥的人 | 任何人（公钥公开） |
| 对第三方可证明 | 不能 | 能（不可否认） |
| 性能 | 快（一个 hash 的量级） | 慢得多（大数运算/点乘） |
| 密钥分发 | 需要安全地共享密钥 | 只需分发公钥 |
| 典型用途 | TLS 记录 MAC、会话 token、内部服务鉴权 | 代码签名、JAR 签名、证书、电子合同、区块链 |

一句话记法：**MAC 证明"我们俩共享秘密"，签名证明"这是谁的"**。

## 6. 签名在真实系统里翻车的五种方式

### 6.1 随机数复用 → 私钥被完整算出来（可现场推导）

DSA/ECDSA 的签名公式里有一个每次签名都必须全新的随机数 `k`：

```text
r = (g^k mod p) mod q
s = k^-1 (z + r·d) mod q        d 是私钥，z 是消息摘要
```

如果两次签名用了同一个 `k`，那么 `r` 相同。攻击者看到两组 `(z1, r, s1)`、`(z2, r, s2)` 就能解方程：

```text
k = (z1 - z2) / (s1 - s2) mod q
d = (s1·k - z1) / r mod q
```

用玩具参数（p=23, q=11, g=2）实跑：

```text
签名者私钥 d = 7，公钥 y = g^d mod p = 13
两次签名用了同一个随机数 k = 6（复用！）
签名 1：(r, s1) = (7, 5)，消息摘要 z1 = 3
签名 2：(r, s2) = (7, 9)，消息摘要 z2 = 5
  [通过] 签名 1 本身是合法的（不是伪造，因此泄漏是真的）
  k = (z1 - z2) / (s1 - s2) mod q = 6
  d = (s1*k - z1) / r mod q = 7
  [通过] 复用掉的随机数 k 被还原
  [通过] 私钥 d 被完整还原 -> 从此可以伪造任何签名
```

这不是理论攻击：

- **索尼 PS3（2010）**：ECDSA 的 `k` 是常数，fail0verflow 直接算出私钥，从而能签自制固件；
- **Android 比特币钱包（2013）**：`SecureRandom` 在部分 Android 版本上有缺陷，`k` 重复，私钥批量泄漏；
- 币圈几乎所有"钱包被盗"事件里，都有一批是 nonce 复用/偏置（格攻击）导致的。

修复思路：每个签名都用新的 `k`；做不到就**用确定性派生**（RFC 6979 从"私钥 + 消息"派生 `k`），
这样既不重复也不依赖随机数质量。Ed25519 天生如此——这也解释了为什么它签名两次结果一样却依然安全。

### 6.2 公钥替换：签名没被攻破，攻破的是"你手上是谁的公钥"

```text
真实公钥指纹: 8eb795038f206b8a...
攻击者公钥指纹: 191cefc6810d222a...
攻击者用自己的私钥签了一条"转 900 元给 C"的指令。
  [通过] 用攻击者的公钥验：通过（这条签名确实是攻击者的）
  [通过] 用真实公钥验：拒绝
```

签名算法本身完全正确，问题是"公钥是从哪来的"。公钥来源必须可信：

- **证书链（CA）**：证书 = 公钥 + 身份信息 + CA 的签名；
- **预置指纹 / 公钥固定（pinning）**：App、SSH 的 `known_hosts` 都是这个思路；
- **密钥透明日志（CT）**：让"给谁发过证书"公开可审计。

> 下一节 jarsigner 的输出里正好有一条 `PKIX path building failed: unable to find valid certification path`
> ——这就是"自签证书没有信任锚"时，验签方拒绝承认身份的真实报错。

### 6.3 重放：签名只证明"没被改"，不证明"只发了一次"

```text
  [通过] 同一条 (消息, 签名) 提交两次，两次都验签通过
```

签名绑定的是"消息字节"，没有"这是第几次"的信息。转账、下单、领取优惠券这类动作必须在协议层加：

- 一次性 `nonce` 且服务端去重；
- 时间戳 + 允许的时间窗（同时解决"延迟重放"）；
- 单调递增的流水号（本文消息里就带了"流水号 T-0001"）。

### 6.4 只签了一部分内容 / 签名没绑定上下文

这是**工程上最常见**的翻车方式，而且完全不需要破解密码学：

| 坑 | 例子 | 后果 |
|---|---|---|
| 只签 body 不签元数据 | 只签 HTTP body，不签 amount / 收款方 / 时间 | 攻击者改未签字段 |
| 同一个密钥签多种用途 | 登录 token 和转账指令用同一签名密钥 | 把登录签名搬到转账上（跨协议重放） |
| 不做域分离 | 签名只覆盖 `payload` | 加一个前缀 `"MyApp/v1/transfer"` 就能隔开不同用途 |
| 编码不唯一 | 同一 JSON 多种写法（空格、key 顺序、数字格式） | 验签失败，或不同系统算出不同签名 |
| 验签不绑定元素 | SAML 的 XML Signature Wrapping（XSW）、JWT 的 `alg=none` | 签名有效，但被套到别的元素/被要求不验签 |

防守原则：**签名要覆盖"所有会改变行为的字段"，并且把"用途/版本/接收方"一起签进去**（域分离），
消息序列化用确定性编码（canonical JSON、protobuf 的确定性序列化）。

### 6.5 证书过期、没有时间戳、密钥泄露后没吊销

jarsigner 的实测输出里，几段警告正好对应几个真实问题：

```text
Warning:
This jar contains entries whose certificate chain is invalid. Reason: PKIX path building failed:
sun.security.provider.certpath.SunCertPathBuilderException: unable to find valid certification path to requested target
This jar contains entries whose signer certificate is self-signed.
This jar contains signatures that do not include a timestamp. Without a timestamp, users may not be
able to validate this jar after any of the signer certificates expire (as early as 2027-10-28).
```

- **没有信任锚**：自签证书可以"验签通过"（数学上没问题），但"身份"没人背书；
- **没有时间戳**：证书 2027 年过期后，2026 年签的东西也无法再证明"当时签名是有效的"。
  解决办法是 RFC 3161 时间戳服务：签名时把"签名值"交给 TSA 盖时间戳；
- **密钥泄露后要能吊销**：CRL/OCSP、短期证书、证书透明日志。签名验证的正确问法是
  "**在签名发生的那一刻**，这个公钥是否有效"，而不是"现在是否有效"。

Java 生态里"代码签名"的最小模型就是 jar 签名，脚本第 3 段完整跑了一遍：

```text

2) jar 打包 + jarsigner -sign

3) jarsigner -verify：签名通过

Warning:

jarsigner -verify 退出码: 0

4) keytool -printcert -jarfile：签名者证书与指纹

```

签名后的 jar 里到底有什么？`META-INF/` 下多出三个文件：

```text
META-INF/MANIFEST.MF    每个 entry 一行 SHA-256 摘要
META-INF/DEMO-SIG.SF    对 MANIFEST 的总摘要（+ 逐条摘要）
META-INF/DEMO-SIG.RSA   用私钥对 .SF 的签名（PKCS#7/CMS）
```

实测内容（节选）：

```text
META-INF/MANIFEST.MF：每个 entry 一行 SHA-256 摘要
Manifest-Version: 1.0
Created-By: 17.0.12 (Oracle Corporation)

Name: com/ds/crypto/DigitalSignatureDemo.class
SHA-256-Digest: ynoblM/GJvojm/okitnfGqRi+jvbBLhcMDcvYrb8wNg=

Name: com/ds/crypto/TextbookSignatureDemo.class
SHA-256-Digest: 473pXFHSBgA2x33KxHmZphPiN9gc6PhtlxAu2slTdTY=

Name: com/ds/crypto/DigitalSignatureDemo$Verifier.class
SHA-256-Digest: xFl54aJFlP9D1DG0ZyMpjkT/R3KsSlApG1ue5iCafCU=

Name: com/ds/crypto/Hex.class
SHA-256-Digest: Eo0P+x5iU3OdH8KfHiWjE8AyDcJ/YFDj6+rQNfqNxOE=

META-INF/DEMO-SIG.SF：对 MANIFEST 的总摘要，随后被 demo-signer 的私钥签名成 .RSA
Signature-Version: 1.0
SHA-256-Digest-Manifest: mqhNPH+KhZL4SHopdb6EN73McLkoo/OYd8g/w7MsUC8=
SHA-256-Digest-Manifest-Main-Attributes: q+HEV8m1IwUYwNQHQGsfJAc4lW7q5RD
 I/twsXkQQyTA=
```

**这就是"文件级完整性 + 一个签名"的三层结构**，和我们手写的演示完全同构：

1. 每个 class 单独算 SHA-256 写进 MANIFEST（相当于"每个文件一份摘要"）；
2. MANIFEST 再算一次摘要写进 `.SF`；
3. `.SF` 被私钥签名成 `.RSA`——**只有一份签名需要做 RSA 运算**，成千上万个文件都能被它保护。

所以改动任何一个字节都会断链。实测把 `Hex.class` 追加一个字节：

```text
6) 篡改 jar 里的 com/ds/crypto/Hex.class 一个字节后重新验签
jarsigner: java.lang.SecurityException: SHA-256 digest error for com/ds/crypto/Hex.class
jarsigner -verify（篡改后）退出码: 1
```

报错信息精确点出了问题："`Hex.class` 的 SHA-256 digest 对不上"。这正是第 1 节那种"改一个 bit 就拒绝"
在真实工具链里的化身。顺带一个细节：`.SF` 的文件名是 `DEMO-SIG` 而不是 `demo-signer`——
jarsigner 会把别名截断到 8 个字符，这在写"按文件名找签名块"的脚本时会踩坑。

## 8. 常见误区清单

| # | 常见说法 | 事实 |
|---|---|---|
| 1 | 签名就是"把 hash 用私钥加密" | 只对了一半：现代方案是"hash + 结构化填充 + 私钥运算"，没有填充的裸 RSA 可被伪造（第 2 节） |
| 2 | 验签通过 = 内容安全/可信 | 只能说明"发件人有这把私钥、内容没被改"；内容是否有害、签名者是否可信，是另一回事（SolarWinds 的签名是有效的） |
| 3 | 有签名就不用管重放 | 签名不含"次数/时间"，必须加 nonce/时间戳（6.3） |
| 4 | HTTPS 有证书，就不需要应用层签名 | TLS 只保护"这一次连接"；落库、转发、离线文件都需要自己能验的签名 |
| 5 | 自签证书验签通过就算数 | 数学上通过，但"身份"没人背书（jarsigner 直接报 PKIX path building failed） |
| 6 | 签名长度会随消息变长 | 不会，只由算法/密钥决定（1 字节和 1 MB 都是 256 字节） |
| 7 | ECDSA 签名固定 72 字节 | 不固定，DER 编码在 70~72 之间浮动；按固定长度解析会出错 |
| 8 | 同一消息签两次结果不同才安全 | 不是判据：Ed25519 确定性且安全，关键是 nonce 不能复用 |
| 9 | SHA-1 还能凑合 | 已被实际碰撞（SHAttered），签名场景直接不可用 |
| 10 | 用 `SecureRandom` 就万事大吉 | 历史上有实现缺陷（Android 2013）；ECDSA 建议改为 RFC 6979 确定性派生 |
| 11 | 签名能保密内容 | 不能，签名是明文旁边多一段数据 |
| 12 | 自己实现 RSA 填充/验签逻辑 | 不要。填充解析的细微差别就是历史漏洞来源（BERserk 等），用标准库 + 标准算法名 |

## 9. 落地清单

**选型与参数**

- 新系统：Ed25519；需要曲线/硬件生态：ECDSA P-256；必须兼容 RSA：RSA-PSS，至少 2048 位（3072 更稳）；
- 禁止：RSA-1024、SHA-1、MD5、`alg=none`、调用方传入的任意算法名（防降级）；
- 验签端固定算法白名单，长度/格式严格校验。

**签名覆盖范围（比算法更常出事）**

- 覆盖**所有**会改变行为的字段（金额、收款方、时间、版本、接收方）；
- 加**域分离前缀**（如 `"MyApp/v1/transfer"`），不同用途不共用同一签名空间；
- 序列化用确定性编码，避免"同一语义、不同字节"；
- 把 nonce/时间戳/流水号一起签进去，服务端负责去重。

**密钥管理**

- 私钥放 HSM/KMS，不要进配置文件、日志、CI 变量；
- 轮换计划 + 吊销通道（CRL/OCSP/短期证书）；
- 备份与恢复流程要演练（私钥丢了等于全部历史签名无法追溯）。

**验证端**

- 公钥来源可信（证书链 / 预置指纹 / pinning）；
- 验证"签名发生的那一刻"的证书有效性（配合 RFC 3161 时间戳）；
- 验签失败一律拒绝并记录，不要把异常当"程序错误"吞掉；
- 分布式场景防重放（Redis 去重 nonce 等）。

**后量子（现在开始规划，不用现在上线）**

- NIST 已标准化 ML-DSA（FIPS 204）；生产上先做"混合签名"（经典 + 后量子）双签，验签端先支持；
- 关注证书/固件这些生命周期很长的东西：今天签的固件可能 10 年后还要验。

## 10. 一页速查

```text
签名 = hash + 填充 + 私钥运算；验证 = 同样的填充 + 公钥运算 → 是/否
改一个 bit    → 拒绝
改签名        → 拒绝
换公钥        → 拒绝（但"公钥从哪来"是另一个问题）
同一消息重复提交 → 仍然通过（重放要自己防）
签名不加密    → 消息是明文
```

| 你想要的 | 用什么 |
|---|---|
| 完整性 + 身份 + 不可否认 | 数字签名（Ed25519 / ECDSA P-256 / RSA-PSS） |
| 只要完整性、双方共享密钥、追求快 | HMAC-SHA256 |
| 既要保密又要认证 | 先签名/认证，再加密（或 AEAD + 签名），别用"私钥加密"当签名 |
| 证明"某个时间点就存在" | 签名 + RFC 3161 时间戳 |
| 证明"公钥属于谁" | 证书（CA / pinning / CT） |

## 12. 延伸阅读

- RFC 8017（PKCS#1 v2.2）：RSA 加密与签名、PSS、PKCS#1 v1.5 的权威定义
- RFC 8032：Ed25519 / Ed448（确定性签名的代表）
- FIPS 186-5：DSA / ECDSA / RSA 的数字签名标准（含 EdDSA）
- RFC 6979：确定性 ECDSA/DSA 的 nonce 派生
- RFC 3161：时间戳协议（TSA）
- SHAttered（2017）：SHA-1 实际碰撞，`shattered.io`
- fail0verflow（2010）：PS3 ECDSA 常数 nonce 破解
- BERserk / CVE-2014-1568：PKCS#1 v1.5 验签解析缺陷
- NIST FIPS 204：ML-DSA（后量子签名）
