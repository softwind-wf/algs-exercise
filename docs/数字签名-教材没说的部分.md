教材的原话是：

> "私钥用来对数据'签名'，即加密，且签名后的数据可以公开。所有人都可以通过用公钥解密数据
> 来验证签名，但没有私钥的人无法生成签名的数据。（注意在这个方案中公钥和私钥角色的互换）"

这句话在 1978 年的 RSA 论文语境里是对的；但作为 2026 年的教材，它**跳过了决定安全性的四件事**，
而这个"跳"不是措辞问题——照字面实现，你会得到一个**只能签 255 字节、验证逻辑形同虚设、且可被伪造**的东西。
下面是照字面实现跑出来的结果。

---

## 0. 一页看完全部缺口

| 教材的说法 | 教材没讲 | 照字面实现的后果（实测） |
|---|---|---|
| 私钥对数据"签名"，即加密 | 先 hash，把任意长消息压成固定长度 | 2048 位密钥上限 **255 字节**；1 MB 消息**根本做不了** |
| 用公钥"解密"来验证 | 验证是**布尔判定**，不是解密 | "解密成功"永远为真 ⇒ 忘记比较就**全放行** |
| 公钥和私钥"角色互换" | 只对原始 RSA 幂运算成立 | ECDSA/Ed25519 **没有解密运算**；加密/签名填充不同，不能互换 |
| 没说填充 | PKCS#1 v1.5 的类型 1 填充 / PSS 随机盐 | 不填充 ⇒ **可乘性伪造**：两条签名相乘伪造第三条 |
| 只说"真实、认证、不可否认" | 消息覆盖范围、编码、重放、时间戳 | 只签 body 不签金额；同一签名可重放 |
| 9.8.3.2 证书："公钥 + 可用它解密的加密文本 E" | X.509 字段、链验证、主机名、有效期、吊销、CT | 只验"数学上能解开"，等于没有身份验证 |

一句话总结：**教材给的是"原始 RSA 的直觉"，不是"数字签名方案"。**
现代签名方案 = `hash` + `结构化填充` + `私钥运算` + `验证返回布尔`，四者缺一不可。

## 1. 照字面实现，先跑通短消息

```text
【1】照教材字面实现：σ = m^d mod n，验证 = σ^e mod n 与原文比较
消息 M（87 字节）: 转账指令：2026-10-28 从 A 账户转 100.00 元 给 B 账户（流水号 T-0001）
m = 消息按大端解释成的整数，约 696 位
签名 σ = m^d mod n = 0x6d38fe0b6831...e40827feceb1
签名长度 = 256 字节（RSA 模数长度）
验证（教材版）：用公钥算 σ^e mod n，得到
  m' = 0xe8bdace8b4a6...303031efbc89
  把 m' 还原成字节并与原文比较 -> 相等
  [通过] 教材版：短消息可以"签"也能"验"
```

到这里教材"没错"：`m < n` 时，`σ = m^d mod n` 确实能被任何有公钥的人还原。
但教材没说这个方案的边界，而边界恰好决定了它能不能用。

### 1.1 缺口一：超过 255 字节就做不了

```text
255 字节（首字节 0x00）: m 有 2032 位 < n 的 2048 位 -> 可以签
256 字节（首字节 0xFF）: m 有 2048 位，m ≥ n -> 做不了
1 MB 的消息: m 有 7999999 位，比 n 大得多，教材版连算都没法算
真实方案（RSA-PSS + SHA-256）：1 MB 消息 -> 签名 256 字节，验签 true
```

- 原始 RSA 只能处理"小于 n 的整数"，2048 位密钥的天花板是 **255 字节**（首字节为 0 时的极限）；
- 真实签名先 `SHA-256` 把消息压到 32 字节，**长度不再是问题**（1 MB 与 1 字节的签名都是 256 字节）。

教材缺的第一块：**先 hash**。这不是优化，是可用性的前提。

### 1.2 缺口二："验证 = 解密"没有"是/否"语义

```text
对合法签名做"公钥解密"，去掉左侧补零后得到 87 字节
  前 24 字节（hex）: e8bdace8b4a6e68c87e4bba4efbc9a323032362d31302d32...
  与原消息比较: true

随便拿一个数当签名（s = 12345），"解密"同样"成功"，得到 256 字节垃圾：
  550a1368f710c2a664a1b108fedf2a7c...

如果实现者写成"解密没报错就算验证通过"（照着书本实现时很容易发生）：
  sloppyVerify(任意伪造签名) = true
```

这是教材这句话最危险的地方：**RSA 运算对任何输入都能算出一个整数**，所以"解密成功"永远为真。
照着"解密验证"写代码，只要忘了"再和原文比一比"，就等于完全不验签。
真实 API 是 `Signature.verify(...) -> boolean`，失败直接返回 `false`（或抛异常），语义上不可能"忘了比较"。

教材缺的第二块：**验证是布尔判定**，不是解密出明文。这也顺带解释了为什么验签失败**不告诉你哪里错**
（区分失败原因会泄漏信息，是 padding oracle 一类攻击的入口）。

### 1.3 缺口三 / 四：不 hash、不填充 ⇒ 两种伪造

```text
【4】可乘性伪造（真实 2048 位密钥同样成立）
截获两条"合法签名"：σ(65) 与 σ(66)
相乘：σ(65)*σ(66) mod n = 0x79e258830e...f2a9df63f6
它就是 m3 = 65*66 mod n = 4290 的合法签名
  [通过] 2048 位真实密钥下，乘法伪造同样通过

【5】存在性伪造（先挑签名，再反推消息）
任取 s = 7，反推 m = 7^e mod n = 0x147229cbfb...613592c6d4（约 2045 位）
于是 (m, s) 天然通过教材版验证，攻击者从没碰过私钥
```

- **可乘性**：`(m1^d)(m2^d) = (m1·m2)^d (mod n)`。两条合法签名相乘就是第三条消息的签名；
- **存在性**：验证公式就是"拿公钥算一遍"，所以从签名反推消息恒成立。

hash 同时堵住这两个口子：攻击者控制不了 `H(M)` 的取值，也就拼不出能通过验证的乘积/原像。
填充（`00 01 FF…FF 00 || DigestInfo` 或 PSS 的随机盐）再加一道：**结构不合法直接拒绝**。

## 2. "角色互换"这句话的适用边界

教材让你"注意在这个方案中公钥和私钥角色的互换"。实测发现：这句话在 JDK 上**恰好能跑**，但原因很微妙。

```text
【6】用 JCE 照教材写：私钥 ENCRYPT_MODE + 公钥 DECRYPT_MODE
JCE 允许这条路径：密文 256 字节，公钥还原出 转账指令：...（流水号 T-0001）

同一消息"签"两次，两次密文是否相同 = true
  [通过] 两次结果相同 ⇒ JCE 用的是 PKCS#1 v1.5 的**类型 1**（签名式、确定性）填充
把密文用公钥幂运算算回去，得到 EM 的前 16 字节: 0001ffffffffffffffffffffffffffff
  [通过] EM 以 00 01 FF 开头：确认走的是签名式类型 1 填充

长度上限实测：
  245 字节 -> 可以（密文 256 字节）
  246 字节 -> IllegalBlockSizeException: Data must not be longer than 245 bytes
```

看出来了吗：**JCE 在"私钥加密"时偷偷用了签名填充（类型 1）**，所以"角色互换"能跑通——
但代价是：没有 hash、没有 `DigestInfo`、上限 245 字节、且与标准签名格式不互操作。

真正的答案是：

| 说法 | 何时成立 | 何时不成立 |
|---|---|---|
| 公钥加密、私钥解密 | RSA-OAEP / PKCS#1 v1.5 加密（类型 2 填充） | ECDSA / Ed25519 没有"加密" |
| 私钥签名、公钥验签 | 所有签名方案 | 它不是"加密反过来"，是独立的方案（PSS 有随机盐，Ed25519 连大数运算都没有） |
| 公私钥"角色互换" | 只有原始 RSA 幂运算 `m^e / m^d` 这一层 | 一旦有填充/摘要/曲线，互换就会错（类型 2 填充当签名会被拒；签名填充当加密会泄漏） |
| "签名 = 加密" | 口语比喻 | 工程上必须按签名方案实现，不能拿加密 API 凑 |

所以：**"私钥加密"是理解 RSA 的一个好比喻，但不是实现签名的方法。**

## 3. 教材没讲的原理：为什么是这套结构

### 3.1 陷门单向函数

RSA 的可逆性来自 `e·d ≡ 1 (mod λ(n))`：`(m^d)^e = m`。
- 公钥 `(n, e)` 公开，**任何人都能做 e 次幂**（验签）；
- 私钥 `d` 保密，**只有持有者能做 d 次幂**（签名）；
- 想从公钥推 `d`，等价于分解 `n`——这就是"陷门"。

签名方案本质上是把这个"单向 + 陷门"的方向反过来用：**签名走陷门方向，验证走公开方向。**

### 3.2 必须先 hash 的三个理由

1. **长度**：RSA 一次只吃 `< n` 的整数；hash 把任意消息压成 32 字节；
2. **代数结构**：RSA 保持乘法，hash 是非线性的，破坏这个同态（可乘性伪造失效）；
3. **抗碰撞/第二原像**：要保证"改内容 ⇒ 改摘要"，否则签名可被搬用到另一份文件上（SHA-1 已被实际碰撞，签名场景直接不可用）。

### 3.3 填充在防什么

```text
PKCS#1 v1.5 签名：EM = 00 01 FF FF ... FF 00 || DigestInfo(SHA-256, H)
PSS：            EM = maskedDB || H || 0xbc    （盐随机，每次不同）
```

- 没有填充，攻击者可以用"乘一个 σ"来构造任意新消息的签名（第 1.3 节）；
- 有填充，任何"自己拼出来的"签名都要恰好满足 `00 01 FF…FF 00` 的结构，概率可忽略；
- `DigestInfo` 绑定 hash 算法，防止跨算法替换（用 MD5 的签名冒充 SHA-256）；
- PSS 的随机盐让签名与消息"解耦"，有可证明安全归约，所以是新系统的首选。

### 3.4 为什么验证必须返回"是/否"

验证 = 用公钥做公开运算 + 重算摘要 + 逐字段严格比对，结果只有"通过/拒绝"。
它**不解密**，所以：
- 不会"解出明文"，也就不存在"解密成功即验证通过"这种荒谬语义；
- 失败原因不向外区分（防止 padding oracle 之类信息泄漏）；
- 长度/结构不对就直接拒绝，不需要"先解出来再看看"。

## 4. 具体该怎么做：教材完全没给的落地部分

### 4.1 选算法

| 场景 | 推荐 | 备注 |
|---|---|---|
| 新系统、两端可控 | **Ed25519** | 64 字节、快、无随机数陷阱 |
| 需要曲线/硬件生态 | ECDSA P-256 + SHA-256 | 签名 70~72 字节（DER 浮动） |
| 与 RSA 生态互通 | RSA-PSS（≥2048，3072 更稳） | 兼容旧系统才用 PKCS#1 v1.5 |
| 不要用 | RSA-1024、SHA-1、MD5、自拼填充 | — |

### 4.2 最小代码（JCA，八行）

```java
// 签名
KeyPair kp = KeyPairGenerator.getInstance("Ed25519").generateKeyPair();
Signature signer = Signature.getInstance("Ed25519");
signer.initSign(kp.getPrivate());
signer.update(message);                  // message 是 byte[]，任意长度
byte[] signature = signer.sign();

// 验签：返回值只有 true / false
Signature verifier = Signature.getInstance("Ed25519");
verifier.initVerify(kp.getPublic());
verifier.update(message);
boolean ok = verifier.verify(signature);
```

RSA-PSS 版本只多一行参数（必须签/验两侧一致）：

```java
Signature s = Signature.getInstance("RSASSA-PSS");
s.setParameter(new PSSParameterSpec("SHA-256", "MGF1", MGF1ParameterSpec.SHA256, 32, 1));
```

### 4.3 签名要覆盖什么（教材一个字没提，但工程上最容易错）

- **所有会改变行为的字段**：金额、收款方、时间、版本、接收方；
- **域分离**：前缀 `"MyApp/v1/transfer"`，不同用途不共用签名空间；
- **确定性编码**：canonical JSON / protobuf 确定性序列化，避免"同语义不同字节"；
- **nonce / 时间戳 / 流水号**：签名不防重放（同一签名可以再提交一次）；
- **私钥来源**：HSM/KMS，轮换与吊销。

### 4.4 证书链怎么验（教材 9.8.3.2 只讲概念）

```powershell
# 生成自签证书（实验用）
keytool -genkeypair -alias demo -keyalg RSA -keysize 2048 -sigalg SHA256withRSA `
        -validity 365 -dname "CN=Demo Signer" -storetype PKCS12 `
        -keystore demo.p12 -storepass changeit

# 给 jar 签名 / 验证
jarsigner -keystore demo.p12 -storepass changeit -sigalg SHA256withRSA -digestalg SHA-256 app.jar demo
jarsigner -verify -certs app.jar

# 看证书内容
keytool -printcert -jarfile app.jar
```

我们实跑时 jarsigner 给出的三段警告，正好是教材没讲的三个验证环节：

```text
This jar contains entries whose certificate chain is invalid. Reason: PKIX path building failed:
  ... unable to find valid certification path to requested target
This jar contains entries whose signer certificate is self-signed.
This jar contains signatures that do not include a timestamp. ... after any of the signer certificates expire
```

- **信任锚**：链必须走到浏览器/系统预置的根，否则"数学上验过"也不算数；
- **有效期**：签名发生的那一刻证书有效 → 需要 RFC 3161 时间戳（教材只提"证书"，没提时间）；
- **吊销**：CRL / OCSP / 短期证书；密钥泄露后要让旧签名失效。

### 4.5 证书里到底有什么（X.509 补丁）

教材说"证书由一个公钥 K_A 和一个可以用公钥 K_A 解密的加密文本 E 构成"，这仍是"私钥加密"的口语版。
真实结构是：

```text
Certificate = tbsCertificate || signatureAlgorithm || signatureValue
tbsCertificate = 版本 / 序列号 / 签发者 / 有效期 / 主体名 / 主体公钥 / 扩展(用途、SAN、CRL 地址 ...)
signatureValue = CA 用自己私钥对 tbsCertificate 的签名
```

验证链：**叶证书 → 中间 CA → 根 CA（信任锚）**，再检查主机名匹配、有效期、KeyUsage、
吊销状态，可选证书透明日志（CT）。

## 5. 一页速查：教材版 vs 真实版

| 维度 | 教材字面版 | 真实签名方案 |
|---|---|---|
| 签名对象 | 数据本身（整数必须 < n） | 消息摘要（32 字节）+ 结构化填充 |
| 长度上限 | 255 字节（原始 RSA）/ 245 字节（PKCS#1 v1.5 路径） | 任意长度 |
| 验证 | 公钥"解密"，调用方自己比较 | `verify()` 返回 boolean |
| 可伪造性 | 可乘性伪造 + 存在性伪造 | 两者都不成立 |
| 随机性 | 不涉及 | PSS/ECDSA 随机化；Ed25519 确定性但安全 |
| 安全边界 | 只靠"私钥不泄露" | 私钥 + hash 强度 + 填充校验 + 密钥来源 + 覆盖范围 |
| 证书 | 公钥 + "可解密的 E" | X.509 结构 + 链验证 + 有效期 + 吊销 + 时间戳 |
