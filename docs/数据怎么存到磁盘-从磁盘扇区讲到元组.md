## 第 0 层：硬盘本身

实测（注册表 + 设备 ioctl）：

| 项目 | 值 | 怎么读出来的 |
| --- | --- | --- |
| 磁盘型号 | NVMe `HFM512GD3JX013N`（SK hynix 512GB NVMe SSD） | `HKLM\SYSTEM\CurrentControlSet\Services\disk\Enum` |
| 逻辑扇区 | 512 字节 | `IOCTL_STORAGE_QUERY_PROPERTY` 的 `BytesPerLogicalSector` |
| 物理扇区 | 4096 字节 | 同一 ioctl 的 `BytesPerPhysicalSector` |

关键事实：

1. **磁盘不认识"文件"、不认识"记录"、也不认识"页"。** 它只认"从某个位置开始，读/写 N 个块"。
2. 读写的最小单位是**扇区**。这台 SSD 对外报告逻辑扇区 512B，实际物理扇区 4096B（这叫 512e：接口假装 512，介质其实是 4K）。所以哪怕你只改 1 个字节，设备层面也要读/写一整个 4KB。
3. SSD 内部还有更细的结构：闪存页（读写的单位，通常 4KB–16KB）、擦除块（一擦一大片，通常几 MB）。**写之前必须先擦**，擦除慢且寿命有限——这是"日志式写入、不要频繁原地改"这类设计的物理动机。
4. 一块盘被切成**分区**，分区被格式化成**文件系统**。到这里，"第几号扇区"就变成了"卷内的偏移"。

## 第 1 层：文件系统（NTFS）

| 项目 | 值 |
| --- | --- |
| 卷 | D:（NTFS） |
| 簇大小 | 4096 字节 = 8 个 512B 扇区 |
| 总大小 | 116,444,360,704 字节（约 108 GB） |

**簇（cluster）是文件系统分配空间的最小单位**：一个文件即使只有 1 字节，也要占 1 个簇（4KB）。文件系统还维护一张表：这个文件的第 0 簇放在卷的哪个簇、第 1 簇放在哪……这就是"文件为什么看起来是一串连续字节，而物理上可能东一块西一块"。

## 第 2 层：文件在磁盘上的真实位置

用 `FSCTL_GET_RETRIEVAL_POINTERS` 问文件系统要这个文件的物理分布（`run-storage-page-demo.ps1` 建出来的 `t_demo` 表，relfilenode 23409）：

```
数据文件 : D:\PGData\17\data\base\23354\23409   大小 16384 字节

VCN 0..2  ->  LCN 8256251   共 2 个簇 / 8192 字节，卷内字节偏移 33817604096
VCN 2..4  ->  LCN 8256261   共 2 个簇 / 8192 字节，卷内字节偏移 33817645056
```

两个词：

- **VCN**（Virtual Cluster Number）：文件内部的簇序号，从 0 开始数。用户态看到的"文件偏移 8192"就是 VCN 2。
- **LCN**（Logical Cluster Number）：卷内的簇序号，也就是这块数据在 D: 盘上的真实位置。

所以这 16KB 的文件实际是**两段各 8KB 的物理区域**（LCN 8256251 和 8256261，中间隔着 8 个簇）。文件系统负责把"VCN 2"翻译成"LCN 8256261"，应用程序完全不用管。

**数据库页 8KB = 2 个簇。**第一页正好占 VCN 0..2，第二页正好占 VCN 2..4——每一页都从簇边界开始，不跨簇、不共享簇。这是巧合吗？不是：PostgreSQL 按 8KB 对齐分配，而 NTFS 簇 4KB，8KB 页天然落在偶数簇上。

## 第 3 层：一次「读」在操作系统里怎么走

数据库要读第 0 页时，最终就是一次（或几次）系统调用：

```
你的程序                      read(fd, buf, 8192) / pread64
   │
   ▼
系统调用入口                  把参数从用户栈搬到内核（几十纳秒）
   │
   ▼
VFS + NTFS 驱动               把"文件偏移 8192"翻译成"卷偏移 33817645056"
   │
   ▼
页缓存 (page cache)           4KB 为单位，命中就直接拷贝返回，不碰设备
   │  未命中
   ▼
卷管理器 / 分区层              加上分区起始偏移
   │
   ▼
NVMe 驱动                     组一个 4KB 的读命令塞进提交队列
   │
   ▼
SSD 控制器                    收到命令 → 从 NAND 读出 4KB（或更多）→ 返回
```

实测（本机，数据已在文件系统缓存里）：

```
顺序读同一页 500 次，平均 18.69 µs/次
```

这个 19 µs 里，真正搬数据（8KB 内存拷贝）只占不到 1 µs，大头是**系统调用 + 内核路径 + 页缓存查找**。如果没命中缓存、真的要读设备，NVMe 一次 4KB 读大约几十微秒（比机械盘快两个数量级，但仍是内存的几百倍）。

**这就是"为什么数据库按 8KB 整页读"的物理原因：**

- 一条记录 244 字节，如果按记录读，读一行就要一次系统调用 + 一次设备读（4KB），1 万行就是 1 万次；
- 按 8KB 页读，一次系统调用拿回 33 行，1 万行只要约 300 次；
- 8KB 正好 = 2 个文件系统簇 = 2 个物理扇区，**没有读放大**（不会为了读 8KB 去碰第三个扇区）。

## 第 4 层：数据库把文件切成 8KB 的页

```
数据文件 : D:\PGData\17\data\base\23354\23409   16384 字节 = 2 页

第 0 页 : 文件偏移      0 ~   8191   (VCN 0..2)
第 1 页 : 文件偏移   8192 ~  16383   (VCN 2..4)
```

**证明"数据库里的页"和"磁盘上的这 8192 字节"是同一个东西**：

```
第 0 页  DB 算出的 md5 = 810ac52d194ae2344e034bc0fd4cc368
        文件算出的 md5 = 810ac52d194ae2344e034bc0fd4cc368   [一致]
第 1 页  DB 算出的 md5 = 3100389bdc69413b3530a61387fa98c7
        文件算出的 md5 = 3100389bdc69413b3530a61387fa98c7   [一致]
```

一个用 `md5(get_raw_page('t_demo',0))`（PostgreSQL 自己读出来的页），一个用 PowerShell 直接从文件读前 8192 字节算的。一致，说明中间没有任何"加密/变形"，页就是文件里的这 8192 字节。

### 第 0 页最前面 64 字节

```
      0  00 00 00 00 b8 90 b1 0c 00 00 01 00 9c 00 00 01  |................|
     16  00 20 04 20 00 00 00 00 08 9f e8 01 10 9e e8 01  |. . ............|
     32  18 9d e8 01 20 9c e8 01 28 9b e8 01 30 9a e8 01  |.... ...(...0...|
     48  38 99 e8 01 40 98 e8 01 48 97 e8 01 00 81 e8 01  |8...@...H.......|
```

左边是文件偏移，中间是十六进制字节，右边是能显示的 ASCII（`.` 表示不可显示）。

### 页头 24 字节

| 偏移 | 字段 | 实测值 | 含义 |
| --- | --- | --- | --- |
| 0..7 | pd_lsn | 0/CB190B8 | 本页最后一次修改的 WAL 位置（段号 / 段内偏移） |
| 8..9 | pd_checksum | 0x0000 | 页校验和（本机没开启） |
| 10..11 | pd_flags | 0x0001 | 标志位 |
| 12..13 | pd_lower | 156 | 已用部分末尾 = 空闲空间起点 |
| 14..15 | pd_upper | 256 | 空闲空间末尾 = 元组区起点 |
| 16..17 | pd_special | 8192 | 特殊区起点（普通堆页就是页尾） |
| 18..19 | pd_pagesize_version | 0x2004 | 高 13 位 8192 = 页大小，低 3 位 4 = 格式版本 |
| 20..23 | pd_prune_xid | 0 | 清理用的最早事务号 |

空闲空间 = `256 − 156 = 100` 字节。

### 行指针数组

每个行指针 4 字节，是一个打包的 32 位整数：

```
 31              17 16  15 14                              0
┌──────────────────┬──────┬────────────────────────────────┐
│   lp_len (15 位)  │ flags│       lp_off (15 位)            │
└──────────────────┴──────┴────────────────────────────────┘
```

实测前 5 项（原始 4 字节 → 解出的三元组）：

```
lp   原始4字节      lp_off   flags   lp_len
 1   08 9f e8 01      7944       1      244
 2   10 9e e8 01      7696       1      244
 3   18 9d e8 01      7448       1      244
 4   20 9c e8 01      7200       1      244
 5   28 9b e8 01      6952       1      244
```

以第 1 项为例：`08 9f e8 01` 小端读成 0x01E89F08，低 15 位 = 0x1F08 = 7944，中间 2 位 = 1（正常），高 15 位 = 0xF4 = 244。**从 4 个字节里就读出了"第 1 行在这页的 7944 处、长 244 字节"**。

## 第 5 层：一个元组的 244 字节

第 1 个行指针指向页内偏移 7944，从那里开始的 244 字节就是一行：

```
   7944  68 0d 00 00 00 00 00 00 00 00 00 00 00 00 00 00  |h...............|
   7960  01 00 03 00 02 09 18 00 01 00 00 00 13 73 74 75  |.............stu|
   7976  64 65 6e 74 31 00 00 00 30 03 00 00 78 78 78 78  |dent1...0...xxxx|
   7992  78 78 78 78 78 78 78 78 78 78 78 78 78 78 78 78  |xxxxxxxxxxxxxxxx|
```

逐字段拆开：

### 元组头（23 字节 + 1 字节对齐 = 24）

| 元组内偏移 | 长度 | 原始字节 | 字段 | 解出的值 | 含义 |
| --- | --- | --- | --- | --- | --- |
| 0..3 | 4 | `68 0d 00 00` | t_xmin | 3432 | 插入这一行的事务号 |
| 4..7 | 4 | `00 00 00 00` | t_xmax | 0 | 0 = 没被删；非 0 = 删除事务号 |
| 8..11 | 4 | `00 00 00 00` | t_field3 | 0 | cmin/cmax（同事务内第几次改） |
| 12..15 | 4 | `00 00 00 00` | t_ctid.block | 0 | 物理地址的块号 |
| 16..17 | 2 | `01 00` | t_ctid.posid | 1 | 物理地址的槽号 → ctid = **(0,1)** |
| 18..19 | 2 | `03 00` | t_infomask2 | 0x0003 | 低 11 位 = 3 个属性 |
| 20..21 | 2 | `02 09` | t_infomask | 0x0902 | 各种状态位（含"已提交"提示位） |
| 22 | 1 | `18` | t_hoff | 24 | 数据从元组第 24 字节开始 |
| 23 | 1 | `00` | 空值位图 | 无空值 | 没有 NULL 就不占位 |

### 属性区

| 元组内偏移 | 长度 | 原始字节 | 字段 | 解出的值 |
| --- | --- | --- | --- | --- |
| 24..27 | 4 | `01 00 00 00` | id (integer) | **1** |
| 28 | 1 | `13` | name 的变长头 | 1 字节格式，长度 = 0x13 >> 1 = **9** |
| 29..36 | 8 | `73 74 75 64 65 6e 74 31` | name 的数据 | "**student1**" |
| 37..39 | 3 | `00 00 00` | 对齐填充 | 让下一个字段落到 4 字节边界 |
| 40..43 | 4 | `30 03 00 00` | pad 的变长头 | 4 字节格式，长度 = 0x330 >> 2 = **204** |
| 44..243 | 200 | `78 78 ...` | pad 的数据 | 190 个 'x' + 10 个空格（char(200) 补空格） |

合计 24 + 4 + 9 + 3 + 204 = **244** 字节，和行指针里的 lp_len 完全对上。

**从磁盘字节直接还原出的这一行：**

```
1 | student1 | xxxxxxxxxx...(190 个 x)
```

到这一步，"数据存在磁盘上"这句话就落地了：**它就是文件里从偏移 7944 开始的 244 个字节**，没有任何魔法。数据库做的，只是在上面套了一层又一层"按什么规则解释这些字节"的约定。

## 第 6 层：再往上，全是"解释规则"

同一批字节，不同层看到不同的东西：

| 层 | 看到什么 | 用什么规则解释 |
| --- | --- | --- |
| 硬盘 | 扇区 | 只认扇区号和长度 |
| NTFS | 簇、extent 表 | VCN ↔ LCN 映射 |
| 文件 | 字节数组 | 偏移 |
| PostgreSQL 页层 | 页头 + 行指针 + 元组区 | `pd_lower` / `pd_upper` / 32 位行指针 |
| 元组层 | 元组头 + 属性区 | `t_hoff` + 属性对齐 + 变长头 |
| 表/schema 层 | id / name / pad 三列 | catalog 里的列类型和顺序 |

**核心换算式**（这条式子把逻辑地址一路算到物理位置）：

```
行 (p, s)                                    ← ctid：第 p 页、第 s 个槽
  ↓ 页号 p
文件偏移 = p × 8192 + 行指针[p][s].lp_off     ← 本例：0 × 8192 + 7944 = 7944
  ↓ 文件偏移
卷内偏移 = extent 表(VCN = 文件偏移 ÷ 4096) × 4096 + (文件偏移 mod 4096)
  ↓ 卷内偏移
物理位置 = 分区起始偏移 + 卷内偏移
  ↓
SSD 的某个 NAND 页
```

## 把整条链串起来

**写**（`INSERT`）：

1. 应用发 SQL，数据库算出一条 244 字节的元组；
2. 找一个有空位的页（FSM），在内存里把元组写到 `pd_upper` 往下的位置，行指针登记 (7944, 1, 244)，`pd_lower`/`pd_upper` 更新；
3. 先把"改了第 0 页第几槽"写进 WAL 文件（顺序追加，一次 `write` 到另一个文件）；
4. 提交返回；页留在内存的缓冲池里，标记为脏；
5. 之后某刻，缓冲池把整个 8KB 页交给操作系统写回 `base/23354/23409` 的偏移 0——**写回是整页 8KB，不是 244 字节**；到盘上就是 2 个 4KB 物理扇区。

**读**（`SELECT ... WHERE id=1`）：

1. 索引给出 ctid = (0,1)；
2. 缓冲池里找第 0 页，没有就 `read(fd, buf, 8192)` 读进来；
3. 从页偏移 24 取第 1 个行指针 → 7944 / 244；
4. 从页偏移 7944 取 244 字节，`t_hoff=24` 开始解属性：id=1、name='student1'、pad='xxx...'；
5. 查 `t_xmin=3432` 这个事务是否已提交、是否可见，可见就返回。

## 常见误解（物理层版）

| 误解 | 物理事实 |
| --- | --- |
| 磁盘能按字节寻址 | 只有扇区，512B 或 4KB 起读 |
| 改 1 个字节只写 1 个字节 | 物理扇区 4KB，读改写或整页 8KB 写回 |
| 文件是连续的 | 文件是一张 extent 表，本例 16KB 就分了两段 |
| 数据库页是"虚拟"的 | md5 对得上：页就是文件里的 8192 字节 |
| 记录是数据库直接写到盘上的 | 记录先写成页内布局，整页才落盘 |
