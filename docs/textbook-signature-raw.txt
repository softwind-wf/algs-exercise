教材原话（9.8.3.1）：
  "私钥用来对数据'签名'，即加密……所有人都可以通过用公钥解密数据来验证签名，
   但没有私钥的人无法生成签名的数据。（注意在这个方案中公钥和私钥角色的互换）"

下面严格按这句话实现（原始 RSA，不做 hash、不做填充）。
密钥：RSA 2048 位，n 有 2048 位，e = 65537

==================================================================
【1】照教材字面实现：σ = m^d mod n，验证 = σ^e mod n 与原文比较
==================================================================
消息 M（87 字节）: 转账指令：2026-10-28 从 A 账户转 100.00 元 给 B 账户（流水号 T-0001）
m = 消息按大端解释成的整数，约 696 位
签名 σ = m^d mod n = 0x6d38fe0b6831...e40827feceb1
签名长度 = 256 字节（RSA 模数长度）

验证（教材版）：用公钥算 σ^e mod n，得到
  m' = 0xe8bdace8b4a6...303031efbc89
  把 m' 还原成字节并与原文比较 -> 相等
  [通过] 教材版：短消息可以"签"也能"验"
→ 到这里教材没说错，但也没说边界在哪。下面逐条踩。

==================================================================
【2】问题一：教材版只能签 255 字节以内——教材只字未提
==================================================================
255 字节（首字节 0x00）: m 有 2032 位 < n 的 2048 位 -> 可以签
  [通过] 255 字节（首字节 0x00）可以直接做 RSA
256 字节（首字节 0xFF）: m 有 2048 位，m ≥ n -> 做不了
  [通过] 256 字节可能已经 ≥ n，教材版直接失败
1 MB 的消息: m 有 7999999 位，比 n 大得多，教材版连算都没法算
  [通过] 教材版对 1 MB 消息无能为力（m ≥ n）

真实方案（RSA-PSS + SHA-256）：1 MB 消息 -> 签名 256 字节，验签 true
  [通过] 真实方案靠 hash 把消息压到 32 字节，长度不再是问题
→ 教材缺的第一块：先 hash。没有它，RSA 只能签"比 n 小"的整数，
  2048 位密钥的上限就是 255 字节（首字节为 0 时的极限）。

==================================================================
【3】问题二："验证 = 公钥解密"没有是/否语义，忘记比较就等于不验签
==================================================================
对合法签名做"公钥解密"，去掉左侧补零后得到 87 字节
  前 24 字节（hex）: e8bdace8b4a6e68c87e4bba4efbc9a323032362d31302d32...
  与原消息比较: true
  [通过] 教材版验证确实要"解密 + 逐字节比较"两步，比较这步靠调用方

随便拿一个数当签名（s = 12345），"解密"同样"成功"，得到 256 字节垃圾：
  550a1368f710c2a664a1b108fedf2a7c...
  [通过] 任何字节都能被"解密"成某个整数——所以"解密成功"不能当验证判据

如果实现者写成"解密没报错就算验证通过"（这在照着书本实现时很容易发生）：
  sloppyVerify(任意伪造签名) = true
  [通过] 这种实现会把任何伪造签名都判为通过（攻击者只需随便造 256 字节）
→ 教材缺的第二块：验证的输出必须是"是/否"，不是"一段解密结果"。
  真实 API 是 Signature.verify(...) -> boolean，失败直接 false/异常。

==================================================================
【4】问题三：不 hash ⇒ 可乘性伪造（真实 2048 位密钥同样成立）
==================================================================
截获两条"合法签名"：σ(65) 与 σ(66)
相乘：σ(65)*σ(66) mod n = 0x79e258830e...f2a9df63f6
它就是 m3 = 65*66 mod n = 4290 的合法签名
  [通过] 2048 位真实密钥下，乘法伪造同样通过（与教材假设的密钥大小无关）
→ 教材缺的第三块：hash 破坏 RSA 的乘法同态；
  否则"两个合法文件的签名相乘"就得到第三个文件的签名，私钥根本不用出场。

==================================================================
【5】问题四：不 hash ⇒ 存在性伪造（先挑签名，再反推消息）
==================================================================
任取 s = 7，反推 m = 7^e mod n = 0x147229cbfb...613592c6d4（约 2045 位）
于是 (m, s) 天然通过教材版验证，攻击者从没碰过私钥
  [通过] 先选签名 s，再令 m = s^e mod n，教材版验证必然通过
→ 这类伪造在真实世界里有时有危害（协议把"消息"当任意二进制时），
  教材缺的第四块：hash 让攻击者无法反推成"有意义的文本"。

==================================================================
【6】用 JCE 照教材写：私钥 ENCRYPT_MODE + 公钥 DECRYPT_MODE
==================================================================
JCE 允许这条路径：密文 256 字节，公钥还原出 转账指令：2026-10-28 从 A 账户转 100.00 元 给 B 账户（流水号 T-0001）
  [通过] JCE 确实能按教材字面做出来（这就是教材没提醒的地方）

同一消息"签"两次，两次密文是否相同 = true
  [通过] 两次结果相同 ⇒ JCE 用的是 PKCS#1 v1.5 的**类型 1**（签名式、确定性）填充
把密文用公钥幂运算算回去，得到 EM 的前 16 字节: 0001ffffffffffffffffffffffffffff
  00 01 FF FF ... 说明是类型 1（签名式）填充，不是加密式的类型 2（随机）填充；
  换句话说，JCE 的"私钥加密"实际上已经偷偷用了签名填充——
  但它没有 hash、没有 DigestInfo，所以只能签 245 字节以内，也无法和标准签名互操作。
  [通过] EM 以 00 01 FF 开头：确认走的是签名式类型 1 填充

长度上限实测：
  245 字节 -> 可以（密文 256 字节）
  [通过] 2048 位 + PKCS#1 v1.5 的单次上限 = 256 - 11 = 245 字节
  246 字节 -> IllegalBlockSizeException: Data must not be longer than 245 bytes
  [通过] 246 字节直接抛异常（教材完全没提这个上限）

→ 更要命的是：这条路径只对原始 RSA 存在。ECDSA/Ed25519 里根本没有"解密"运算，
  "公钥私钥角色互换"这句话在那两种算法上直接不成立。

==================================================================
【7】真实方案：同一把密钥、同一条消息，四项对照
==================================================================
RSA-PSS：签名 256 字节；同一消息两次签名相同 = false
  [通过] PSS：合法签名验签通过
  [通过] PSS：改一个字节即拒绝
  [通过] PSS：改签名即拒绝
SHA-256(M) = 0049f6b7979b89eb9327e4b8c399b2b7bbb0f1016b97c944e0cd5dac98cdcd86

四项对照：
  长度上限  教材版 255 字节 / 真实版任意长度（签 32 字节 hash）
  伪造      教材版可乘性伪造 + 存在性伪造 / 真实版两者都不成立
  验证语义  教材版返回"解密结果"，要调用方自己比 / 真实版返回 boolean
  覆盖范围  教材版只覆盖消息字节 / 真实版还要求签名覆盖上下文（域分离、时间戳）
