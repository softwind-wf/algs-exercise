链：localhost（服务器证书）  <-中间 CA 签发-  Alg4 Demo Intermediate CA  <-根签发-  Alg4 Demo Root CA（自签）
   第一层的"签发者"= 第二层的"主体"，这就是它能拼成链的原因。
   根的私钥对应信任锚；中间 CA 的存在是为了根私钥能离线——
   日常签发用中间 CA 的私钥，它泄露了可以吊销换新，根不动。
  [通过] server 的 issuer == intermediate 的 subject
  [通过] intermediate 的 issuer == root 的 subject
  [通过] root 自签：issuer == subject
  [通过] intermediate 是 CA (=true)，且 pathLen=0（只能签终端证书，不能再签 CA）
  [通过] server 是终端证书（CA:false）
  [通过] 根的到期时间不早于中间 CA（根活得最久）

【2】逐级验签：每一环都用上一环的公钥验
==================================================================
  [通过] server 证书 -> 用 intermediate 公钥验签通过
  [通过] intermediate 证书 -> 用 root 公钥验签通过
  [通过] root 证书 -> 用自己的公钥验签通过（自签，自己给自己背书）
  [通过] server 证书 -> 直接用 root 公钥验，拒绝（中间的签名对不上根的公钥）

注意最后一行的含义：签名验证不做"信任判断"，它只回答"是不是这把私钥签的"。
"要不要信"是链拼接 + 信任锚 + 各项策略检查（有效期/用途/主机名）合起来决定的。

==================================================================
【3】PKIX 校验：把"信任锚"换掉，结论就变
==================================================================
  [通过] 信任锚 = 我们的 root -> 校验通过
  校验路径：server -> intermediate -> root(锚)
  [通过] 信任锚换个不相干的根 -> 校验失败
  失败原因：CertPathValidatorException: Path does not chain with any of the trust anchors

同一条链、同样的签名，信任锚不同结论就相反：所谓"可信"，
从来不是证书自身的属性，而是"它能不能连到我已经信任的那张根证书上"。

【4】真 TLS 握手：让 JDK 的默认校验器来判卷
==================================================================
做法：本地起一个 SSLServerSocket（用 keytool 生成的私钥与证书链），
客户端只信任我们的 root，并且打开 HTTPS 式的主机名校验
（SSLParameters.setEndpointIdentificationAlgorithm("HTTPS")）。
失败原因从握手异常的 cause 链里抠出来，连 JDK 自己的原话一起打印。

  结果：握手成功，之后可以开始传数据

【场景 5】证书只写了 CN=localhost、没有 SAN（不预设结论，实测 JDK 的行为）：
  结果：握手成功 —— JDK 的 HTTPS 校验在 SAN 缺失时仍回退到 CN（RFC 2818 的老规矩）。
  但这不代表可以依赖它：浏览器对公开 CA 的证书只认 SAN，CA/B Forum 2017 年起
  就不再签发"只有 CN"的证书。自己给自己签测试证书时，务必带上 SAN。

这 5 个场景全部由客户端默认校验器自动完成，应用代码只是连了一下：
链拼接、签名、有效期、CA 资格、用途、主机名，六道里错了任何一道都握手失败。

【5】小结：证书在 TLS 里干了什么
==================================================================
1) 服务器把 证书链（不是公钥）发给客户端；
2) 客户端用预置的根证书验证这条链 -> 确认"这个公钥确实属于这个域名"；
3) 用握手过程临时协商出的对称密钥保护后续数据；
4) 证书只在"证明身份"这一步用到，它不参与加密业务数据。

所以整个 HTTPS 的安全感，建立在两种东西上：
  - 数学：签名/密钥交换无法伪造；
  - 信任：那一百多张预置根证书背后的组织不会乱签。
后者是运营与审计问题，不是密码学问题——证书体系把这两件事强行绑在了一起。
