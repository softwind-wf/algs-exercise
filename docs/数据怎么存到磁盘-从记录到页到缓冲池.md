# 数据怎么存到磁盘、又怎么读出来

一句话版本：**数据库不是"一行一行存取"，而是"一页一页搬"。** 一条记录先被装进一个 8KB 的页里，页在内存的缓冲池中被修改；改页之前先把"要改什么"顺序写进日志（WAL）；脏页之后才整块写回磁盘的数据文件。读的时候反过来：先拿到这条记录所在页的块号，把这个 8KB 整页搬进内存，再在页内按偏移切出那一行。

本文是实机演示的说明。所有数字都来自真实跑库，原始输出在 `docs/storage-page-demo-raw.txt`，一条命令可复现：

> 想继续往底层看（磁盘扇区、文件系统簇、文件字节怎么变成页和元组），见 [数据怎么存到磁盘-从磁盘扇区讲到元组.md](<数据怎么存到磁盘-从磁盘扇区讲到元组.md>)；再往下到盘片材质、磁记录原理、NAND 电荷，见 [数据怎么存到磁盘-磁盘材质与读写原理.md](<数据怎么存到磁盘-磁盘材质与读写原理.md>)。

## 0. 先看整体：一条记录的五层容器

```
SQL 一行数据                                     ← 逻辑层：DBMS 看到的"行"
  └── 元组 (tuple / heap tuple)，244 字节         ← 页内的那条记录
        └── 页 (page / block)，8192 字节          ← 磁盘 I/O 的最小单位
              └── 数据文件 (段 segment)，最大 1GB  ← 一个文件装很多页
                    └── 文件系统块 4096 字节        ← OS 眼中的块
                          └── 磁盘扇区 512B / 4KB  ← 硬件真正读写的单位
```

PostgreSQL 的默认设置（本次实测）：

| 项目 | 值 | 从哪看 |
| --- | --- | --- |
| 页大小 block_size | 8192 字节 | `SHOW block_size;` |
| 共享缓冲池 shared_buffers | 128MB（= 16384 个页） | `SHOW shared_buffers;` |
| 数据文件位置 | `D:/PGData/17/data/base/23354/23409` | `pg_relation_filepath('t_demo')` |
| 文件与页 | 表 40 行 → 2 页 = 16384 字节 | `pg_relation_size('t_demo')` |

关键词：`base/<数据库 OID>/<relfilenode>`。**表在磁盘上就是一个按页编号的大文件**，第 0 页从偏移 0 开始，第 1 页从偏移 8192 开始，第 n 页从 n×8192 开始。没有"第几行"的位置概念，只有"第几页、页内第几个槽"。

## 1. 页长什么样

8KB 页的布局（PostgreSQL，`t_demo` 第 0 页实测）：

```
偏移 0                                                       偏移 8192
┌──────────┬───────────────────┬─────────────┬──────────────────────┐
│ 页头 24B │ 行指针数组 (32×4B) │   空闲空间   │  元组区（从后往前长）  │
└──────────┴───────────────────┴─────────────┴──────────────────────┘
           ↑ pd_lower=152                 ↑ pd_upper=256
```

- `pd_lower`：已用部分（页头 + 行指针数组）的末尾，空闲空间从这里开始。
- `pd_upper`：空闲空间的末尾，元组区从这里往后（往页尾方向）堆。
- 两者之间 `pd_upper - pd_lower = 256 - 152 = 104` 字节，就是这一页还能塞下的空隙。
- `pd_special = 8192`：页尾特殊区起点（普通堆页没有特殊区，所以就是页尾）。

算一遍验证：页头 24 + 32 个行指针 × 4 = 128，所以 `pd_lower = 152`；32 个元组每个占 248 字节（244 + 4 字节对齐填充），`pd_upper = 8192 − 32×248 = 256`。正好对上。

### 1.1 页头 24 字节：每一页的"目录卡片"

| 字段 | 字节 | 含义 |
| --- | --- | --- |
| pd_lsn | 0–7 | 最后一次修改这一页的 WAL 位置（崩溃恢复用） |
| pd_checksum | 8–9 | 页校验和（本机未开启，所以是 0） |
| pd_flags | 10–11 | 标志位 |
| pd_lower | 12–13 | 空闲空间起点 |
| pd_upper | 14–15 | 空闲空间终点 |
| pd_special | 16–17 | 特殊区起点 |
| pd_pagesize_version | 18–19 | 高 13 位页大小 8192 + 低 3 位格式版本 4 = 0x2004 |
| pd_prune_xid | 20–23 | 最早可清理事务号（配合 VACUUM） |

实测：`page_header(get_raw_page('t_demo',0))` 给出 `lower=152, upper=256, special=8192`；把这一页最前面的 32 字节原样打印出来，按字段切开：

```
00 00 00 00 28 1b b1 0c │ 00 00 │ 00 00 │ 98 00 │ 00 01 │ 00 20 │ 04 20 │ 00 00 00 00 │ 08 9f e8 01 │ 10 9e e8 01
   最后一次修改的 WAL 位置     校验和   标志    lower    upper  special  0x2004      prune_xid      行指针 1        行指针 2
                                              =152     =256   =8192
```

手工解出来同样是 152 / 256 / 8192 / 0x2004，和 pageinspect 一字不差（多字节整数在本机是小端序，低位字节在前，所以 `98 00` 要读成 0x0098）。**所谓"页格式"不是玄学，就是一张固定偏移的字节表。**

### 1.2 行指针：页内的"门牌号目录"

每个行指针 4 字节（32 位），小端序存一个整数，位段是：

```
 31              17 16   15 14                              0
┌──────────────────┬───────┬─────────────────────────────────┐
│   lp_len (15 位)  │ flags │       lp_off (15 位)             │
└──────────────────┴───────┴─────────────────────────────────┘
```

- `lp_off`：元组在这一页内的字节偏移。
- `flags`：1=正常，2=重定向（指向同一页里的新版本），3=死（已被清理、指向已不存在的元组），0=未使用（可复用）。
- `lp_len`：元组总长度。

实测第 1 个行指针的原始 4 字节 `08 9f e8 01` 解出来是 `lp_off=7944, flags=1, lp_len=244`：元组 1 从页内偏移 7944 开始，长 244 字节，正好顶到页尾 8192。

行指针数组**从页头往后长**，元组**从页尾往前长**，两边往中间挤，中间剩下的就是 `pd_upper - pd_lower` 这块空地。页里删掉的空位不会立刻消失，靠后面的 VACUUM 回收。

## 2. 写路径：一条 INSERT 到底做了什么

```
INSERT INTO t_demo VALUES (100,'student100',...)
  │
  ├─1─ 执行器决定往哪张表、哪个索引插
  ├─2─ 查 FSM（空闲空间映射，fork 1）找一个还有空位的页 → 块号 0
  ├─3─ 在共享缓冲池里 pin 住第 0 页；不在内存就先从磁盘读 8KB 进来
  ├─4─ 在页内从 pd_upper 处向前分配元组空间，写入 t_xmin、字段数据
  ├─5─ 在行指针数组末尾登记新的行指针（lp_off / lp_len / flags）
  ├─6─ 更新页头 pd_lower/pd_upper，把这一页标记为"脏页"
  ├─7─ 往 B+ 树索引里插入一条 (key=100, ctid=(0,10))
  ├─8─ 【提交】把"我改了哪页哪个槽"的 WAL 记录顺序写进 WAL 文件并 fsync
  └─9─ 提交返回。此刻数据文件可能还是旧的，脏页留在内存里
        ↓ 之后某一刻
      bgwriter / CHECKPOINT 把脏页整块写回数据文件
```

### 2.1 证据一：WAL 先落盘，数据页后落盘

脚本插入一行 `id=100`，**不做** CHECKPOINT，直接去磁盘上读数据文件：

```
检查点之前，数据文件里有 student100 吗?   没有 —— 数据还只在内存的缓冲页里
检查点之后，数据文件里有 student100 吗?   有 —— 脏页被写回磁盘
```

但同一时刻，WAL 已经写好了。用 `pg_waldump` 把这一小段 WAL 的原始记录打出来：

```
rmgr: Heap        ... desc: INSERT off: 10, flags: 0x01, blkref #0: rel 1663/23354/23409 blk 0 FPW
rmgr: Btree       ... desc: INSERT_LEAF off: 41, blkref #0: rel 1663/23354/23415 blk 1 FPW
rmgr: Transaction ... desc: COMMIT
```

三条记录正好对应上面第 7、8 步：堆页插入（第 0 页、第 10 个槽）、B 树叶子插入（key 100 在 index 第 1 页第 41 项）、提交。`FPW` = Full Page Write，本页自上次检查点后第一次修改，改动前的整页也顺手存进 WAL，防止"页写了一半崩溃"。

WAL 位置从插入前的 `0/CB150A8` 涨到插入后的 `0/CB19478`。**提交只保证 WAL 在磁盘上；数据页可以晚点再写。** 这就是"崩溃也能恢复"的底气：重放 WAL 就能把内存里没来得及写回去的修改补上。

### 2.2 证据二：缓冲池里那一页是"脏"的

```
表      fork  页号  是否脏页  使用计数
t_demo  0     0     t        5        ← 主数据页，已被改过、还没写回
t_demo  0     1     t        5
t_demo  1     0     t        3        ← FSM：记录每页还剩多少空位
t_demo  2     0     t        3        ← VM：可见性映射，配合 VACUUM 判死活
```

- `fork 0` 主数据；`fork 1` 空闲空间映射（插入时靠它找页）；`fork 2` 可见性映射（扫描时跳过"全是活行"的页）。
- "使用计数"（usagecount）是缓冲池的时钟算法用的，命中一次加一，满了就淘汰计数最低的页。

## 3. 读路径：一条 SELECT 怎么找到那一行

```
SELECT * FROM t_demo WHERE id = 40;
  │
  ├─1─ 规划器选访问路径：走主键索引（代价 0.14..8.16）还是全表顺序扫描
  ├─2─ 索引扫描：B+ 树从根往下走到叶子，叶子项 = (key, ctid)
  │      拿到 ctid = (1,8) —— 第 1 页、第 8 个槽
  ├─3─ 用 (表, 块号) 做键查缓冲池哈希表
  │      命中 → 直接拿到内存里的页
  │      未命中 → 向磁盘要这一页：读 8KB，找一个空闲缓冲槽放进去（可能淘汰别人）
  ├─4─ 页头校验（LSN/校验和）→ 行指针数组第 8 项 → 偏移 + 长度
  ├─5─ 切出元组，检查 t_xmin 是否对本事务可见（MVCC），不可见就继续找
  └─6─ 按属性偏移把字段逐个解出来，返回给执行器
```

实测的执行计划（`EXPLAIN (ANALYZE, BUFFERS)`）：

```
Index Scan using t_demo_pkey on t_demo  (actual time=0.006..0.007 rows=1)
  Index Cond: (id = 40)
  Buffers: shared hit=2
```

`shared hit=2`：一个索引页 + 一个数据页，都命中内存。如果是冷缓存，这里会显示 `shared read`，那就意味着真的发生了两次磁盘 I/O。

三组对比：

| 查询 | 访问路径 | Buffers |
| --- | --- | --- |
| `WHERE id = 40` | Index Scan：B 树定位 → ctid → 堆页 | shared hit=2 |
| `WHERE ctid = '(1,1)'` | Tid Scan：直接按物理地址取页 | shared hit=1 |
| `WHERE pad LIKE '%zzz%'` | Seq Scan：从第 0 页扫到最后一页 | shared hit=2 |

`ctid` 是 PostgreSQL 给的"物理地址"= (块号, 槽号)。它**会变**（更新后行会换位置），所以业务上不能用它当主键——只能用来做"这一页上还有哪些行"这类物理层的观察。

## 4. 为什么非要"按页"存取

磁盘（尤其机械盘）的随机访问代价极高：

| 操作 | 典型耗时 | 折算 |
| --- | --- | --- |
| 机械盘寻道 | 约 8–10 ms | 一次随机读 = 找一个 8KB 页 |
| 机械盘顺序读 | 100–200 MB/s | 顺序读 8KB 约 0.05 ms |
| SATA SSD 4K 随机读 | 50–100 µs | 比机械盘快约 100 倍 |
| NVMe SSD 4K 随机读 | 20–80 µs | 再快 2–5 倍 |
| 内存访问 | 约 100 ns | 比磁盘快千倍以上 |

结论：

1. **一次 I/O 必须尽量多拿数据**。读 8KB 顺手带回几十条记录，比按行读上千次便宜得多。
2. **把热页留在内存**。缓冲池（128MB = 16384 页）把随机 I/O 变成大部分命中。
3. **写也要摊平**。WAL 是顺序追加写；真正的随机写（脏页回写）交给 bgwriter/检查点批量做。
4. **页内空间要管理**。FSM 告诉你哪页还有空位，插入不会盲目找页；页填满了才开新页。

代价也要说清楚：写放大（改一个字节也要整页读进来、整页写回去）、删了空间不立刻还给文件、需要 VACUUM 清理死人。

## 5. 删一行、改一行：为什么页不会变小

```
DELETE FROM t_demo WHERE id = 10;
UPDATE t_demo SET pad = ... WHERE id = 11;
```

实测（页数仍然是 2，一个字节都没少）：

| lp | lp_off | lp_flags | lp_len | t_xmin | t_xmax | t_ctid |
| --- | --- | --- | --- | --- | --- | --- |
| 10 | 0 | 3（死） | 0 | — | — | — |
| 11 | 5712 | 1（正常） | 244 | 3432 | 3435 | (0,33) |

- **DELETE 不是擦掉数据**，只是给这一行写上 `t_xmax = 删除事务号`，告诉所有人"从这一刻起这行不可见"。数据还在页里。
- **UPDATE 也不是原地改**。它写一个**新版本**（这里落在第 0 页第 33 槽），旧版本的 `t_ctid` 指向新版本 `(0,33)`，形成一条"版本链"。`SELECT` 时从链头往下找第一个对本事务可见的版本。
- 这个设计是为了 MVCC：读的人不需要等写的人，写的人也不需要等读的人。

**空间要等 VACUUM**：

```
VACUUM t_demo 之后：
lp 10: lp_flags 3 → 0   （死行槽位变成"未使用"，空间可以再分配）
lp 11: lp_flags 1 → 2   （旧版本被清掉，行指针变成指向新版本的重定向）
```

VACUUM 之后行指针 10 的 flags 从 3 变成 0，这块空间才能被后续 INSERT 复用（本次演示里，脚本随后插入的 id=100 就正好落在了第 0 页第 10 槽）。

所以"删了这么多数据为什么磁盘不降"的答案：**文件只会变大不会变小**。要真的缩小得 `VACUUM FULL`（重写整表，代价大）或者 `pg_repack`。

## 6. 往下两层、往上一层

- **往下：文件系统**。数据文件在 OS 眼里是一串 4KB 块；数据库的 8KB 页横跨两个文件系统块。OS 还有一层页缓存（page cache），所以严格说"从磁盘读"其实是"从 OS 缓存读"或"从设备读"，两次都可能。
- **往下：磁盘硬件**。真正的最小读写单位是扇区（512B 或 4KB）。数据库按 8KB 对齐读写，正是为了不触发"读一个页要打扰多个扇区"的读放大。
- **往上：表空间和段**。一个数据文件最大 1GB，超过就分段；表空间可以指定到不同磁盘，用来把 I/O 分散开。
- **另一个数据库的对比**：

| | PostgreSQL | InnoDB(MySQL) |
| --- | --- | --- |
| 页大小 | 8KB | 16KB |
| 行的存放 | 堆表（heap），行按插入顺序堆在页里 | 聚簇索引，行就在主键 B+ 树的叶子页里 |
| 索引项 | (key, ctid) —— ctid 是物理地址 | (key, 主键)—— 回表再用主键查一次 |
| 页内指针 | 行指针数组（4 字节/项） | 页目录（slot 数组）+ 记录链表 |

## 9. 常见误解

| 误解 | 实际 |
| --- | --- |
| 数据"一行一行"存在磁盘上，读一行就一次 I/O | 按 8KB 页整块读写，一页装几十条 |
| 提交成功 = 数据已经写进数据文件 | 提交只保证 WAL 落盘；数据页可能还在内存 |
| DELETE 之后磁盘空间就释放了 | 只在行上写 `t_xmax`，空间要 VACUUM 才可复用，文件不会变小 |
| UPDATE 是原地修改那一行 | 写新版本 + 旧版本链，ctid 会变 |
| 索引里存的是整行 | 存的是 (key, 物理地址 ctid)，命中后再按 ctid 取页 |
| 数据库页大小可以随便改 | 编译期定死（PG 8KB/16KB/32KB 变体），一页必须能被文件系统块整除 |

## 10. 一句话总结

**写**：找到有空位的页 → 在内存里的页上追加元组和行指针 → 先把 WAL 顺序写盘 → 脏页等检查点再整块写回数据文件。
**读**：索引（或顺序扫描）给出页号和槽号 → 查缓冲池，没命中就读 8KB 整页进来 → 页内按行指针的偏移/长度切出元组 → 按可见性挑出该返回的那个版本。
