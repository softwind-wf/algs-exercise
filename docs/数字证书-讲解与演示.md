## 1. 一句话先说清：证书是什么

```text
证书 = 一段被 CA 私钥签过名的结构化数据
     = 身份（subject）+ 公钥（SPKI）+ 用途（extensions）+ 有效期（validity）
       + 签发者（issuer）+ 序列号（serialNumber）
       + CA 对上面这些字节的签名（signatureValue）
```

用大白话说：**证书是 CA 给"这把公钥属于这个身份"开的一张盖章证明。**

生活里最接近的东西不是身份证，而是**盖章的介绍信**：信上写着"持信人张三，是我单位员工，这是他本人"，盖着单位公章。收信方不认识张三，但认这个公章——信任从"我不认识你"转移到了"我认识盖章的人"。证书完全一样：浏览器不认识 `example.com` 的运维，但认识签发它的 CA。

但要注意一个关键差别：**介绍信上的字谁都能照着抄，公章抄不了。** 证书里 `issuer` 那一行文字不是保证，CA 的签名才是。第 2 段会用一个伪造例子把这点做实。

证书回答的问题，和签名回答的问题，是两件事：

| 问题 | 谁来回答 | 在哪一篇 |
|---|---|---|
| 这段内容有没有被改？是不是某把私钥签的？ | 数字签名 | 上一篇 |
| 这把公钥属于谁？ | 证书（CA 背书） | 这一篇 |

所以本文反复出现的一句话是：**证书解决的是"公钥属于谁"，不是"内容有没有被改"。** 后者签名已经做完了，做不了的是前者。还要记住一句：**证书自己也是一段被签名的数据。** 它享受签名带来的一切保护——改一个字节就验不过（第 4 段实测），但它不因此变得更"真"：它只是把"该信谁"的问题，从站点转移到了 CA 身上。

| 证书能保证 | 证书不能保证 |
|---|---|
| 公钥与 subject 的绑定关系（在有效期内、用途范围内） | 持私钥的人或组织靠谱 |
| 这张证书本身没被改过（CA 签名） | 服务器现在没被入侵、网站内容安全 |
| 有效期、用途、可签发的层级 | 私钥没泄露（泄露了要靠吊销，见第 5 节） |

## 2. 为什么签名还不够：一次公钥替换

先看第 1 段的真实输出。场景很朴素：Bob 要证明"这条转账指令是我发的"，Alice 需要 Bob 的公钥才能验签；而公钥要么随消息一起传，要么去某个地方下载——**这条路上的任何一跳都能把公钥换掉。**

```text
Mallory 截获了 Bob 发布的公钥，换成自己的公钥，再用自己的私钥签一条指令。
  [通过] 用真正的 Bob 公钥验 Mallory 的签名 -> 拒绝（签名算法工作正常）
  [通过] 用"被换进来的那把公钥"验签 -> 通过（Alice 以为这是 Bob 的公钥）
```

把这两行翻成三句话：第一行说明**算法没问题**，拿真 Bob 的公钥去验 Mallory 的签名会正确拒绝；第二行说明**问题不在算法**，Alice 手上那把公钥已经被换成 Mallory 的，于是"Mallory 签的"在她眼里就是"Bob 签的"；两行合起来——**签名证明"持有某私钥的人发的、内容没被改"，但它回答不了"这把公钥属于谁"。**

这不是密码学被攻破，而是分发渠道被攻破。现实里对应的就是：DNS 被污染后给你一个假公钥、公司代理换掉下载的公钥、聊天软件里别人发来的"我的公钥"。

CA 的做法在第 1 段后半段跑了一遍：把"身份 + 公钥"写成结构化数据，用 CA 自己的私钥签名，客户端只用一把**事先就信任的** CA 公钥去验。

```text
CA 的做法：把"身份 + 公钥"写成一段结构化数据，用 CA 自己的私钥签个名。
  Bob 的证书 subject = CN=Bob 的签名密钥,O=Alg4 Demo,C=CN
  [通过] 用事先装好的 CA 公钥验证书 -> 通过：CA 担保这把公钥属于 Bob
  [通过] Mallory 自己签一张写着 CA 名字的证书 -> 用 CA 公钥验签被拒绝
         实际抛出 SignatureException: Signature does not match.
```

第三行最值得看：Mallory 把 `issuer` 一字不差地写成 `Alg4 Demo Root CA`，但那张证书的签名是用 Mallory 自己的私钥做的，CA 公钥验不过，JDK 直接抛 `SignatureException: Signature does not match.`。**文字可以随便写，签名不能。**

注意 CA 只是把问题**上移了一层**，没有消灭它：现在你要可信地拿到"CA 的公钥"。这个链条的终点，就是预装在系统/浏览器/JDK 里的根证书（第 6 节）。公钥分发只有三条路：

| 方式 | 怎么建立信任 | 代价 |
|---|---|---|
| CA 证书链 | 预置根证书 → 逐级签名验证 | 要信任一百多个 CA 组织（第 6 节的 110 张） |
| 预置指纹 / pinning | 把公钥或证书哈希写死在客户端 | 换证书就得发版 |
| 证书透明日志（CT） | 公开审计"谁给谁签过证书" | 只能发现问题，不能阻止 |

一句话：**签名保证"没被掉包"，证书保证"掉包了你能发现"。** 少了后半句，前半句再强也没用。

## 3. 证书长什么样：三段结构，加一层 TLV

第 2 段先用 `Der` 类手工拼了一张证书（不调 keytool、不引第三方库），再交给 `CertificateFactory` 解析。它先打印结构：

```text
Certificate ::= SEQUENCE {
    tbsCertificate      -- 待签名数据：版本、序列号、签发者、有效期、主体、公钥、扩展
    signatureAlgorithm  -- 用什么算法签的（必须与 tbs 里那个字段一致）
    signatureValue      -- 对 tbsCertificate 整个字节串的签名
}
```

`tbs` 就是 "to be signed"。**签名只盖中间那段正文**，外层两个字段不参与签名——`signatureValue` 当然不能签自己；`signatureAlgorithm` 靠"必须与 tbs 内部那份算法标识一致"来防替换。

本次手拼的 tbs 是 637 字节，其中真正的内容 633 字节（`30 82 02 79` 这 4 个字节是头）：

```text
tbsCertificate 共 637 字节，开头 32 字节：30820279a00302010202080dc0214d77f87be4300d06092a864886f70d01010b ...
```

### 3.1 先懂 TLV：标签 + 长度 + 值

ASN.1 是"数据长什么样"的语法，DER 是"怎么把它写成唯一一段字节"的规则。每个节点都是 TLV：

| 部分 | 例子 | 读法 |
|---|---|---|
| 标签 Tag | `30`、`02`、`A0`、`A3`、`82` | 1 字节。`0x20` 位表示"里面还有子 TLV"（constructed）；高两位 `00` 是通用类型，`10` 是上下文相关 |
| 长度 Length | `0d`、`81 85`、`82 02 79` | 最高位为 0：短格式，就是长度本身；最高位为 1：长格式，低 7 位是"后面还有几个字节表示长度" |
| 值 Value | 内容或子 TLV 串 | 定长，长度由上一段给出 |

`30 82 02 79` 读作：SEQUENCE，长度用 2 字节表示，值 `0x0279 = 633`。所以整段是 `4 + 633 = 637` 字节——和输出里的两个数字对得上。

DER 在 TLV 之上又加了几条"只允许一种写法"的规矩，本次演示里全都用到了：

| 规则 | 为什么 | 本次出现的地方 |
|---|---|---|
| 长度必须用最短形式 | 同一内容不能有两种编码 | `0d` 而不是 `81 0d` |
| INTEGER 用最短补码，正数最高位为 1 时补 `0x00` | 否则会被读成负数 | 序列号首字节 `0x0d` 最高位 0，不用补；换成 `0xF0…` 就必须补 |
| BIT STRING 第一个内容字节是"未用位数" | 位串不一定凑满整字节 | `03 82 01 0f` 后面跟 `00`，表示 0 个未用位 |
| BOOLEAN 的 TRUE 必须是 `0xFF` | 不允许 `0x01` 之类 | `0101 FF`（critical 标记） |
| SET OF 内部按编码字节排序 | 集合不能有两种顺序 | 每个 RDN 一个 SET，只有一个元素时看不出差别 |
| 不许不定长 | BER 的 `80 … 00 00` 在 DER 里非法 | 本演示全部定长 |

### 3.2 把 tbs 逐行拆开

下面是从第 2 段输出里摘的关键片段，`//` 后面是注释（原输出没有注释）：

```text
30820279     SEQUENCE (633 字节)              // 整个 tbsCertificate；30=SEQUENCE，82=长度占 2 字节，0279=633
  a003         [0] (3 字节)                    // A0 = context [0] constructed：version 外面又包了一层
    0201         INTEGER = 2                   // 值 2 表示 v3；v1 时整个 [0] 省略，默认就是 1
  0208         INTEGER = 990828534630480868    // serialNumber：8 字节，首字节 0x0d 最高位为 0，不用补 0x00
  300d         SEQUENCE (13 字节)              // signature：AlgorithmIdentifier
    0609         OID = 1.2.840.113549.1.1.11（sha256WithRSAEncryption）
    0500         NULL = (空)                   // RSA 系算法标识后面习惯跟一个 NULL 参数
  303d         SEQUENCE (61 字节)              // issuer：一个 Name（X.500 目录名）
    310b         SET (11 字节)                  // 一个 RDN 用 SET OF 包住
      3009         SEQUENCE (9 字节)            // RDN 里是"属性类型 + 值"
        0603         OID = 2.5.4.6（C 国家）
        1302         PrintableString = "CN"     // 13 = PrintableString；UTF8String 是 0C
    3112         SET (18 字节)
      3010         SEQUENCE (16 字节)
        0603         OID = 2.5.4.10（O 组织）
        0c09         UTF8String = "Alg4 Demo"
    311a         SET (26 字节)                  // 第三条 RDN：CN=Alg4 Demo Root CA，内部结构同上

    170d         UTCTime = "261101063116Z"     // 17=UTCTime，0d=13 字节，"YYMMDDHHMMSSZ"
    170d         UTCTime = "271101073116Z"     // 即 2026-11-01 06:31:16 UTC ~ 2027-11-01 07:31:16 UTC
  304c         SEQUENCE (76 字节)              // subject：结构同 issuer，四条 RDN（C/O/OU/CN），此处不展开
  30820122     SEQUENCE (290 字节)             // subjectPublicKeyInfo
    300d         SEQUENCE (13 字节)            // 算法：rsaEncryption
      0609         OID = 1.2.840.113549.1.1.1（rsaEncryption）
      0500         NULL = (空)
    0382010f     BIT STRING = 未用位 0，位串 3082010a0282010100d4bd3d…（共 270 字节）
                                                // 03=BIT STRING；内容 271 字节 = 1 个"未用位数" + 270 字节位串
  a38185       [3] (133 字节)                  // A3 = context [3] constructed：extensions 被包了一层
    308182       SEQUENCE (130 字节)           // 一串 Extension
      300c         SEQUENCE (12 字节)
        0603         OID = 2.5.29.19（basicConstraints 基本约束）
        0101         BOOLEAN = TRUE            // critical = true
        0402         OCTET STRING = 3000       // 内容是空 SEQUENCE{}，即 CA:false
      300e         SEQUENCE (14 字节)
        0603         OID = 2.5.29.15（keyUsage 密钥用途）
        0101         BOOLEAN = TRUE            // critical = true
        0404         OCTET STRING = 03020780   // BIT STRING：未用位 7，0x80 = digitalSignature
      302e         SEQUENCE (46 字节)
        0603         OID = 2.5.29.17（subjectAltName 主体备用名）
        0427         OCTET STRING = 302582127365727665722e65…（共 39 字节）
                                               // 30 25 是 SEQUENCE 头（37 字节内容），里面两个 82 12 "…"（[2] dNSName）
      3013         SEQUENCE (19 字节)
        0603         OID = 2.5.29.37（extKeyUsage 扩展密钥用途）
        040c         OCTET STRING = 300a06082b06010505070301
                                               // 30 0a | 06 08 2b 06 01 05 05 07 03 01 = serverAuth（1.3.6.1.5.5.7.3.1）
      301d         SEQUENCE (29 字节)
        0603         OID = 2.5.29.14（subjectKeyIdentifier 主体密钥标识）
        0416         OCTET STRING = 04145c360c4e59060a400316…（共 22 字节）
                                               // 22 = 04 14 两字节头 + 20 字节 SHA-1(公钥位串)
```

几个"看懂就够"的要点：

- **方括号标签有两种**：`A0`/`A3` 这种 constructed 的叫**显式标签**，作用只是"再包一层"（version、extensions 都是可选字段，包一层好写"有没有"）；SAN 里 `82 12` 的 `82` 是**隐式标签**，直接把 `PrintableString` 换成了 `[2] dNSName`，所以内容就是域名原文，没有额外类型头。
- **`1302 "CN"` 与 `0c09 "Alg4 Demo"`**：同样是字符串，国家用 `PrintableString`（`13`），组织名用 `UTF8String`（`0C`）。这不是随便挑的，RFC 5280 对每个属性规定了可选类型。
- **`SET` 与 `SEQUENCE` 的区别**：`SEQUENCE` 有序，`SET` 无序（DER 要求按编码排序）。DN 之所以写成 `SET OF AttributeTypeAndValue`，是因为同一属性可以出现多次（比如两个 OU）。

### 3.3 手拼的字节，JDK 认不认

```text
CertificateFactory 解析结果：X.509，版本 v3，签名算法 SHA256withRSA
  [通过] 手拼的字节被 JDK 当成合法的 v3 证书
  [通过] subject 解析回 CN=server.example.com
  [通过] 用 CA 公钥验签通过：签名覆盖的正是 tbsCertificate 那一整段字节
  [通过] 证书重新编码后与手拼的字节逐字节相同 -> 我们造的就是标准 X.509
```

最后一条最能说明问题：JDK 把证书**重新编码**一遍，如果和我们手拼的字节完全相同，就证明我们的编码是 DER 的规范形式（同一内容只有一种写法）。如果长度用了非最短形式、SET 顺序乱排，重新编码就会对不上——这也是为什么"证书格式"看起来啰嗦，实际上是为了让全世界算出**同一串字节**，否则签名没法验。

所以"证书"没有魔法：它就是一段按 ASN.1 排好版、被 CA 私钥用 SHA256withRSA 签过的字节。X.509 只是大家约好的字段排布。

## 4. 字段逐个讲：每个字段各防什么

第 3 段把一张终端证书的字段打印成一张表。下面补上"它防什么"这一列的重点：

| 字段 | 本次实测值 | 它防什么 |
|---|---|---|
| `version` | v3 | 扩展只有 v3 能带；v1/v2 证书没有 SAN、没有 basicConstraints，现代校验器直接不认 |
| `serialNumber` | `0x641ec35f9a341714` | 证书的唯一编号。吊销时按它指名（CRL/OCSP 都靠它），所以必须唯一且不可预测 |
| `signature`（tbs 内） | SHA256withRSA | 声明签发算法。改它会让验签失败，且必须与外层 `signatureAlgorithm` 一致 |
| `issuer` | `CN=Alg4 Demo Root CA,O=Alg4 Demo,C=CN` | 谁签的。验签时靠它去找上一级公钥——**但它只是文字**，见下 |
| `validity` | 2026-11-01 06:31:16 UTC ~ 2027-11-01 07:31:16 UTC | 过期/未生效一律拒绝；也防"提前签一张十年后的证书" |
| `subject` | `CN=server.example.com,OU=Web,O=Alg4 D…` | 证书给谁。TLS 里还要和你要连的主机名核对（第 7 节） |
| `subjectPublicKeyInfo` | RSA 2048 位 | 被绑定的公钥本体——整张证书存在的理由就是为了它 |
| `signatureValue` | 256 字节 | CA 私钥对 tbs 全部字节的签名；RSA-2048 的签名长度固定 256 字节 |
| `extensions` | 见下表 | 约束"这张证书能干什么" |

扩展是证书里最容易出事、也最值得看的部分：

| 扩展 | 本次取值 | 它防什么 | 关键扩展 |
|---|---|---|---|
| `basicConstraints` | CA=false（DER 里写成空 SEQUENCE `3000`） | 防止终端证书被拿去当 CA 签发下一级（第 6 段实测拒绝） | 是 |
| `keyUsage` | `digitalSignature`（`03020780`） | 限定这把钥匙只能做签名，不能签证书、不能加密 | 是 |
| `subjectAltName` | `DNS:server.example.com, DNS:www.example.com` | 证书真正覆盖哪些域名/IP，主机名校验只看它 | 否（但事实上决定生死） |
| `extKeyUsage` | serverAuth（`1.3.6.1.5.5.7.3.1`） | 限定用途是 TLS 服务器，防止"给代码签名用的证书拿来当网站证书" | 否 |
| `subjectKeyIdentifier` | SHA-1(公钥位串)，20 字节 | 让上下级证书快速对上"是哪把钥匙"（配合 AKI），链拼接时少走弯路 | 否 |

`basicConstraints` 写成空 SEQUENCE 而不是 `BOOLEAN FALSE`，是 DER 的规矩：`CA` 的默认值就是 false，**默认值必须省略**。这一点在手写 DER 时很容易错（`CertificateDemo` 的 `basicConstraints()` 方法里专门有一行注释说明）。

### 4.1 issuer 和 subject 只是文字

这是全篇最容易被忽略的一句：`issuer` 和 `subject` 都是"目录名"（DN），格式是 `C=..,O=..,CN=..`，**谁都可以写成任何样子，写 `CN=Bank of China` 不花一分钱**。

它们的可信度完全来自"谁签的"。第 1 段那个伪造例子里，`issuer` 和真证书一模一样，唯一的不同是签名用的私钥——`SignatureException: Signature does not match.` 就是全部答案。

所以读证书的标准姿势是：**先看签名能不能验到一张你信的根上，再看字段。** 反过来（先看 `subject` 写着 `CN=某银行` 就信）就是钓鱼证书能得手的原因。

### 4.2 签名到底盖住了哪些字节

第 4 段做了四种篡改，全部被拒：

```text
  [通过] 把 subject 改成 evil.example.com，签名不动 -> 验签拒绝
         实际抛出 SignatureException: Signature does not match.
  [通过] 把公钥换成攻击者的公钥，签名不动 -> 验签拒绝（公钥被签名保护）
         实际抛出 SignatureException: Signature does not match.
  [通过] 用另一把 CA 私钥签同一段 tbs -> 用真 CA 公钥验签拒绝
         实际抛出 SignatureException: Signature does not match.
  [通过] 只翻转 tbs 最后一个字节的 1 个 bit -> 验签拒绝
         实际抛出 SignatureException: Signature does not match.
  [通过] 对照组：原始证书验签通过
```

| 攻击者想做的 | 结果 | 为什么 |
|---|---|---|
| 把 subject 改成别的域名 | 拒绝 | 签名覆盖 tbs 的**全部字节**，subject 也在里面 |
| 把公钥换成自己的 | 拒绝 | 公钥在 SPKI 里，同样是 tbs 的一部分 |
| 用别的私钥重新签 | 拒绝 | 验签用的是 CA 公钥，不是"任意能签的钥匙" |
| 改 1 个 bit | 拒绝 | 任何字节变化都会改变摘要 |
| **找一张受信任的 CA 签** | 可能成功 | 这就是第 6、8 段要防的：不是改证书，而是"合法地"拿到一张 |

最后一行是重点：**密码学挡住了"改"，挡不住"骗"。** 攻击者改不了你的证书，但他可以去申请一张看起来像你的证书，或者让客户端信任他自己的根。

## 5. 证书怎么被验证：六道检查，外加吊销

第 9 段把验证流程总结成六道检查，加第七道吊销：

| # | 检查 | 查什么 | 本次实测的失败表现 |
|---|---|---|---|
| 1 | 签名 | 用 issuer 的公钥验 tbs 的签名 | 第 4 段：`SignatureException: Signature does not match.` |
| 2 | 链 / 签发者 | issuer 的证书可不可信？一路递归到信任锚 | 第 3 段：`Path does not chain with any of the trust anchors`；TLS 场景 4：`unable to find valid certification path…` |
| 3 | 有效期 | notBefore ≤ 现在 ≤ notAfter | 第 5 段：`CertificateExpiredException`；TLS 场景 3：`validity check failed` |
| 4 | CA 资格 | 链上除叶子外必须 CA:true + keyCertSign，pathLen 不越界 | 第 6 段：`CA key usage check failed: keyCertSign bit is not set` |
| 5 | 用途 | keyUsage / EKU 允许这次用途（如 serverAuth） | 本次证书带 `EKU=serverAuth`；未单独跑失败场景 |
| 6 | 主机名 | SAN 里有没有你要连的名字/IP | 第 7 段 7 条匹配实验；TLS 场景 2：`No subject alternative DNS name matching localhost found.` |
| 7 | 吊销 | CRL / OCSP：没过期但私钥泄露了，要能立刻失效 | 演示离线，`setRevocationEnabled(false)` 显式关掉，未跑 |

### 5.1 签名通过 ≠ 信任通过

第 2 段的逐级验签，把"逐环"这件事演示得很清楚：

```text
  [通过] server 证书 -> 用 intermediate 公钥验签通过
  [通过] intermediate 证书 -> 用 root 公钥验签通过
  [通过] root 证书 -> 用自己的公钥验签通过（自签，自己给自己背书）
  [通过] server 证书 -> 直接用 root 公钥验，拒绝（中间的签名对不上根的公钥）
```

第四行是关键：**跳级验签会失败**。签名验证只回答"是不是这把私钥签的"，它根本不知道什么叫"信任"。要不要信，是"链拼接 + 信任锚 + 一串策略检查"合起来决定的。

### 5.2 同一张证书，换个信任锚结论就反

第 3 段用 PKIX 校验器跑了两遍，只改信任锚：

```text
  [通过] 信任锚 = 我们的 root -> 校验通过
  校验路径：server -> intermediate -> root(锚)
  [通过] 信任锚换个不相干的根 -> 校验失败
  失败原因：CertPathValidatorException: Path does not chain with any of the trust anchors
```

同一条链、同样的签名、同样的有效期，**结论完全相反**。所以"可信"从来不是证书自身的属性，而是"它能不能连到我已经信任的那张根证书上"。这句话解释了后面所有的坑：证书没问题、链没问题，只是客户端不认那个根。

顺带记住两个报错的区别，排障时非常有用：`PKIX path building failed` 是**拼不出路径**（缺中间证书，或根不在信任库）；`PKIX path validation failed: …` 是**拼出来了，但某道检查没过**（比如 `validity check failed`）。

### 5.3 CA 资格：普通证书不能当 CA 用

第 6 段构造了一条攻击链：拿一张普通证书（`CA:false`）的私钥去签"Bob 的证书"，再把它当中间 CA 拼进链里。

```text
正常链：root（CA:true） -> intermediate（CA:true, pathLen=0） -> server.example.com
  [通过] PKIX 校验通过：链走到预置的根，且每一级都是合格的 CA

攻击链：普通证书（CA:false）用它的私钥去签一张"Bob 的证书"，再把它当中间 CA 拼进链里。
  [通过] PKIX 校验 -> 拒绝（普通证书不是 CA，不能签发下一级）
  被拒原因：CertPathValidatorException: CA key usage check failed: keyCertSign bit is not set
```

这就是 `basicConstraints` 与 `keyUsage` 必须是**关键扩展**的原因：`CA:true + pathLen:0` 表示"我能签证书，但只能签终端证书"；`keyCertSign` 表示"只允许做签发这一件事"。两者缺一，校验器就不让你当中间 CA。**攻击者只能去偷 CA 的私钥，不能自己声明自己是 CA。**

## 6. 证书链与信任锚

### 6.1 三层，一层比一层短命

脚本用 keytool 生成了三张证书，第 1 段把它们打印出来：

| 角色 | subject | issuer | 有效期（UTC） | CA / pathLen |
|---|---|---|---|---|
| root | `CN=Alg4 Demo Root CA,O=Alg4 Demo,C=CN` | 同 subject（自签） | 2026-11-01 07:30:56 ~ 2036-10-29 07:30:56 | true / 无限制 |
| intermediate | `CN=Alg4 Demo Intermediate CA,…` | `CN=Alg4 Demo Root CA,…` | 2026-11-01 07:30:58 ~ 2031-10-31 07:30:58 | true / 0 |
| server | `CN=localhost,O=Alg4 Demo,OU=Web,C=CN` | `CN=Alg4 Demo Intermediate CA,…` | 2026-11-01 07:31:02 ~ 2029-02-03 07:31:02 | false / — |

```text
  [通过] server 的 issuer == intermediate 的 subject
  [通过] intermediate 的 issuer == root 的 subject
  [通过] root 自签：issuer == subject
  [通过] intermediate 是 CA (=true)，且 pathLen=0（只能签终端证书，不能再签 CA）
  [通过] server 是终端证书（CA:false）
  [通过] 根的到期时间不早于中间 CA（根活得最久）
```

第一行的等式就是"能拼成链"的全部原因：**上一层的 issuer 等于下一层的 subject**。有效期也是刻意设计的——根 10 年、中间 5 年、站点 2 年多；根活得最久，换根最贵。

### 6.2 为什么要有中间 CA

"根直接签站点"在技术上完全可行，但工程上不行，原因有三条：

1. **根私钥必须离线**。根只在签中间 CA 时用一次，平时锁在离线机器或 HSM 里；日常签发全用中间 CA 的私钥，中间 CA 的机器可以联网。
2. **可以按用途/地区轮换**。不同业务线、不同地区各用一支中间 CA，出问题只影响一支。
3. **泄露可吊销**。中间 CA 泄露，吊销它一条记录就能让整支失效，根不动；根一旦要换，全世界所有客户端都得更新信任库，那是以年计的工程。

`pathLen=0` 是这套设计的刹车：这支中间 CA **只能签终端证书，不能再签下一级 CA**，防止它无限扩张出一个子树。

PKIX（Public Key Infrastructure X.509，RFC 5280 那套路径校验算法）把验证分成两个阶段：**建路径**（path building，从叶子往上找 issuer，直到某张信任锚）和**验路径**（path validation，逐条跑签名、有效期、CA 资格、用途、策略）。前面那两个报错 `path building failed` / `path validation failed`，正好对应这两个阶段。

### 6.3 默认信任集合：cacerts 里躺着 110 张根

第 8 段打开 JDK 自带的 `cacerts`（口令 `changeit`）看真实数据：

```text
  C:\Program Files\Java\jdk-17\lib\security\cacerts
  共 110 张预置根证书（去重后的信任锚）。前 3 张：
  - actalisauthenticationrootca [jdk]
      subject : CN=Actalis Authentication Root CA,O=Actalis S.p.A./03358520967,L=Milan,C=IT
      有效期  : 2011-09-22 11:22:02 UTC ~ 2030-09-22 11:22:02 UTC，算法 SHA256withRSA
  - addtrustexternalca [jdk]
      subject : CN=AddTrust External CA Root,OU=AddTrust External TTP Network,O=AddTrust AB,C=SE
      有效期  : 2000-05-30 10:48:38 UTC ~ 2020-05-30 10:48:38 UTC，算法 SHA1withRSA
  [通过] JDK 预置的根证书数量 > 50（这就是默认信任集合）
```

三点值得注意：

- **110 是个具体数字，不是"很多"**：这 110 张根证书的私钥，决定了全世界 Java 程序默认信任谁。它们分布在几十个组织手里。
- **"在信任库里"不等于"永远有效"**：上面第二张 AddTrust 根 2020 年就到期了，仍留在库里。信任库记录的是"曾经被认可"，实际校验还要过有效期那一关。
- **三份信任库可能不一样**：JDK 有 `cacerts`，操作系统有一份，浏览器（Chrome/Firefox）各有一份。同一张证书，Java 客户端报错、浏览器却正常，最常见的原因就是两边根库不同。

### 6.4 装根证书 = 把签发权交给别人

第 8 段的结论值得单独抄一遍：

```text
  - 信任是传递的：你信根，根签中间，中间签站点，于是你信站点；
  - 根证书的私钥对应着"签发能力"，所以必须离线保管、多年才轮换一次；
  - 企业做 HTTPS 解密（MITM 代理）时，就是往客户端塞一张自制根证书——
    客户端从此信任它签发的所有站点证书。这也解释了为什么"装根证书"是敏感操作。
```

"信任一张根证书"这句话的准确含义是：**信任这把私钥签发的任何证书，给任何域名。** 所以企业装自建根做 HTTPS 解密（中间人代理）在技术上和攻击者的做法完全一样，区别只在"谁装的、有没有告知"。

| 谁掌握那把根私钥 | 能做什么 |
|---|---|
| 企业 IT | 解密所有员工的 HTTPS 流量，员工端无感知 |
| 恶意软件 / 被入侵的终端 | 给任意域名签"合法"证书，浏览器不报警 |
| 被攻破或被迫配合的 CA | 单点信任：它签的东西全世界都认 |

## 7. 真 TLS 握手实测：5 个场景

### 7.1 怎么测的

第 4 段不是"模拟"校验，而是真的起了一个 TLS 服务器、真的连了一次：

```text
做法：本地起一个 SSLServerSocket（用 keytool 生成的私钥与证书链），
客户端只信任我们的 root，并且打开 HTTPS 式的主机名校验
（SSLParameters.setEndpointIdentificationAlgorithm("HTTPS")）。
失败原因从握手异常的 cause 链里抠出来，连 JDK 自己的原话一起打印。
```

这里有一个 Java 特有的坑，值得单独标出来：**`SSLSocket` 默认只校验证书链，不校验主机名。** 必须显式 `setEndpointIdentificationAlgorithm("HTTPS")` 才会做主机名匹配。忘了这一行，等于自己把第 6 道检查关掉了——很多"Java 客户端被中间人"的事故都是这个原因。

五个场景用同一套客户端代码（只信任我们的 root），换的只是服务器那张证书：

| 场景 | 服务器证书的问题 | JDK 原话（节选） | 对应检查 |
|---|---|---|---|
| 1 | 无（链完整，SAN 有 localhost） | 握手成功 | 六道全过 |
| 2 | SAN 只写了 shop.example.com，却连 localhost | `No subject alternative DNS name matching localhost found.` | 6 主机名 |
| 3 | 证书已过期（2020 年签发、只活 30 天） | `PKIX path validation failed: … validity check failed` | 3 有效期 |
| 4 | 由另一家根 CA 签发，客户端不信任 | `PKIX path building failed: … unable to find valid certification path to requested target` | 2 链 / 信任锚 |
| 5 | 只有 CN=localhost，没有 SAN | 握手成功（JDK 17 仍回退 CN） | 6 主机名（回退路径） |

三条失败的原话连起来看：

```text
场景 2：SSLHandshakeException: No subject alternative DNS name matching localhost found.
        <-  CertificateException: No subject alternative DNS name matching localhost found.
场景 3：SSLHandshakeException: PKIX path validation failed: java.security.cert.CertPathValidatorException: validity check failed
        <-  ValidatorException: PKIX path validation failed: java.security.cert.CertP…
场景 4：SSLHandshakeException: PKIX path building failed: sun.security.provider.certpath.SunCertPathBuilderException:
        unable to find valid certification path to requested target  <-  ValidatorException: PKIX…
```

### 7.2 逐个场景解释

**场景 1（基线）**：链完整、SAN 里有 `localhost`、有效期正常、EKU 是 serverAuth。它证明这套校验不是"一律拒绝"，场景 2~4 的失败不是环境问题。

**场景 2（主机名不匹配）**：证书本身完全合法、链也验得过、也没过期，唯一的问题是**名字对不上**。注意报错是 `No subject alternative DNS name matching localhost found.`——它连"证书里到底写了什么"都不告诉你，只说"没有匹配的名字"。这道检查排在签名/链/有效期之后，所以能走到这一步，说明前面全过了。

**场景 3（过期）**：报错是 `PKIX path validation failed` 而不是 `building failed`，这个区别很关键——**路径拼出来了，是某道检查没过**，具体到 `validity check failed`。看到这句先查两件事：证书的 notBefore/notAfter，以及客户端机器的系统时间（时间错乱会导致所有证书"未生效"或"已过期"）。

**场景 4（别的 CA 签发）**：证书什么都对，就是根不在客户端的信任库里。报错 `unable to find valid certification path to requested target` 是 TLS 排障里出现频率最高的一句，它的意思不是"证书错了"，而是"**我没法把它连到任何一张我信的根上**"。

**场景 5（只有 CN 没有 SAN）**：这是本次唯一"不预设结论、实测"的场景。结果是**握手成功**：

```text
【场景 5】证书只写了 CN=localhost、没有 SAN（不预设结论，实测 JDK 的行为）：
  结果：握手成功 —— JDK 的 HTTPS 校验在 SAN 缺失时仍回退到 CN（RFC 2818 的老规矩）。
  但这不代表可以依赖它：浏览器对公开 CA 的证书只认 SAN，CA/B Forum 2017 年起
  就不再签发"只有 CN"的证书。自己给自己签测试证书时，务必带上 SAN。
```

结论要分两半说：JDK 17.0.12 在 SAN 里没有任何 dNSName 时，**仍会回退去比 CN**（RFC 2818 的老规矩）；但浏览器和公开 CA 早已只认 SAN，RFC 6125 之后新写的校验代码也不该回退。所以"能跑"和"能依赖"是两件事，这个坑第 8 节还会展开。

## 8. 五个常见坑，每个都有本次的实测证据

### 坑 1：UTCTime 的两位年份，2050 写成 1950

第 5 段专门复现了这个陷阱。同一个"2050-12-31 到期"，两种写法两种命运：

```text
想表达"2050-12-31 到期"，按规则用 GeneralizedTime("20501231235959Z")：
  解析回来 notAfter = 2050-12-31 23:59:59 UTC  <- 正确
同一个日期，若有人用两位年份写成 UTCTime("501231235959Z")：
  解析回来 notAfter = 1950-12-31 23:59:59 UTC  <- 变成 1950 年了
  [通过] → 这张证书被判为早已过期（CertificateExpiredException）
         实际抛出 CertificateExpiredException: NotAfter: Mon Jan 01 07:59:59 CST 1951
```

规则来自 RFC 5280：**UTCTime 的 YY≥50 视为 19YY，YY<50 视为 20YY。** 所以 `50` 被读成 1950。注意最后一行显示的是 `1951-01-01 07:59:59 CST`——因为 1950-12-31 23:59:59 UTC 换算到东八区正好跨年，这个"错上加错"的日期很容易让人以为是时区问题，其实是年份问题。怎么避免：2050 年及以后一律 `GeneralizedTime`（四位年份）。用库的时候让它自己选（`CertificateDemo` 里的 `CertSpec.time()` 就是 `year >= 2050` 才用 generalized），不要手写时间字符串。

### 坑 2：通配符只顶一层

第 7 段把 `*.example.com` 的匹配规则跑成了七条断言：

```text
证书 A 的 SAN: DNS:www.example.com
证书 B 的 SAN: DNS:*.example.com
  [通过] A vs www.example.com -> 匹配
  [通过] A vs www.example.com.evil.cn -> 不匹配（后缀不同）
  [通过] A vs example.com -> 不匹配（少了 www 这一层）
  [通过] B vs a.example.com -> 匹配（* 顶一层）
  [通过] B vs a.b.example.com -> 不匹配（* 不能跨层）
  [通过] B vs example.com -> 不匹配（* 必须至少顶一层）
  [通过] B vs evilexample.com -> 不匹配（必须有点号边界）
```

最后一行值得多说一句：`evilexample.com` 不以 `.example.com` 结尾（它结尾是 `example.com` 但前面没有点），所以不匹配。写匹配逻辑时如果只做 `endsWith("example.com")`，就会被 `evilexample.com` 骗过去。另外注意 `*.example.com` 既不匹配 `example.com` 本身，也不跨层匹配 `a.b.example.com`——它只能顶一个标签。

怎么避免：要覆盖 `example.com` 和它下面多层，就逐个写进 SAN，别指望通配符。`*.example.com` 只适合"一层子域随便起名"的场景。

### 坑 3：只有 CN、没有 SAN

第 7 段先按现代规则判了一次，再让 JDK 的 TLS 校验器判了一次，结论相反：

```text
  [通过] 不写 SAN 的证书：getSubjectAlternativeNames() 返回 null
  [通过] 按现代规则，只有 CN 没有 SAN -> 不匹配（CN 只是给人看的）
（JDK 的 TLS 校验在 SAN 里没有 dNSName 时仍会回退去比 CN，
  这是 RFC 2818 的老规矩；浏览器早已不再回退。要兼容老客户端才需要留 CN。）
```

于是就有了场景 5 的"握手成功"。这个坑的麻烦之处在于**它不会报错**：在你自己的 JDK 环境里一切正常，换到浏览器、iOS、Go 的 HTTP 客户端就全挂。

怎么避免：签证书时无条件带 SAN（哪怕只有一个域名）；自己的校验代码不要写"SAN 为空就比 CN"的兜底。

### 坑 4：自签证书为什么会"浏览器报警"

自签证书的签名是**自己给自己签的**，第 2 段实测它是合法的：

```text
  [通过] root 证书 -> 用自己的公钥验签通过（自签，自己给自己背书）
```

从数学上说，这张证书没有任何问题：签名有效、字段齐全、没过期。但从信任上说，**链走到它自己就断了**——它不是任何客户端预置的信任锚。于是浏览器只能给出那个熟悉的警告：证书不受信任。

| | 自签证书 | CA 签发的证书 |
|---|---|---|
| 签名有效性 | 有效（自己的私钥签的） | 有效 |
| 链的终点 | 它自己 | 一张预置根证书 |
| 第三方背书 | 没有 | 有 |
| 客户端结论 | 不受信任（除非手动装进信任库） | 受信任 |

第 3 段那句 `Path does not chain with any of the trust anchors` 就是这件事的另一种说法。同一系列上一篇讲义里，`jarsigner` 对自签 jar 的警告也是同一句 `PKIX path building failed`，还额外加了一句 `The signer's certificate is self-signed.`——工具早就把原因写在脸上了。怎么避免：公开站点用 Let's Encrypt 之类的公开 CA；内网自建 CA 时，必须把根证书通过受控渠道装进客户端（这正是第 6.4 节说的"把签发权交给别人"，要谨慎）。

### 坑 5：中间证书没装全，线上最常见的事故

这是部署层面最高频的故障：**服务器只发了叶子证书，没发中间证书。** 客户端手里有根，但叶子到根之间缺了一环，路径拼不起来，报错和场景 4 一模一样：

```text
PKIX path building failed: sun.security.provider.certpath.SunCertPathBuilderException:
unable to find valid certification path to requested target
```

本次脚本在生成证书时就防了这一手，`Install-Chain` 那段注释写得很直白：

```powershell
# 0.6 把 叶子 + 中间 + 根 拼成链，装回各自的 keystore：
#     KeyManager 只会发送 keystore 里存的链，不装中间证书客户端就拼不出路径。
# 注意：-alias 必须与 keystore 里那把私钥的别名一致，keytool 才会把链装到该私钥条目上；
# 换成一个新别名导入，只会得到一张 trustedCertEntry（没有私钥，链也丢了）。
```

也就是说，"装链"这件事有两个独立的坑：**没装**（链不全）和**装错地方**（装成了 trustedCertEntry，私钥条目上还是只有一张叶子）。用 `keytool -list -v -alias server` 看 `Certificate chain length` 就能分辨：我们的 `server.p12` 里装的是叶子 + 中间 + 根三张。

为什么这个坑特别阴险：

- 浏览器**有时**会顺着证书里的 AIA 扩展去把中间证书下载回来，所以你在浏览器里测是好的；
- JDK、curl、很多移动端 HTTP 库**默认不补链**，一到这些客户端就全线失败；
- 报错还是那句笼统的 `unable to find valid certification path`，看起来像"客户端没装根"，实际是"服务器没发中间"。

怎么排查：`openssl s_client -connect host:443 -showcerts` 看服务器到底发了几张证书；`keytool -printcert -file server.pem` 看叶子证书的 issuer 是不是中间 CA。**服务器应该发"叶子 + 所有中间"，不发根**（根本来就在客户端手里，多发一张只是浪费字节）。

## 10. 一页速查

| 术语 | 一句话 |
|---|---|
| CA | 有资格签发证书的机构；"资格"体现在 `basicConstraints CA:true` + `keyCertSign` |
| 根证书 | 自签、预装在客户端里的信任锚；私钥离线，多年才换一次 |
| 中间证书 | 根签发的"二级 CA"，日常签发用它，泄露可单独吊销 |
| 叶子证书 | 给具体站点/服务的那张，`CA:false`，不能签下一代 |
| 信任锚 | 验证的终点，你"一开始就信"的那张根证书；换锚结论就变 |
| PKIX | RFC 5280 的证书路径校验算法，分建路径 + 验路径两个阶段 |
| SAN | Subject Alternative Name，证书真正覆盖的域名/IP；现代客户端只认它 |
| CN | Common Name，DN 里那个"通用名"；只剩兼容老客户端的作用 |
| DN | Distinguished Name，`C=..,O=..,OU=..,CN=..`；**只是文字**，可信度来自签名 |
| EKU | Extended Key Usage，限定用途（serverAuth / clientAuth / codeSigning） |
| keyUsage | 更粗的用途位串（digitalSignature / keyEncipherment / keyCertSign） |
| pathLen | 还能往下挂几级 CA；`0` 表示只能签终端证书 |
| SKI / AKI | 主体/签发者密钥标识，值为公钥的 SHA-1，用来快速对上是哪把钥匙 |
| CRL / OCSP | 两种吊销查询：下载列表 / 在线问一句"这张还有效吗" |
| CSR | 证书签名请求：把"公钥 + 想要的 subject"交给 CA，等它签回来 |
| PKCS12 / JKS | 两种 keystore 格式；PKCS12 是标准，JKS 是 Java 私有老格式 |
| AIA | 证书里"去哪下载签发者证书"的扩展；浏览器可能用它补链，JDK 默认不补 |

```text
证书   = tbsCertificate（身份 + 公钥 + 用途 + 有效期）+ 算法标识 + CA 签名
生成   = 私钥 → CSR → CA 用中间 CA 私钥签 → 得到叶子证书 → 把 叶子+中间 装进服务器
验证   = 建路径 → 验签名 → 查有效期 → 查 CA 资格 → 查用途 → 查主机名 → 查吊销
可信   = 能不能连到"我已经信任的那张根"，不是证书自身的属性
自签   = 签名有效，但链走到自己就断了（没人背书）
报错   = building failed（拼不出链） vs validation failed（某道检查没过）
```

## 11. 与"数字签名"那份讲义的关系

一句话：**签名解决"这段数据是谁签的、改没改"，证书解决"这把公钥是谁的"；后者是前者的前置条件，不是替代品。**

上一篇把签名拆到"hash + 填充 + 私钥运算"，也演示了公钥替换攻击——但那里只演示了"用攻击者的公钥能验过"，没有回答"怎么防止公钥被换"。这一篇就是那个答案：用一张被 CA 签过名的结构化数据把公钥和身份绑在一起，再用预置的根证书给 CA 背书。两篇合起来，才是一条完整的"从密钥到信任"的链路。
