# 非二元联系集里的箭头：为什么「两个箭头」会有两种解释

教材：《数据库系统概念》原书第 6 版·本科教学版（机械工业出版社）第 7 章 数据库设计与 E-R 模型
· 7.5.5 非二元联系集 · 图 7-13（instructor / student / project 通过 proj_guide 关联）。

配套动手脚本（同一组数据插进三张表，直接看哪些行被拒绝）：

- `src/main/resources/sql/nonbinary_arrows_demo.sql`（PostgreSQL 17）
- `src/main/resources/sql/nonbinary_arrows_demo_mysql.sql`（MySQL 8.0）

---

## 1. 一句话概括

- **箭头 = “至多一个”**（多对一里的“一”方）。
- **一个箭头**：含义唯一，主码 = 非箭头端主码的并集。
- **两个及以上箭头**：同一张图能读成「把箭头端当成**一个整体**」或「把每个箭头端**逐个**看」，两种读法约束不同、结果不同 —— 所以教材规定**一个联系集最多画一个箭头**。
- 两种读法在**只有一个箭头**时重合（只有一个箭头端，“整体”和“逐个”是同一句话）。

---

## 2. 先把箭头定死：图 7-13 的单箭头例子

书上的原话：*假设一个 student 在每个项目上最多只能有一位导师。这种约束可用从 proj_guide 的边指向 instructor 的箭头来表示。*

也就是：

```
student ──┐
project ──┼──< proj_guide >──→ instructor      箭头指向 instructor
instructor ┘
```

**含义**：给定 `(student, project)` 这一个组合，至多对应一位 `instructor`。

**主码**：既然 `(student.ID, project.ID)` 能唯一确定一行，`proj_guide` 的主码就是它 ——
**箭头端（instructor）的主码不进主码**。用 SQL 表达这条约束，就是对 `(sid, pid)` 建唯一约束。

> 为什么 `instructor` 的主码不进主码？因为箭头说的是“多对一”里的“一”：很多 (学生, 项目) 组合可以对应同一位教师（一位教师能带很多学生），所以 `instructor` 在联系集里不唯一。

---

## 3. 再加一个箭头，问题就来了

假设图 7-13 上除了指向 `instructor` 的箭头，再画一个指向 `project` 的箭头（即两个箭头）。此时有两种解释：

### 读法Ⅰ —— 把箭头端当成一个整体

**其余端（这里是 student）的一个组合 → 至多对应箭头端的一个“实体组合”。**

具体到本例：`(instructor, project)` 这个组合最多带一个 `student` ——
“同一个项目上，同一位教师至多带一个学生”。

### 读法Ⅱ —— 把每个箭头端逐个看

**每一个箭头端实体集，都分别被“其余所有实体集”唯一决定。**

具体到本例，它其实是两条约束的合取：

1. `(student, project)` → 至多一个 `instructor`（每个学生在一个项目上至多一位导师）；
2. `(student, instructor)` → 至多一个 `project`（每个学生跟一位导师至多做一个项目）。

于是 `{student, project}` 和 `{student, instructor}` 各是一个候选码。

### 两种读法为什么不是一回事

用同一组事实来看（表：`proj_guide(sid, pid, iid)`）：

| 已有事实 | 读法Ⅰ（唯一键 `(iid,pid)`） | 读法Ⅱ（唯一键 `(sid,pid)` + `(sid,iid)`） |
| --- | --- | --- |
| `(s1,p1,i1)`、`(s1,p2,i2)` | 接受 | 接受 |
| 追加 `(s1,p1,i2)`：学生 s1 在项目 p1 上有两位导师 | **接受**（`(i2,p1)` 不重复） | **拒绝**（`(s1,p1)` 重复） |
| 追加 `(s2,p1,i1)`：导师 i1 在项目 p1 上带两个学生 | **拒绝**（`(i1,p1)` 重复） | **接受**（`(s2,p1)`、`(s2,i1)` 都不重复） |

两张表最终**行数相同**（都是 3 行），但**内容互不包含**：读法Ⅰ那张有 `(s1,p1,i2)` 没有 `(s2,p1,i1)`，
读法Ⅱ那张正好相反。所以同一张“两个箭头”的 E-R 图，真的能设计出两种不同的库。

### 一个箭头时为什么就重合了

只有一个箭头端时，“把箭头端当成一个整体”和“把箭头端逐个看”说的是同一件事 ——
都退化成第 2 节那句话：`(student, project)` → 至多一个 `instructor`。
脚本实测：单箭头表（`UNIQUE(sid,pid)`）与读法Ⅱ表内容完全相同（差异行数 = 0）。

---

## 4. 教材的结论与读这段的坑

- 结论：**一个联系集外最多画一个箭头**；只有一个箭头时两种解释等价。
  教材最后说，第 8 章学函数依赖（8.4 节）后可以用不混淆的方式描述这两种解释。
- 读这段最容易读反的地方：第①条里 `A_{i1}, …, A_{im}` 是**箭头指向**的那些实体集，
  “谁决定谁”和“主码取谁”两半句要连着一起读；判断标准只有一个 ——
  **回到图 7-13 那句原话**：箭头指向谁，就表示“其余参与者的一个组合至多对应它的一个实体”，
  因此**它不进主码**。抓住“整体 vs 逐个”这一对区别，这段就通了，不必纠结下标。

## 5. 动手验证脚本

```bat
rem PostgreSQL
.\psql.bat -f src\main\resources\sql\nonbinary_arrows_demo.sql
rem MySQL（把 <库名> 换成目标库）
.\sql.bat -db <库名> -f src\main\resources\sql\nonbinary_arrows_demo_mysql.sql
```

三张表只差唯一约束，插同一组数据：

| 表 | 唯一约束 | 含义 |
| --- | --- | --- |
| `*_single` | `(sid, pid)` | 单箭头（图 7-13 画法） |
| `*_read1` | `(iid, pid)` | 读法Ⅰ：整体看 |
| `*_read2` | `(sid, pid)` + `(sid, iid)` | 读法Ⅱ：逐个看 |

实测（PostgreSQL 17.11 / MySQL 8.0.44，临时库 `nbdemo_check`，已删）：

| 插入 | 单箭头表 | 读法Ⅰ表 | 读法Ⅱ表 |
| --- | --- | --- | --- |
| `(s1,p1,i1)` | 成功 | 成功 | 成功 |
| `(s1,p2,i2)` | 成功 | 成功 | 成功 |
| `(s1,p1,i2)` | **拒绝**（`(s1,p1)` 重复） | 成功 | **拒绝**（`(s1,p1)` 重复） |
| `(s2,p1,i1)` | 成功 | **拒绝**（`(i1,p1)` 重复） | 成功 |
| 最终 3 行内容 | A1、A2、C | A1、A2、**B** | A1、A2、**C** |

结论：单箭头表 = 读法Ⅱ表（差异 0 行）；读法Ⅰ表 = 读法Ⅱ表 的差异各 1 行、方向相反。

## 6. 自测

**题 1** 图 7-13 中从 proj_guide 指向 instructor 的箭头，在说哪一句约束？`proj_guide` 的主码是什么？
**题 2** 若再加一个指向 project 的箭头，“读法Ⅰ”和“读法Ⅱ”各自允许哪些事实？给出一个只有读法Ⅰ允许的事实和一个只有读法Ⅱ允许的事实。
**题 3** 为什么教材不允许多个箭头？

**答案**
1. 每个 `(student, project)` 组合至多对应一位 `instructor`；主码为 `(student.ID, project.ID)`（箭头端 `instructor` 的主码不进主码）。
2. 读法Ⅰ：`(instructor, project)` 至多对应一个 `student`，如 `(s1,p1,i1)` 与 `(s1,p1,i2)` 并存；读法Ⅱ：`(student,project)`→至多一个 `instructor` 且 `(student,instructor)`→至多一个 `project`，如 `(s1,p1,i1)` 与 `(s2,p1,i1)` 并存 —— 后者恰恰是读法Ⅰ禁止的。
3. 因为两个及以上箭头时，同一张图既能读成“整体”，又能读成“逐个”，两者约束不同、建出的库不同，会造成歧义。
