## 一、逐术语对照

### 1. 函数依赖 `X → Y`
- **教材的话**："关系 R 中任意两个元组，若在 X 上取值相同，则在 Y 上取值也相同。"
- **翻译**："知道 X 就知道了 Y"，本质是一条**业务规则**，不是从数据里统计出来的。
- **怎么判它是否成立**：算左边闭包 `X⁺`，看右边是否都在里面 —— `X → Y 成立 ⟺ Y ⊆ X⁺`；缺口 `Y − X⁺` 非空就说明 Y 里有属性推不出来。`FdCalculator.checkFd` 一次返回闭包、缺口与结论（平凡依赖由自反律必然成立，与 F 无关），演示【五】逐个列出，不必先枚举 F⁺。
- **你自己的例子**：座位号决定舱位 —— 12A 是经济舱、5A 是公务舱。
- **自己验证**（反例查询，0 行才说明成立）：

```sql
SELECT seat_no, count(DISTINCT cabin_class) FROM booking_segment
 WHERE seat_no IS NOT NULL GROUP BY seat_no HAVING count(DISTINCT cabin_class) > 1;
```

### 2. 平凡函数依赖
- **教材的话**："若 Y ⊆ X，则 X → Y 是平凡的。"
- **翻译**：废话型依赖（`{学号, 姓名} → 学号`）。讨论范式时一律忽略，否则什么表都不合格。
- **你自己的例子**：`booking_segment(booking_id, seg_no) → booking_id`。

### 3. 属性闭包 `X⁺`
- **教材的话**："在 F 下由 X 能函数决定的所有属性的集合。"
- **翻译**：一个工具，不是要背的知识点。做法：从 X 出发反复扫 FD，左边被包含就把右边并进来（教材图 8-8，第 193 页）。
- **你自己的例子**：`timetable` 里 `{schedule_id}⁺` = 全部 9 个属性 ⇒ schedule_id 是超键。
- **自己验证**：`.\scripts\run-fd-tests.ps1` 的闭包演示【零】会按图 8-8 逐步打印 `(AG)⁺` 的推导 —— A→B、A→C、CG→H、CG→I 依次生效、第 2 轮无变化终止，得到 ABCGHI；`FdCalculator.attributeClosureTrace` 把"第几轮用了哪条 FD、加进了什么"整份返回。`FdInvariantTest` 里的"口径等价"一条会断言 `X→Y ∈ F⁺ ⟺ Y ⊆ X⁺`。

### 4. 超键 → 5. 候选键 → 6. 主键 → 7. 主属性
- **超键**：能唯一确定一行（可以"过大"）。
- **超键怎么判**：算 `α⁺`，看它是否盖住全部属性 —— `α 是超键 ⟺ α⁺ ⊇ R`。缺口 `R − α⁺` 非空就说明"这几列推不出来"。`FdCalculator.checkSuperkey` 一次返回闭包、缺口与结论，演示【六】逐个列出。注意超键**不要求极小**：`AG` 是超键，`ABG`、`ABCGHI` 也是。
- **候选键**：极小的超键（少一列就不行）。
- **主键**：你从候选键里挑出来那个。
- **主属性**：出现在**任何一条**候选键里的属性（不是"主键里的属性"！）。
- **你自己的例子**（3 行数据就能看清）：

| sno | sname | major |
|---|---|---|
| S1 | 张三 | 计算机 |
| S2 | 李四 | 计算机 |
| S3 | 张三 | 数学 |

`{学号}`：超键 + 候选键（极小）；`{学号, 姓名}`：超键但**不是**候选键（太大）；`{姓名}`：不是超键（张三两人）。
`airline_demo` 的真实例子：`timetable` 有三条候选键（`{schedule_id}`、`{flight_no,day_of_week,valid_from}`、`{flight_no,day_of_week,route_no}`）。

### 8. 部分函数依赖
- **教材的话**："X → Y 且存在 X 的真子集 X' → Y。"
- **翻译**：Y 只依赖复合键的**一半**。单属性主键的表不可能有部分依赖。
- **你自己的例子**：`booking_segment` 的主键是 `(booking_id, seg_no)`，两个属性都只被整键决定，**没有**部分依赖。

### 9. 传递函数依赖
- **教材的话**："X → Y 且 Y → Z，则 X → Z 是传递依赖。"
- **翻译**：绕了一个非键属性才到达 Z。
- **你自己的例子**：`seat_no → cabin_class` 挂在 `booking_segment` 上，就是绕了一层。

### 10. 1NF
- **翻译**：每列都是原子的（不可再分）。
- **你自己的例子**：全部满足。反面例子是"把多个座位号塞进一个字段写成 `'12A,13B'`"。

### 11. 2NF / 12. 3NF / 13. BCNF
三条一起看，因为它们只差一个条件：

| 范式 | 条件 | 你自己的例子 |
|---|---|---|
| 2NF | 1NF + 非主属性完全依赖候选键 | `booking_segment` 满足（主键两列都被整键决定）|
| 3NF | 2NF + 不存在"非键 FD 指向**非主属性**" | 例 1 的 `TNO→CNO` 中 CNO 是主属性 ⇒ 3NF **放行** |
| BCNF | 3NF + **任何**非平凡 FD 的左边都是超键 | `seat_no → cabin_class`：seat_no 不是超键 ⇒ BCNF **拦下** |

- **一句话记法**：3NF 给"右边是主属性"开了后门；BCNF 把后门堵死。
- **怎么判**：未分解时只看 F 就够（逐条非平凡 FD 判左部是否超键，不用枚举 F⁺）；**分解后的子模式不能只看 F**，要把 F⁺ 投影到 Ri 上判，见第 21 条。
- **自己验证**：`com.ds.fd.BcnfCheck`（未分解 / 分解后 / 整个分解三种判定，演示【十】）；`docs/BCNF体检报告-airline_demo.md` 里每个关系的 "结论:" 一行就是判定结果。

### 14. 无损连接分解
- **翻译**：拆完再连接，行数与原来完全相同（不出现伪元组）。
- **二元怎么判**：拆成 R1、R2（R1∪R2=R）时，**无损 ⟺ R1∩R2 → R1 或 R1∩R2 → R2**，即公共属性得是某一侧的超键；用闭包看 `(R1∩R2)⁺` 是否盖住 R1 或 R2。
- **n 元怎么判**：二分定理**不能连用**（无损不传递），要用表格法（chase）：行=子模式、列=属性，子模式含的列填区分变量 `a`、否则填 `b`；反复用 F 里的 FD 让"左部相等的行"右部也相等；若某行变成全 `a`，则无损。
- **自己验证**：`com.ds.fd.LosslessJoin` —— `checkBinary`（公共属性闭包 + 两个方向）与 `checkChase`（表格法，返回最终表格与追踪步骤），演示【八】跑了无损/有损各两例；`LosslessJoinTest` 还在 `fd-cases.txt` 的所有二拆分上交叉验证两条判定路径一致。
- **你自己的例子**：`airline_demo` 里三层设计连接回来 5 行 = 原表 5 行（数据侧"第 4 步"脚本）。

### 15. 保持依赖
- **翻译**：每条原 FD 都能在**某一张子表上**检查出来，不用连接。
- **判据**：分解 D={R1,…,Rn} 保持依赖 ⟺ `(F1 ∪ … ∪ Fn)⁺ = F⁺`，其中 `Fi = F⁺ 在 Ri 上的限定`（只含左右部都落在 Ri 内的依赖）。
- **方法一（图 8-10）**：显式算 F⁺ → 按子模式取限定 Fi → 拼成 F' → 再算 F'⁺ 与 F⁺ 比较。忠实于定义，但 F⁺ 的条数是指数级的，只适合小例子。
- **方法二（修改属性闭包，图 8-11）**：不构造 F'，对 F 中每条 `α→β` 单独算投影闭包 —— `result=α`；重复"对每个 Ri：`t = (result∩Ri)⁺ ∩ Ri`，`result ∪= t`"到不变；`β ⊆ result` 即这条保持，所有依赖都保持才算分解保持依赖。代价是多项式时间（一次 |R| 轮 × n 个子模式 × 闭包）。
- **方法二为什么对**（两个方向）：
  1. **可靠**：取 `γ = result∩Ri`，`t = γ⁺_F ∩ Ri`。因为 γ、t 都在 Ri 内，`γ→t ∈ F⁺` 且左右部都在 Ri，所以 `γ→t ∈ Fi ⊆ F'` —— 每一步加进来的属性都是 F' 能推出的，不会多算。
  2. **完备**：F' 中每条依赖都属于某个 Fi，左右部同在一个 Ri。对"α 到某属性在 F' 下的推导长度"归纳：用到 Fi 里的 FD 时，其左部已包含于 result，取 `result∩Ri` 即可让它在 F 下触发，右部随即被 `t` 收进 result —— 所以 F' 能推出的属性最终都会进来，不会漏算。
  因此不动点时 `result = α⁺_{F'}`，`β ⊆ result` ⟺ `α→β ∈ F'⁺`；又 `F' ⊆ F⁺`，故 `F'⁺=F⁺` ⟺ F 的每条依赖都在 F'⁺ 中（逐条查即得结论）。
- **为什么截断可行**：`γ→(γ⁺_F ∩ Ri)` 恰好就是 Fi 里的那条依赖（左右部都在 Ri、且属于 F⁺），所以在 F 下求一次闭包再截断，等价于在 Fi 下求闭包，却不用把 Fi 物化出来。
- **自己验证**：`com.ds.fd.DependencyPreservation` —— `checkByFPlus`（图 8-10）与 `checkByModifiedClosure`（修改闭包，返回每条 FD 的 result 与结论），演示【九】；测试在 `fd-cases.txt` 所有二拆分上逐对比较两法结论与"丢失集合"是否一致，并各给一个"无损但不保持依赖"和"保持依赖但有损"的例子。
- **你自己的例子**：例 2（员工/部门/项目）拆完 `ENO→PNO` 跨在两张表之间 ⇒ **不保持依赖**（数据侧见 `bcnf_demo_walkthrough.sql` 的例 2 与 `bcnf-audit-raw.txt` 的 "保持依赖" 行）。

### 16. 多值依赖 `X →→ Y` / 17. 4NF
- **翻译**：X 定下来之后，Y 是**一组值**，和表里其余属性互不相干。
- **你自己的例子**：`airline_demo` 里 `flight_no →→ flight_date`（同一班号有多个日期），这属于比 BCNF 更高一层的问题，暂时不用管。

### 18. Armstrong 公理
- **翻译**：三条变形规则（自反/增广/传递），用途是"推导"而不是"背诵"。
- **自己验证**：闭包演示与不变量测试里"候选键之间互相蕴含"的推导，就是用它算的。

### 19. 无关属性 `A` / 20. 正则覆盖 `F_c`
- **无关属性**：从一条 FD 里去掉后，F 能逻辑蕴含的依赖一条不少 —— 这个属性就是多余的。
  - 左部看"少了它还能不能推出右边"：`(α−A)⁺ ⊇ β` ⇒ A 在左部无关；
  - 右部看"拿掉它以后剩余部分能否反推出它"：`F′ = (F−{α→β}) ∪ {α→(β−A)}` 下 `A ∈ α⁺` ⇒ A 在右部无关。
- **正则覆盖 F_c**：与 F 有相同闭包、不含无关属性、左部互不相同的依赖集。它是"验证数据库是否满足 F"时真正该拿来校验的那份，因为最小。
- **自己验证**：`com.ds.fd.CanonicalCover`：`check(fd, F_c)` 返回左/右部无关属性；`compute(F)` 按图 8-9 反复"合并律 + 删一个无关属性"（右部删空则整条删除），返回结果与每一步步骤；演示【七】用教材原例跑通。
- **易错点**：检测必须用**当前的 F_c**，不能用最初的 F（图 8-9 框内的那条注释）。
- **实现约束**（2026-10-17 修复）：①右部为空的依赖恒成立，入口直接丢弃，否则会被逐个删空成 `∅→∅` 垃圾；②合并律按属性**集合**分组，不按拼接字符串 —— 属性名可以是多字符的，`{A, BC}` 与 `{AB, C}` 拼接后都是 `ABC`，拼串做键会把两个不同左部误合并。

### 21. BCNF 判定：未分解 / 分解后（教材 198 页）
- **未分解的 R**：只看**给定的 F** 就够 —— 逐条非平凡 `α→β ∈ F` 算 `α⁺`，只要有一条不包含 R（α 不是超键）就判不属于 BCNF，不用枚举 F⁺。定理：F 中没有违反项 ⇒ F⁺ 中也没有。
- **定理为什么成立**（补一条推导）：设 F 无违反项。任取 α，若 `α⁺ ≠ α`，图 8-8 的闭包算法必在某一步用了某条 `X→Y`（`X ⊆ 当时的 result ⊆ α⁺`）；X 是超键 ⇒ `X⁺ = R`；又 `α⁺ ⊇ X`，闭包单调 ⇒ `(α⁺)⁺ ⊇ X⁺ = R`；闭包幂等 ⇒ `α⁺ = R`。所以任何 α 的闭包只能是 α 或 R，F⁺ 里的非平凡依赖若左部不是超键就自相矛盾。
- **分解后只看 F 就错**：教材反例 `R(A,B,C,D,E)`、`F={A→B, BC→D}` 拆成 `R1(A,B)` 与 `R2(A,C,D,E)`。F 中**没有一条**依赖的左右部都落在 R2 内（`A→B` 的 B、`BC→D` 的 B 都不在），按 F 判会误以为 R2 属于 BCNF；但 F⁺ 里有 `AC→D`（`A→B` 增广成 `AC→BC`，再与 `BC→D` 传递 = 伪传递律），`AC⁺ = ABCD` 缺 E，AC 不是 R2 的超键 ⇒ R2 不属于 BCNF。
- **分解后的判定（教材给的方法）**：对 Ri 的每个属性子集 α，算 `α⁺`（仍用原 F），要求二者至少一个成立：
  1. `α⁺ ⊇ Ri`（α 是 Ri 的超键）；
  2. `α⁺ ∩ (Ri − α) = ∅`（α 推不出 Ri 内的任何新属性）。
  都违反时，见证依赖 `α → (α⁺−α) ∩ Ri` 属于 F⁺；它可能不在 F 中 —— 这正是只看 F 会漏判的原因。
- **为什么对（两个方向）**：① 报出来的都是真违反：`β=(α⁺−α)∩Ri` 非空、`β ⊆ Ri−α`、`α→β ∈ F⁺`、α 不是 Ri 的超键；② 真违反都会被报出：若 `α'→β' ∈ Π_Ri(F⁺)` 非平凡且 α' 不是 Ri 的超键，取 `α = α'`，则 `β' ⊆ (α⁺−α)∩Ri` 且 `α⁺` 不含 Ri 全部属性，条件被违反。
- **复杂度**：枚举 `2^|Ri|` 个子集，每个算一次闭包；比物化 F⁺（指数条数）便宜，但仍是子集枚举。
- **自己验证**：`com.ds.fd.BcnfCheck` —— `checkRelation`（未分解，只看 F）/ `checkRelationByFPlus`（物化 F⁺ 对照）/ `checkProjected`（子集闭包法）/ `checkProjectedByFPlus`（物化 `Π_Ri(F⁺)` 对照）/ `checkDecomposition`（整个分解）；演示【十】跑教材反例与"3NF 但非 BCNF"的经典形状，测试在 `fd-cases.txt` 的所有用例、所有二拆分上交叉验证两条路线结论一致。

### 22. BCNF 分解算法（图 8-11）
- **算法**：`result = {R}`；重复：若 result 中存在 Ri 不属于 BCNF，取一条在 Ri 上成立、非平凡、`α→Ri ∉ F⁺`（α 不是 Ri 的超键）、且 `α∩β = ∅` 的依赖 α→β，做 `result := (result − Ri) ∪ (Ri − β) ∪ (α, β)`；直到所有模式都属于 BCNF。
- **为什么必须 α∩β=∅**：拆分后两块是 `(Ri−β)` 与 `(αβ)`，它们的公共属性是 `(Ri−β) ∩ (αβ) = α − β`。只有 α∩β=∅ 时公共属性才等于 α；而 α→β（连同自反律 α→α）保证 α 是 `(αβ)` 的超键，二元无损定理"公共属性决定某一侧"于是成立。若交集非空，α∩β 中的属性被 β 带走、不再出现在 Ri−β 里，α 不完整，无损性就没有保证。
- **一定无损**：每一步的公共属性 α 决定右侧 `αβ` ⇒ 每步都是二元无损分解；无损的复合仍然无损（最终结果可用 chase 复核）。
- **可能丢依赖**：BCNF 分解不保证保持依赖 —— `R(A,B,C)`、`F={AB→C, C→A}` 拆成 `(A,C)+(B,C)` 后 `AB→C` 跨两张表丢失（分解仍无损）。需要时用 `DependencyPreservation` 另判。
- **不唯一**：伪代码只说"令 α→β 为一个"，没规定选哪条违反依赖；不同选择会拆出不同的合法 BCNF 分解（教材 8.3.2 的 inst_dept 是按 `dept_name→building,budget` 选的）。
- **代价与"过度规范化"**：教材指出该算法所需时间对原始模式规模是**指数级**的（判断一个 Ri 是否 BCNF 的代价可达指数级），而且可能把 Schema 拆得比必要更碎；文献中有多项式时间的 BCNF 分解算法。
- **自己验证**：`com.ds.fd.BcnfDecomposition` —— `decompose`（闭包版，不物化 F⁺，判断 `α→β ∈ F⁺ ⟺ β ⊆ α⁺`）、`decomposeByFPlus`（照伪代码先算 F⁺ 的字面版，只适合小例子）、`Result` 自动复核 `bcnf()` / `lossless()` / `preservesDependencies()`、`Step` 记录每步违反项与拆分结果；演示【十一】跑教材 class 例子（3 张表、保持依赖）与"无损但丢依赖"的 `(A,C)+(B,C)`；测试在 fd-cases 全部用例上验证 BCNF + 无损 + 每步 α∩β=∅、两块都是真子集、并集仍为 Ri。
- **数据库实战**：`src/main/resources/sql/bcnf_class_wide.sql` 在库 `bcnf_class_demo` 里建宽表 `class_wide`（11 属性 / 11 行）走完"判定 → 分解 → 迁移 → 无损验证 → 异常对比"，逐步说明见 `docs/BCNF实战-class_wide-从判定到分解.md`，原始输出 `docs/bcnf-class-raw.txt`。

### 23. 3NF 合成：保持依赖 + 无损（图 8-12）
- **算法**：先求正则覆盖 `F_c` → 每条 `α→β ∈ F_c` 建一张表 `αβ`；若所有表**都不包含** R 的某个候选键，再补一张"候选键"表；最后（可选）删掉被其他表包含的冗余表。
- **为什么是 3NF**：每张 `αβ` 上 α 是键（α 决定整个表），`F_c` 与 `F` 闭包相同，所以 F⁺ 里每条依赖都能落到某张表上检查。与 BCNF 不同，**保持依赖的 3NF 分解一定存在**，图 8-12 就是构造方法。
- **dept_advisor 例子**：`F={i_ID→dept_name, {s_ID,dept_name}→i_ID}`，`F_c=F`；合成 `(i_ID,dept_name)` 与 `(s_ID,dept_name,i_ID)`；后者含候选键 `{s_ID,i_ID}` ⇒ 不补键；前者被后者包含 ⇒ 删除，最后只剩一张表。结果是 3NF 但**不是 BCNF**。
- **class 例子**：`F` 恰好是正则覆盖；section 表含候选键 ⇒ 不补键；无冗余可删 ⇒ 与 BCNF 分解的三张表完全相同（3NF 合成有时也恰好得到 BCNF）。
- **保依赖 vs 丢依赖**：`R(A,B,C)`、`F={AB→C, C→A}` 的 BCNF 分解 `(B,C)+(A,C)` 丢掉 `AB→C`；3NF 合成先得 `ABC + AC`，删冗余后只剩 `ABC` —— 依赖保住了，但结果仍是 3NF 非 BCNF。这就是"要 BCNF 还是要保依赖"的取舍。
- **怎么判某个子模式是 3NF**：主属性口径 —— 对 Ri 的每个子集 α 算 α⁺；α 不是 Ri 超键时，取 β=(α⁺−α)∩Ri，只要 β 里有**非主属性**（不在 Ri 的任何候选键里）就违反 3NF。注意"主属性"是相对 Ri 的候选键，不是整个 R 的。
- **自己验证**：`com.ds.fd.ThreeNfDecomposition` —— `decompose(R, F)`（含可选删冗余；`decompose(R, F, false)` 可看到合成阶段的冗余）、`Result.canonicalCover()/synthesized()/decomposition()/candidateKeys()/steps()`，自动复核 `thirdNormalForm()` / `bcnf()` / `lossless()`，`preservesDependencies(F)` 应恒为 true；`checkThirdNormalForm(Ri, R, F)` 单独判子模式。演示【十二】跑 dept_advisor、class、补候选键与"BCNF vs 3NF"四个例子。

### 24. 4NF 分解：多值依赖版的 BCNF 分解（图 8-16）
- **多值依赖 α→→β**：给定 α 的值，β 能取的值集合与 R−α−β 的取值集合**相互独立** —— 表现为"α 的每个值对应 β 的一组值，而这组值与其余属性无关地重复出现"。例：`(ID, dept_name, street, city)` 上 `ID→→dept_name` 与 `ID→→street,city` 各自独立，宽表里两组地址信息按笛卡尔积式重复 —— 这是 BCNF 判不出来的冗余（模式可能已是 BCNF）。
- **两条铁律**：①FD 蕴含 MVD（复制律 `α→β ⟹ α→→β`）；②补律 `α→→β ⟹ α→→(R−α−β)`。所以教材例子里的 `ID→→street,city` 其实是 `ID→→dept_name` 的补律产物。
- **4NF 定义（8.6.2 节）**：对 D⁺ 在 Ri 上的限定 Di 中所有**非平凡** MVD α→→β，α 都是 Ri 的超键。与 BCNF 定义的唯一不同就是把 FD 换成 MVD；**4NF ⊆ BCNF**（FD 违反 BCNF ⟹ 复制律 + 补律给出 MVD 违反）。
- **图 8-16 算法**：与图 8-11 完全同构 —— `result = {R}`；重复：若 Ri 不属 4NF，取 Ri 上成立的非平凡 MVD α→→β（`α→Ri ∉ Di` 即 α 不是超键，且 α∩β=∅），做 `result := (result − Ri) ∪ (Ri − β) ∪ (α, β)`。教材例子拆出 `r21(ID,dept_name)` + `r22(ID,street,city)`。
- **一定无损**：每步两块 `(Ri−β)` 与 `(αβ)` 的公共属性是 α、右块差是 β，"公共属性**多重**决定右块差"（α→→β）的二元分解无损；无损复合仍无损。不保证保持 FD 依赖，也会过度规范化（例：`F={A→C}` + `A→→B` 拆两轮得 `(A,B)+(A,C)+(A,D)`）。
- **自己验证**：`com.ds.fd.FourNFDecomposition`（`check` 单独判 4NF 并列出违反项 / `decompose` 图 8-16 主算法 / `Result` 复核 `fourNF()` / `lossless()` / `coversAll()`）与 `com.ds.fd.MultivaluedDependency`；MVD 闭包按补律 + 并/交/差 + 伪传递在 Ri 上迭代到不动点（D⁺ 限定的可靠下界），超键仍用给定 F 的属性闭包。演示【十三】跑教师地址、超键不拆、多步拆分三例。

## 三、读这一章的可执行顺序

1. 先翻完整章的**例题和插图**，只看"它在做什么事"，跳所有公式。
2. 拿一张**自己的表**，把业务规则写成 `X → Y` 若干条（不怕写多，怕不写）。
3. 求候选键（枚举属性子集算闭包，或者用 `FdCalculator.candidateKeys` 算）。
4. 逐条 FD 只问一个问题：**左边是不是超键？** 不是 → 记下来当"肇事者"。
5. 对肇事者做分解：`X∪Y` 一张、`R−Y` 一张，递归到没有肇事者（这就是图 8-11 的 BCNF 分解算法，见第 22 条）；如果**必须保住依赖**，改用 3NF 合成（第 23 条）；冗余来自**一对多独立重复**（多值依赖，BCNF 判不出来）时用 4NF 分解（图 8-16，第 24 条）。
6. 验证三件事：连接行数是否相等（无损）、原 FD 是否还在单表能查（保依赖）、冗余是否消失。
7. 定理证明（无损判定、保依赖反例）**第二遍**再看 —— 有了具体例子，证明才有落点。

## 四、最小记忆集（真正要记住的只有这几条）

1. `X → Y` = 知道 X 就知道了 Y，是业务规则。
2. 候选键 = 能推出全部属性的最小属性集。
3. BCNF = 每条非平凡 FD 的左边都是超键；3NF = 再加一个"右边是主属性就放行"的后门。
4. 违反 BCNF ⇒ 表里会出现重复行 ⇒ 改名要动多行、删行会丢信息。
5. 拆表切的是**右边**（`X∪Y` 与 `R−Y`），不是左边。
6. BCNF 分解一定无损，但可能丢依赖（例 2 就是）。
7. 判 BCNF：未分解时只看 F 就够；**分解后的子模式不能只看 F**，要投影到 F⁺（或对 Ri 的每个子集算闭包）—— `AC→D` 就是只在 F⁺ 里才有的违反项。
8. BCNF 分解算法 = 反复"找一个还不是 BCNF 的 Ri，用违反依赖 α→β（α∩β=∅）拆成 `Ri−β` 与 `αβ`"；一定无损，可能丢依赖、可能过度规范化。
9. 3NF 合成 = 正则覆盖每条 FD 一张表 + 一个候选键（没有表包含它时才补），最后删掉被其他表包含的冗余表；保依赖 + 无损，结果可能仍是 3NF 非 BCNF。
10. 4NF = 把 BCNF 的判据从 FD 换成多值依赖：每个非平凡 MVD α→→β 的左边都得是超键；图 8-16 与图 8-11 同构，每步拆成 `Ri−β` 与 `αβ`，一定无损、不保依赖；FD 蕴含 MVD（复制律），`α→→β` 还总能换成补律形式 `α→→(R−α−β)`。

其余（公理、闭包、最小覆盖、无损判定公式）都是**工具**，用的时候查这份表就行。
