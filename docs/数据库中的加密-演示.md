# 数据库中的加密：加密放在哪一层，安全边界和查询能力完全不同

> 演示脚本：
> `src/main/resources/sql/db_encryption_mysql.sql`（MySQL 内置 AES）、
> `src/main/resources/sql/db_encryption_pg.sql`（PostgreSQL + pgcrypto）、
> `src/main/java/com/ds/db/DbEncryptionDemo.java`（应用层 AES-GCM + 信封加密 + 盲索引）。
>
> 一键复现：`.\scripts\run-db-encryption-demo.ps1`。
>
> 最近一次实跑环境：MySQL 8.0.44、PostgreSQL 17.11、OpenJDK 17；
> 三段演示退出码均为 0，原始输出见
> `docs/db-encryption-mysql-raw.txt`、`docs/db-encryption-pg-raw.txt`、
> `docs/db-encryption-app-raw.txt`、`docs/db-encryption-atrest-raw.txt`。

本文只用一组很小的数据：5 个学生，其中 **S001 和 S003 手机号相同**（都是 `13900001111`）。
故意保留这个"同值"，因为加密方案最容易泄漏的就是"哪两行相同"。

读完你应该能回答三个问题：

1. 加密放在**应用层、数据库函数、存储引擎（TDE）**，分别防住谁？
2. 为什么"加密了"之后，等值查询、范围查询、排序会一个个失效？有没有折中？
3. 为什么口令不能"加密"，只能"哈希"？

---

## 0. 同一个手机号，四种存法

| 存法 | 数据库里 Phone 列的值 | 等值查询 | 主要泄漏 |
|---|---|---|---|
| 明文 | `13900001111` | 走索引，任意条件 | 全泄漏（DBA、备份、日志、注入） |
| 确定性加密（ECB/固定 IV） | 每次都是同一串 16 字节 | 仍可走索引 | 同值同密文 → 频率/等值关系泄漏 |
| 随机化加密（随机 IV/salt） | 每次不同 | 只能全表解密 | 不泄漏等值，但查询退化 |
| 随机化 + 盲索引 | 密文 + `HMAC(手机号)` | 摘要列走索引 | 仍泄漏"哪些行同值" |
| 应用层信封加密（AES-GCM） | 密文 + nonce + tag + 包好的 DEK | 靠盲索引；否则解密 | 密钥在应用/KMS，不在库 |

下面按"从数据库自带能力到应用层"的顺序逐个跑。

## 2. 数据库内置函数：MySQL 的 AES_ENCRYPT

MySQL 8.0 默认 `block_encryption_mode = aes-128-ecb`。
`AES_ENCRYPT(明文, 密钥)` 不指定模式时就走这个默认值：**128 位密钥、ECB、无 IV**。

```sql
SET @k16 = 'demo-key-16byte';   -- 16 字节 = 128 位
CREATE TABLE student_det (
  sid VARCHAR(8) PRIMARY KEY,
  name VARCHAR(20) NOT NULL,
  phone_enc VARBINARY(32) NOT NULL,
  KEY idx_phone_enc (phone_enc)
);
INSERT INTO student_det (sid, name, phone_enc)
SELECT sid, name, AES_ENCRYPT(phone, @k16) FROM student_plain;
```

```text
+------+--------+----------+----------------------------------+
| sid  | name   | ct_bytes | ct_hex                           |
+------+--------+----------+----------------------------------+
| S001 | 张伟   |       16 | 89D733BB70458A195853D11A40E4C512 |
| S002 | 李娜   |       16 | E0C1F1629F8E3E28E34552F2A3DD6BB6 |
| S003 | 王强   |       16 | 89D733BB70458A195853D11A40E4C512 |   -- 与 S001 相同
| S004 | 刘洋   |       16 | 5FDE7A634F16369498B5B7237238A0DD |
| S005 | 陈静   |       16 | BAA5D2ECCC34A868837B6C15093E551F |
+------+--------+----------+----------------------------------+
```

11 个字节的手机号被补成 16 字节的整块，可逆：

```sql
SELECT sid, CONVERT(AES_DECRYPT(phone_enc, @k16) USING utf8mb4) AS phone
FROM student_det ORDER BY sid;
```

看上去"加密成功"了。但注意 **S001 与 S003 的密文一模一样**：
ECB 是确定性的，同一明文 + 同一密钥 → 同一密文。于是：

```sql
SELECT HEX(phone_enc) AS ct_hex, COUNT(*) AS rows_cnt,
       GROUP_CONCAT(sid ORDER BY sid) AS sids
FROM student_det
GROUP BY phone_enc
HAVING COUNT(*) > 1;
```

```text
+----------------------------------+----------+-----------+
| ct_hex                           | rows_cnt | sids      |
+----------------------------------+----------+-----------+
| 89D733BB70458A195853D11A40E4C512 |        2 | S001,S003 |
+----------------------------------+----------+-----------+
```

攻击者不需要密钥，靠 `GROUP BY` 就能知道"S001 和 S003 用同一个号码"。
如果手机号列加密了但**身份证号列是明文**，把两列一关联，这个"同一个号码"
就变成了具体的人。这就是"加密了，但泄漏了等值关系"。

更糟的是，密文列仍然可以建索引，等值查询和统计照做：

```sql
EXPLAIN SELECT sid FROM student_det
WHERE phone_enc = AES_ENCRYPT('13900001111', @k16);
```

```text
+----+-------------+-------------+------+---------------+---------------+---------+-------+------+--------------------------+
| id | select_type | table       | type | possible_keys | key           | key_len | ref   | rows | Extra                    |
+----+-------------+-------------+------+---------------+---------------+---------+-------+------+--------------------------+
|  1 | SIMPLE      | student_det | ref  | idx_phone_enc | idx_phone_enc | 34      | const |    2 | Using where; Using index |
+----+-------------+-------------+------+---------------+---------------+---------+-------+------+--------------------------+
```

**等值查询可用，是因为它确定；泄漏等值关系，也是因为它确定。**
这是一枚硬币的两面，不是实现 bug。

## 3. ECB 的硬伤：相同明文块 → 相同密文块

ECB 对每个 16 字节块独立加密：`C_i = E_K(P_i)`，块之间没有链式反馈。
所以只要明文按 16 字节对齐后出现重复块，密文里就出现重复块：

```sql
SET @p32 = CONCAT(REPEAT('A', 16), REPEAT('A', 16));
SET @c32 = AES_ENCRYPT(@p32, @k16);
SELECT LENGTH(@p32) AS pt_bytes, LENGTH(@c32) AS ct_bytes,
       SUBSTRING(HEX(@c32), 1, 32)  AS block1,
       SUBSTRING(HEX(@c32), 33, 32) AS block2,
       (SUBSTRING(HEX(@c32), 1, 32) = SUBSTRING(HEX(@c32), 33, 32)) AS same_block;
```

```text
+----------+----------+----------------------------------+----------------------------------+------------+
| pt_bytes | ct_bytes | block1                           | block2                           | same_block |
+----------+----------+----------------------------------+----------------------------------+------------+
|       32 |       48 | 3F96B9A285F2F9D6A1EB5661A8D3C041 | 3F96B9A285F2F9D6A1EB5661A8D3C041 |          1 |
+----------+----------+----------------------------------+----------------------------------+------------+
```

32 字节明文 = 2 个数据块，PKCS#7 再补一整块 → 48 字节密文，
两块密文完全相同。经典的 "ECB 企鹅图" 就是这个原因：
图像像素块重复，ECB 把重复模式原样搬到密文里。

MySQL 里有个容易踩的细节：**默认 ECB 下，就算给 IV 也会被忽略**。

```sql
SET @iv0 = RANDOM_BYTES(16);
SELECT HEX(AES_ENCRYPT('13900001111', @k16, @iv0)) AS ct_with_iv;
SHOW WARNINGS;
```

```text
+----------------------------------+
| ct_with_iv                       |
+----------------------------------+
| 89D733BB70458A195853D11A40E4C512 |   -- 和没给 IV 时一样
+----------------------------------+
+---------+------+---------------------+
| Level   | Code | Message             |
+---------+------+---------------------+
| Warning | 1618 | <IV> option ignored |
+---------+------+---------------------+
```

要真正用 IV，必须把会话的 `block_encryption_mode` 切到 CBC（见下一节），
并且密钥长度要和模式匹配（`aes-256-cbc` 要 32 字节密钥）。

## 4. 密钥写成 SQL 字面量：数据库自己会记下来

这是工程上最常见、也最容易被忽略的泄漏：

```sql
SELECT LENGTH(AES_ENCRYPT('13900001111', 'demo-key-16byte')) AS ct_bytes_with_literal_key;
```

执行之后，**这条语句的原文**（含密钥）就留在 `performance_schema` 里：

```sql
SELECT SQL_TEXT
FROM performance_schema.events_statements_history
WHERE THREAD_ID = PS_CURRENT_THREAD_ID()
  AND SQL_TEXT LIKE CONCAT('%', @needle, '%');
```

```text
+-------------------------------------------------------------------------------------------+
| SQL_TEXT                                                                                  |
+-------------------------------------------------------------------------------------------+
| SELECT LENGTH(AES_ENCRYPT('13900001111', 'demo-key-16byte')) AS ct_bytes_with_literal_key |
+-------------------------------------------------------------------------------------------+
```

同样的密钥字面量还会出现在：`general_log`、慢查询日志（语句文本）、
审计插件日志、某些连接池/ORM 的 debug 日志、应用异常堆栈里的 SQL。
所以密钥的正确位置是 **KMS / 密钥管理服务 / Java KeyStore + 环境变量**，
SQL 里只传参数绑定，不要把密钥拼进 SQL。

## 5. 换 CBC + 每行随机 IV：同值不同密文，但查询退化

```sql
SET SESSION block_encryption_mode = 'aes-256-cbc';
SET @k32 = REPEAT('K', 32);

SET @iv = RANDOM_BYTES(16);
INSERT INTO student_cbc VALUES ('S001', '张伟', @iv, AES_ENCRYPT('13900001111', @k32, @iv));
-- ... 每行都重新生成 IV
```

```text
+------+--------+----------------------------------+----------------------------------+----------+
| sid  | name   | iv_hex                           | ct_hex                           | ct_bytes |
+------+--------+----------------------------------+----------------------------------+----------+
| S001 | 张伟   | 88981DFBA23E2B8316E975E3AEB13296 | D2ED375B395B4DE2DCA45218782A0FDC |       16 |
| S002 | 李娜   | 670DFBDF129BE5B69066E60565F1C85F | 150BA2C2E34B2E0033401D7874C97D6F |       16 |
| S003 | 王强   | 03730D9B11F40BDC576DEBCBE0B24344 | 826BC3F588A2A43F9F68230D0FD1F0B6 |       16 |
| S004 | 刘洋   | C3DE2CEC33B3EC7572EADDC60E823FC1 | 58E078311CD556829A0154668604B390 |       16 |
| S005 | 陈静   | 71A6B79B237DF4B0755F94039A97F25C | 411580820EEEE4E4580FDA467295694C |       16 |
+------+--------+----------------------------------+----------------------------------+----------+
```

S001 与 S003 同号，但 IV 不同 → 密文不同：

```text
S001  D2ED375B395B4DE2DCA45218782A0FDC
S003  826BC3F588A2A43F9F68230D0FD1F0B6
```

解密必须把每行的 IV 一起取回来：

```sql
SELECT sid, CONVERT(AES_DECRYPT(phone_enc, @k32, phone_iv) USING utf8mb4) AS phone
FROM student_cbc ORDER BY sid;
```

代价立刻出现：**没有可用的索引列，等值查询只能全表解密**。

```sql
EXPLAIN SELECT sid FROM student_cbc
WHERE AES_DECRYPT(phone_enc, @k32, phone_iv) = '13900001111';
```

```text
+----+-------------+-------------+------+---------------+------+---------+------+------+-------------+
| id | select_type | table       | type | possible_keys | key  | key_len | ref  | rows | Extra       |
+----+-------------+-------------+------+---------------+------+---------+------+------+-------------+
|  1 | SIMPLE      | student_cbc | ALL  | NULL          | NULL | NULL    | NULL |    5 | Using where |
+----+-------------+-------------+------+---------------+------+---------+------+------+-------------+
```

5 行数据看不出差距；50 万行时，每次按手机号查人就要解密 50 万次。

另外，CBC 只解决"同值不同密文"，**不提供完整性**：攻击者可以按位翻转密文，
让解密后的明文按预期变化；配合填充报错还能做 padding oracle。
MySQL 内置 AES 没有 GCM/AEAD，所以字段级加密更适合放到应用层（见第 8 节）。

## 6. PostgreSQL + pgcrypto：随机 salt/IV + 完整性校验

先装扩展：

```sql
CREATE EXTENSION IF NOT EXISTS pgcrypto;
```

`pgp_sym_encrypt(明文, 口令)` 每次调用生成新的随机 salt / session key / IV，
输出是 OpenPGP 格式（含算法参数、随机数和 MDC 完整性校验），所以同值不同密文：

```sql
INSERT INTO student_enc (sid, name, phone_enc, phone_bidx)
SELECT sid, name,
       pgp_sym_encrypt(phone, 'demo-passphrase'),
       hmac(phone, 'blind-index-key', 'sha256')
FROM student_plain;
```

```text
 sid  | name | ct_bytes | ct_hex（截断）                            | bidx_hex（截断）
------+------+----------+-------------------------------------------+------------------
 S001 | 张伟 |       77 | c30d040703023ab23402fc9d63ba76d23c01... | ef77724282b9008e...
 S003 | 王强 |       77 | c30d040703029939f840887d27807dd23c01... | ef77724282b9008e...
(5 rows)

 same_ciphertext | ct_bytes
-----------------+----------
 f               |       77
```

11 字节明文 → 77 字节密文（salt、算法参数、IV、session key、MDC 都算进去了）。
同一明文两次加密结果不同，确认 `same_ciphertext = f`。

有口令就能解：

```sql
SELECT sid, pgp_sym_decrypt(phone_enc, 'demo-passphrase') AS phone
FROM student_enc ORDER BY sid;
```

更重要的是**错口令 / 篡改会报错**，而不是悄悄返回一段垃圾明文：

```text
错误口令   -> Wrong key or corrupt data
密文被篡改 -> Wrong key or corrupt data
```

pgcrypto 的 PGP 加密带 MDC（修改检测码），解密时会校验；
裸 CBC 没有这个能力，填充稍微不对就可能返回错误但"看起来像明文"的结果。

## 7. 盲索引：加密和查询之间的折中

需求是"手机号不能明文存，但要能按手机号精确查人"。
解法不是解密全表，而是存一列 **HMAC(手机号)**：

```sql
CREATE INDEX idx_student_enc_bidx ON student_enc (phone_bidx);

SET enable_seqscan = off;   -- 5 行小表默认会走顺序扫描，这里强制看索引路径

EXPLAIN (COSTS OFF)
SELECT sid FROM student_enc
WHERE phone_bidx = hmac('13900001111', 'blind-index-key', 'sha256');
```

```text
 Index Scan using idx_student_enc_bidx on student_enc
   Index Cond: (phone_bidx = '\xef777242...'::bytea)
```

命中 S001、S003。对照"没有盲索引，只能逐行解密"：

```text
 Seq Scan on student_enc
   Filter: (pgp_sym_decrypt(phone_enc, 'demo-passphrase'::text) = '13900001111'::text)
```

Java 演示里同样验证了 MySQL 的行为（`EXPLAIN type=ref key=idx_phone_bidx rows=2`），
并把"逐行解密 5 行"和"一次索引查询"放在一起对比。

盲索引的边界必须说清楚：

| 能做 | 不能做 |
|---|---|
| 等值查询（`WHERE phone_bidx = ?`）、去重、连接 | 范围查询（`>`、`BETWEEN`）、前缀（`LIKE '138%'`）、排序 |
| 走普通 B-Tree 索引，性能接近明文索引 | 同值摘要相同 → 仍泄漏"哪些行同值"（频率分析） |

HMAC 的密钥必须和加密密钥分开管理；如果盲索引密钥泄漏，
手机号空间很小（11 位数字），攻击者可以直接枚举出所有摘要对应的号码。
所以盲索引防的是"拖库后直接读明文"，不是"有密钥的攻击者"。

## 8. 应用层信封加密：AES-GCM + KEK/DEK + 轮换

这是字段级加密比较完整的一种做法（Java 演示，JDBC 连 MySQL）。
核心是**两层密钥**：

```text
KEK（主密钥，放 KMS/KeyStore，不进数据库）
 │  AESWrap 包住
 ├── DEK₁（每条记录随机 256 位）── AES-GCM 加密该行的 name / phone
 ├── DEK₂
 └── ...
```

数据库表里只有：

```sql
CREATE TABLE student_envelope (
  sid VARCHAR(8) PRIMARY KEY,
  name_ct VARBINARY(64), name_nonce VARBINARY(12), name_tag VARBINARY(16),
  phone_ct VARBINARY(64), phone_nonce VARBINARY(12), phone_tag VARBINARY(16),
  phone_bidx BINARY(32),          -- HMAC-SHA256(手机号)
  wrapped_dek VARBINARY(64),      -- AESWrap(KEK, DEK)
  KEY idx_phone_bidx (phone_bidx)
);
```

DBA 视角的一次 `SELECT`：

```text
  S001
    name_ct   = 5D724E5E65CF
    phone_ct  = FC46FB398B1C6904240CB3   (nonce=EE9C3E5A438CB110B2AC02E9, tag=77A902A5799C8CDC4CE3958B57967F4C)
    phone_bidx= 13FE417BDF7549FE1298ADBACE3446261D6B438F756DF794FF77BD58C745601A
    wrapped_dek=C63ADDE8AED6A24177EC98872742523C79AAB3B52CE479959CEBDE59CB78FBA4D41DC2CED223C6BE
```

应用拿到 `wrapped_dek`，用 KEK 解出 DEK，再解 `phone_ct + tag`，才得到明文。
`name` 和 `phone` 用了不同的 nonce，并且 AAD 绑定了 `sid + 字段名`，
所以把 S001 的密文挪到 S002 行、或把 name 密文塞进 phone 列，都会因认证失败被拒绝。

三个关键点，用实跑输出说明：

**① AEAD：改一个字节就解密失败**

```text
解密失败: AEADBadTagException（tag 校验不通过，密文被视为损坏）
```

GCM 的 128 位 tag 保证"密文 + AAD"整体被认证；这比 CBC 的"可能解出垃圾"强。

**② 盲索引让等值查询继续可用**

```text
EXPLAIN: type=ref key=idx_phone_bidx rows=2 Extra=Using where; Using index
命中: [S001, S003]（S001 与 S003 同号）
WHERE phone_ct LIKE '%138%' → 0 行（密文里搜不到明文）
```

**③ 信封加密让 KEK 轮换不用重加密数据**

```text
S001 wrapped_dek 前: c63adde8aed6a24177ec98872742523c79aab3b52ce479959cebde59cb78fba4d41dc2ced223c6be
S001 wrapped_dek 后: 709783fbcc45554c9f31b39cb2633c791b04744cccc354466c97b452d5aa43c11d1acd3307f4acc1
S001 phone_ct 是否变化: false（应为 false）
用新 KEK 解 S001: 13900001111（旧密文直接复用）
旧 KEK 解新 wrapped_dek: 失败（AESWrap 完整性校验拒绝）
```

轮换 KEK 只需要把所有行的 `wrapped_dek` 解包再打包，业务密文一个字节都不用动；
代价是应用要自己管理密钥、nonce 不能重复、AAD 要绑定好上下文。

## 9. 磁盘上的真相：TDE 防的是什么

"数据库文件在磁盘上"和"数据库里能 SELECT 到"是两层。
PostgreSQL 的堆文件可以直接按字节读。先让服务端落盘（`CHECKPOINT`），
再按 `pg_relation_filepath` 找到文件：

```text
在 student_plain 堆文件中搜索明文手机号 '13900001111'：offset=8085
在 student_enc   堆文件中搜索明文手机号 '13900001111'：offset=-1
在 student_enc   堆文件中搜索 S001 的密文字节（77 字节）：offset=8077
```

含义很直接：

- 明文表的磁盘文件里，**手机号就是明文**——备份、磁盘镜像、被拖走的
  `.ibd` / 堆文件都能直接读到；
- 加密表的同一列在磁盘上找不到明文，但能按字节找到那段密文（证明行确实在文件里）。

**TDE（透明数据加密）** 就是在存储引擎层做这件事：
MySQL 的 InnoDB 表空间加密（需要 keyring 组件）、SQL Server 的 TDE、
Oracle 的 TDE 列/表空间加密。它对应用透明，查询、索引、范围扫描全都不变。

但要记住 TDE 的边界：

| TDE 防 | TDE 不防 |
|---|---|
| 磁盘/备份/卷被偷走（没有密钥解不开文件） | DBA 用 SQL 正常查询（引擎解密后返回明文） |
| 误把数据文件拷走 | SQL 注入、越权 SELECT、应用漏洞 |
| 合规要求的"静态加密"检查项 | 字段级最小权限（需要应用层加密） |

PostgreSQL 17 官方核心**没有** TDE（社区有 `pg_tde` 等扩展），
所以 PG 场景下"字段级加密 + 应用层密钥管理"更常见。
本机 MySQL 数据目录（`C:\ProgramData\MySQL\...`）被系统 ACL 拒绝读取，
因此磁盘层用 PostgreSQL 堆文件验证；机制相同——没有 TDE 时数据文件里就是明文。

## 10. 口令不是"加密"，是"哈希"

```sql
CREATE TABLE app_user (username varchar(32) PRIMARY KEY, pwd_hash text NOT NULL);
INSERT INTO app_user VALUES
  ('alice', crypt('alice123', gen_salt('bf', 10))),
  ('bob',   crypt('alice123', gen_salt('bf', 10)));   -- 同一个口令
```

```text
 username |                           pwd_hash
----------+--------------------------------------------------------------
 alice    | $2a$10$huV8OPKJ6TCJEWUDt1SMT.Z9dw4nXqH7oACvl2wQusB83fDx7/Az2
 bob      | $2a$10$sMBuYhn0nVSoXTbpB9B9s.32PNRCfj.K9DxYuxWWrculbxl/iptCG
```

同一个口令，两次哈希不同（随机 salt）；验证时用 `crypt(输入, 存储的哈希) = 存储的哈希`：

```text
 alice | t        bob | t        -- 正确口令
 alice | f        bob | f        -- 错误口令
```

bcrypt 是**单向、故意慢**的（cost=10 约几十毫秒），只能验算不能还原。
口令用可逆加密是反模式：密钥一旦泄漏，所有用户口令直接还原；
而 bcrypt/argon2 即使库和代码都泄漏，攻击者也只能逐个暴力尝试。

## 11. 传输层：连接本身有没有加密

**MySQL 8.0 默认启用 TLS**，客户端默认 `ssl-mode=PREFERRED`，本机 TCP 连接也协商出了 TLS：

```text
+---------------+------------------------+
| Variable_name | Value                  |
+---------------+------------------------+
| Ssl_cipher    | TLS_AES_256_GCM_SHA384 |
+---------------+------------------------+
| have_ssl      | YES                    |
```

显式关掉 TLS 再看，就是空的：

```text
mysql --ssl-mode=DISABLED -e "SHOW SESSION STATUS LIKE 'Ssl_cipher'"
+---------------+-------+
| Ssl_cipher    |       |
+---------------+-------+
```

**PostgreSQL 17 默认 `ssl=off`**，本机连接就是明文：

```text
 ssl | version | cipher
-----+---------+--------
 f   |         |
```

传输加密防的是"链路上抓包"（中间人、同网段嗅探），
和字段加密、TDE 是三件不同的事，不能互相替代。
生产环境至少应该：MySQL/PostgreSQL 开 TLS、客户端 `sslmode=require/verify-full`、
应用与数据库之间不要走公网明文。

## 12. 对照表：怎么选

| 方案 | 数据库看到 | 查询能力 | 泄漏 | 典型用途 |
|---|---|---|---|---|
| 明文 | 明文 | 全部 | 全部 | 非敏感数据 |
| 确定性加密（ECB/固定 IV） | 固定密文 | 等值、索引、统计 | 等值/频率关系 | 很少推荐；仅"必须等值查"且能接受泄漏 |
| 随机化加密（随机 IV/salt） | 每次不同密文 | 只能全表解密 | 几乎不泄漏等值 | 只写少读、或配合盲索引 |
| 盲索引（HMAC） | 密文 + 摘要 | 仅等值 | 等值关系（同值同摘要） | 手机号/邮箱/身份证的精确查人 |
| 应用层 AEAD（GCM）+ 信封 | 密文 + nonce + tag + wrapped DEK | 等值靠盲索引 | 等值关系；密钥在应用 | 敏感字段的主流做法 |
| TDE（存储层） | 明文（引擎内） | 全部 | 无（对 SQL 透明） | 防磁盘/备份被拖走 |
| 传输 TLS | — | — | — | 防链路抓包 |
| 密码哈希（bcrypt/argon2） | 单向摘要 | 只能验算 | 无（慢哈希抗爆破） | 用户口令 |

选型建议（按优先级）：

1. **口令**：bcrypt / argon2id，永不加密、永不解密。
2. **传输**：TLS 全链路，证书校验打开。
3. **静态**：能用 TDE 就开（防磁盘/备份），但它不防 DBA，别把它当字段加密。
4. **敏感字段**（手机号、身份证、银行卡）：应用层 AES-GCM + KMS 管密钥；
   需要精确查人再加盲索引；需要范围查询就设计专门的索引结构，而不是退回明文。
5. **密钥管理**：KEK 进 KMS/HSM，DEK 随机按行生成，定期轮换 KEK（只重包 DEK）；
   密钥不进代码、不进 SQL、不进日志。

## 13. 常见坑清单

1. 把 Base64 当加密（Base64 只是编码，任何人都能解）。
2. 用 ECB 或固定 IV（同值同密文，模式泄漏）。
3. 密钥硬编码在 SQL / 配置文件 / 代码仓库里，还进了 `performance_schema` 和日志。
4. 加密列上仍用 `LIKE '%...%'` / 范围查询，发现查不到就退回明文存储。
5. 以为"加密了"就能防 DBA——字段加密能防，TDE 不能。
6. 忘记备份密钥：密钥一丢，数据永久打不开（比泄漏更常见的事故）。
7. 只加密主表，日志、缓存、报表库、导出文件里仍是明文。
8. 口令用 AES 加密，密钥一泄漏全量还原。
9. nonce 复用：GCM 下同一密钥 + 同一 nonce 加密两条不同明文，会直接破坏机密性和认证。
10. 盲索引密钥和加密密钥混用；或盲索引用了可枚举的哈希（手机号空间太小，必须带密钥）。

## 一句话总结

- **加密的位置决定它能防谁**：TLS 防链路，TDE 防磁盘，字段加密防 DBA/拖库，口令哈希防反查。
- **加密的位置也决定查询能力**：随机化加密让等值查询失效；确定性加密/盲索引把等值查询换回来，
  但会泄漏"哪些行相同"。
- **密钥管理比算法更难**：密钥不要进 SQL、日志、代码；KEK/DEK 分层，轮换只重包 DEK。
