## 1. 一句话

证书在项目里只活在两个时刻：

- **握手时**：证明"这把公钥属于这个域名"，然后双方协商出一把临时的对称密钥；
- **业务里**：当一个签名工具（代码签名、成绩单签名、令牌签名），或者当"谁能连进来"的门禁（mTLS）。

中间的每一个字节传输，都由握手协商出的会话密钥保护，**和证书本身无关**。所以证书不是"加密数据用的"，它是**身份证明**——加密靠的是握手。

## 2. 一次 HTTPS 请求的完整时序

以 university 项目现在的部署（浏览器 → Caddy/Nginx → Spring Boot）为例：

```text
浏览器                                                       服务器
  |  1 DNS：university.example.edu.cn -> 203.0.113.10          |
  |------------------------------------------------------------>|
  |  2 TCP 三次握手（443）                                       |
  |------------------------------------------------------------>|
  |  3 TLS 握手                                                  |
  |     ClientHello（我要访问 university.example.edu.cn）        |
  |------------------------------------------------------------>|
  |                           ServerHello + 证书链 + CertificateVerify + Finished
  |<------------------------------------------------------------|
  |     客户端：逐张验证书链直到信任锚、检查 SAN/有效期/用途        |
  |     然后生成预主密钥，双方算出同一把会话密钥                    |
  |     Finished（确认握手没被篡改）                              |
  |------------------------------------------------------------>|
  |  4 HTTP 请求（GET /student/home）—— 用会话密钥加密             |
  |------------------------------------------------------------>|
  |                             Nginx/Caddy 解密、加 X-Forwarded-Proto，转给 8080
  |                             Spring Boot 处理业务（它根本看不到证书）
  |<------------------------------------------------------------|
  |  5 HTTP 响应 —— 同样用会话密钥加密                             |
```

要点：

1. **证书只在第 3 步出现一次**，第 4、5 步完全不碰证书；应用进程（Spring Boot）甚至不知道有证书这回事——TLS 在反向代理那一层就终结了。
2. 客户端验证的是"**这把公钥能不能证明自己属于这个域名**"，而不是"服务器是不是好人"。
3. 会话密钥是**临时**的：连接断开就丢，下次握手重新协商（TLS 1.3 支持会话复用，见第 3 节末尾）。

## 3. 真实握手报文：7 条消息

下面是本机真实跑出来的报文序列（[tls-handshake-trace.txt](tls-handshake-trace.txt)），客户端访问 `a.example.com`：

```text
>> Produced ClientHello handshake message
     type=host_name (0), value=a.example.com

>> Produced ServerHello handshake message
     "cipher suite"        : "TLS_AES_256_GCM_SHA384(0x1302)",

>> Consuming EncryptedExtensions handshake message

>> Consuming server Certificate handshake message

>> Produced server CertificateVerify handshake message

>> Produced server Finished handshake message

>> Produced client Finished handshake message
```

逐条看它们在防什么：

| # | 消息 | 方向 | 作用 |
|---|---|---|---|
| 1 | ClientHello | C→S | 支持的版本/套件/签名算法；**SNI** 告诉服务器"我要访问哪个域名"；附带一个随机数 |
| 2 | ServerHello | S→C | 选定的套件（本例 `TLS_AES_256_GCM_SHA384`）、密钥交换参数、服务端随机数 |
| 3 | EncryptedExtensions | S→C | 从这里开始握手消息**全部加密**（所以抓包看不到后面的明文） |
| 4 | Certificate | S→C | 服务端证书链：**叶子 + 中间，不发根**（根在客户端信任库里） |
| 5 | CertificateVerify | S→C | 服务端用证书私钥对"握手摘要"签名——证明**私钥在手**，不是只偷了证书 |
| 6 | Finished | S→C | 服务端对握手内容做 MAC，确认没被中间人改过 |
| 7 | Finished | C→S | 客户端同样确认 |

几条容易忽略的细节：

- **日志里 `"client version" : "TLSv1.2"` 不是错**。这是 TLS 1.3 的兼容设计：ClientHello 里有一个 legacy_version 字段固定写 1.2，真正的版本协商在 `supported_versions` 扩展里。所以光看这个字段会误判。
- **CertificateVerify 是"防偷证书"的关键**。证书是公开的，谁都能拿到；只有私钥持有者能对本次握手签名。没有这一步，攻击者把别人的证书原样重放就能冒充。
- **Certificate 里没有根证书**。这是刻意的：根在客户端预置（cacerts / 系统信任库 / 浏览器），服务器发它没有意义，反而增加体积。
- **之后是 HTTP**。整个握手的产出就是一把会话密钥，业务数据全部用它加密。
- **第二次连接会复用**（TLS 1.3 的 PSK / session ticket）：服务端只发 ServerHello + 少量消息，**不再发证书**。这就是"同一站点第二次打开更快"的原因，也是线上要关注 session ticket 密钥轮换的原因。

### 3.1 用 openssl 独立复核：漏发中间证书会怎样

JDK 的校验器告诉我们"通过/拒绝"，openssl 则能看到**服务端到底发了什么**。同一张叶子证书、同一台服务端，只差"发不发中间证书"（[tls-openssl-check.txt](tls-openssl-check.txt)）：

```text
=== 场景 A：服务端发【叶子 + 中间证书】（= Nginx 用 fullchain.pem） ===
CONNECTION ESTABLISHED
Protocol version: TLSv1.3
Ciphersuite: TLS_AES_256_GCM_SHA384
Peer certificate: C=CN, O=Alg4 Demo, CN=a.example.com
Signature type: RSA-PSS
Verification: OK

=== 场景 B：服务端只发【叶子证书】（= 漏配中间证书的线上事故） ===
depth=0 C=CN, O=Alg4 Demo, CN=a.example.com
verify error:num=20:unable to get local issuer certificate
```

`unable to get local issuer certificate` 就是线上那个经典故障的原始出处：客户端手里只有根证书，叶子证书的签发者（中间证书）没发过来，链就断了。浏览器/Java 把它包装成 `PKIX path building failed`，本质上说的都是这一句。

顺带一个手工细节：`openssl s_server -cert` 只读文件里的第一张证书，中间证书要用 `-cert_chain` 单独给；Nginx 的 `ssl_certificate fullchain.pem` 相当于"两个都给"。

## 4. 证书在真实项目里的五处落点

同一个"证书"概念，在项目里扮演五种不同角色：

| 场景 | 谁出示证书 | 谁验证 | 验什么 | 本项目落点 |
|---|---|---|---|---|
| **HTTPS 站点** | 服务器 | 浏览器/客户端 | 链 + SAN + 有效期 + EKU=serverAuth | Caddy/Nginx（或 `tls` profile） |
| **双向 mTLS** | 双方都出示 | 双方互验 | 上面的全部 + 客户端证书的 EKU=clientAuth | 服务间调用、K8s、数据库强制客户端证书 |
| **客户端身份** | 客户端 | 服务端 | 同上 | 内部 API、VPN、设备接入 |
| **代码/文档签名** | 签名者 | 验证方 | 用公钥验签名，不看域名 | jarsigner、成绩单签名、PDF 签章 |
| **令牌签名** | 签发方 | 验证方 | JWT/JWS 的签名段 | 内部 SSO、开放平台 |

区别只在于**证书里的约束**（KeyUsage / EKU）和**谁验**。一张写着 `EKU=serverAuth` 的证书拿去签代码，规范的验证方会拒绝——这就是"专钥专用"。

## 5. university 项目里其实是两张证书

项目里现在同时存在两个 PKCS12，用途完全不同，**不要混用**：

| | `keystore/university.p12` | `keystore/transcript-signing.p12` |
|---|---|---|
| 用途 | HTTPS 服务端证书 | 成绩单签名 |
| KeyUsage | 由 CA 决定（serverAuth + keyEncipherment） | `digitalSignature, nonRepudiation` |
| EKU | serverAuth | 无（或 clientAuth 之外的签名用途） |
| 谁拿着私钥 | Web 进程（Nginx/Caddy 或 Spring Boot 读） | 只有签名服务读 |
| 更换周期 | 90 天（Let's Encrypt）~ 1 年 | 10 年 |
| 泄露后果 | 别人能冒充站点 | 别人能伪造成绩单（更严重） |

`gen-transcript-signing-keystore.ps1` 的注释里写得很直白："与 HTTPS 证书分开，专钥专用"。签名实现（`TranscriptSigner`）优先 RSA-PSS，JDK 8 回退 SHA256withRSA，并且**私钥只在签名服务的内存里**，不给模板层、不给前端。

真实项目里这种"一张证书只干一件事"的分法，好处是：一张证书泄露不牵连另一个能力；用途约束（KeyUsage/EKU）让验证方可以拒绝越权使用；轮换周期可以按各自风险设定。

## 6. 演示：mTLS 与 SNI

### 6.1 双向认证（mTLS）

演示里服务端打开 `setNeedClientAuth(true)`，结果（[tls-handshake-demo-raw.txt](tls-handshake-demo-raw.txt)）：

```text
客户端带证书：服务端看到客户端证书：CN=alice,OU=Student,O=Alg4 Demo,C=CN
  [通过] 服务端拿到了客户端证书 CN=alice，握手完成
客户端不带证书：SSLHandshakeException: Empty client certificate chain
  [通过] 服务端拒绝对不带证书的客户端完成握手
```

mTLS 的本质：**双方各有一张证书，各自验对方的链**。普通 HTTPS 只回答"我连的是不是真的你"；mTLS 还回答"**你是不是被我允许的**"。

生产里它出现在：服务网格（Istio/Linkerd 自动为每个 Pod 签发短期证书）、Kubernetes API、数据库的 `REQUIRE X509`、内部 RPC、设备接入。代价是证书发放与轮换要做自动化——所以 K8s 里通常用 cert-manager 或 SPIFFE/SPIRE，证书有效期只有几小时。

### 6.2 SNI 选证书

演示里一个端口后面挂两张证书，客户端报不同域名拿不同证书：

```text
客户端说访问 a.example.com -> 服务端出示的证书是 a.example.com（SAN DNS:a.example.com, IP:127.0.0.1）
客户端说访问 b.example.com -> 服务端出示的证书是 b.example.com（SAN DNS:b.example.com）
```

这就是 Nginx 的 `server_name`、Caddy 的多站点、以及所有 CDN 在底层做的事。关键点：

- 一个 IP 只能配一个**默认**证书；能不能"按域名给不同证书"，取决于客户端有没有在 ClientHello 里带 SNI；
- 不带 SNI 的老客户端，服务器只能返回默认证书——这就是早年"一个 IP 只能挂一个 HTTPS 站点"的原因（后来有了 SNI，才有一台机器托管几千个站）。

## 7. 线上是怎么"自动运转"的

证书不是签完就完事，真实项目里的工作流是：

```text
申请/续期 -> 部署 -> reload -> 监控 -> 轮换（提前或应急）
```

| 环节 | 常见做法 | 本项目的对应 |
|---|---|---|
| 签发/续期 | ACME（certbot / Caddy / cert-manager）；云厂商 API | Let's Encrypt + certbot，或 Caddy 自动 |
| 部署 | 证书落到固定路径/卷，配置引用 `fullchain.pem` | `deploy/nginx/university.conf`、`deploy/Caddyfile` |
| 生效 | Nginx `reload`（不断连接）；Java 应用需要重启或用热加载 | certbot 的 deploy-hook `nginx -s reload` |
| 监控 | 到期前 30/14/7 天告警；探针检查链完整性 | `keytool -printcert -sslserver`、监控系统探针 |
| 轮换 | 双证书并存 → 切流量 → 下线旧证；或直接热替换 | 保留旧证书与旧配置，5 分钟内可回滚 |
| 多实例 | 证书放共享卷/对象存储/密钥管理服务，别每台各签一张 | Docker 卷 `caddy-data` |

Kubernetes 里这套是被平台收编的：cert-manager 监听 Ingress 注解，自动签发、自动续期、自动更新 Secret；Istio/Linkerd 给每个工作负载签发几小时有效的证书，轮换对业务无感。

## 8. 真实事故清单（每一条都能对上六道检查）

| 症状 | 原因 | 修法 |
|---|---|---|
| 浏览器"证书已过期" / 502 | 忘续期、定时任务没跑 | 自动续期 + 到期告警 |
| `PKIX path building failed` | 只发了叶子证书（用了 `cert.pem` 而不是 `fullchain.pem`） | 换 fullchain，或在服务端补中间证书 |
| `No subject alternative DNS name matching ...` | SAN 里没有实际访问的域名（`www.` vs 裸域、换域名没重签） | 重签并把所有域名写进 SAN |
| 换证书后老客户端全挂 | 客户端做了证书 pinning | 轮换前先发一版"接受新证书"的客户端 |
| 证书泄露 | 私钥进了 git、权限 644、备份没加密 | `.gitignore`、`chmod 600`、KMS/HSM |
| 续期成功但仍报旧证书 | 续期后没 reload / 没重启 | deploy-hook 里加 reload，并验证 |
| 中间证书过期 | 只盯着叶子证书的到期时间 | 同时监控链上每一张 |
| 突然全站证书报错 | 客户端系统时间错乱、或根证书被系统更新移除 | 检查时间同步、根证书库版本 |

## 9. 证书解决不了什么

- **服务端被攻破**：攻击者拿到私钥就能冒充，证书本身拦不住（只能靠吊销 + 短有效期缩小窗口）。
- **业务漏洞**：SQL 注入、越权访问和证书无关。
- **客户端信任被污染**：企业装了自己的根证书做 HTTPS 解密，浏览器会显示"绿锁"但中间人在看——这时证书链是"合法"的。
- **域名/解析被劫持**：攻击者拿到域名控制权后可以合法申请新证书。
- **私钥泄露后的窗口期**：CRL/OCSP 不是实时的，浏览器也未必每次都查；所以现在行业趋势是**缩短有效期**（Let's Encrypt 已在 2025 年停用 OCSP，转向短有效期 + CRL）。

一句话：**证书保证"你连的是持有该域名私钥的人"，不保证"这个人是好人"、也不保证"这个服务没被黑"**。

## 10. 自己动手看一次真实握手

```powershell
# 1) 本仓库演示：真实握手报文 + mTLS + SNI（全程离线，本机回环）
.\scripts\run-tls-handshake-demo.ps1

# 2) 只看报文：JDK 的调试开关（输出很大，适合重定向到文件后搜关键字）
java -Djavax.net.debug=ssl:handshake -cp target\tls-classes com.ds.crypto.TlsHandshakeDemo target\tls-demo trace

# 3) 看任意线上服务器的证书（JDK 自带，Windows 可用）
keytool -printcert -sslserver university.example.edu.cn:443

# 4) 用 openssl 看是否发全链、协商的协议与套件
#    Linux 直接写 openssl；本机在 D:\OpenSSL-Win64\bin\openssl.exe（脚本会自动找到它）
D:\OpenSSL-Win64\bin\openssl.exe s_client -connect university.example.edu.cn:443 -servername university.example.edu.cn -showcerts

# 5) 浏览器：开发者工具 -> Security -> 查看证书，能看到 叶子 -> 中间 -> 根 的完整链
```

报文里的关键字：`ClientHello` / `ServerHello` / `EncryptedExtensions` / `Certificate` / `CertificateVerify` / `Finished`；想知道"为什么没发全链"，数 `BEGIN CERTIFICATE` 的个数即可。
