## 0. 先用一个具体问题开场

先别看理论，先回答一个问题：

> **2022-06-01，张伟的工资是多少？**

在同一个数据库里，这个问题的答案取决于**你什么时候问**：

| 提问时刻 | 系统当时认为 2022-06-01 的工资 | 系统当时认为 2023-06-01 的工资 |
|---|---|---|
| 2023-07-15（当时问） | 14000 | 14000 |
| 2024-05-10（当时问） | 14000 | 16000 |
| 今天（最新信念） | **14500** | **16000** |

同一张表、同一个日期，答案不是一个数，而是**"有效日期"和"提问时刻"两个参数的函数**。
这不是数据错了，而是现实本来就这样：工资会变（现实世界的时间线），我们对工资的认知也会变
（补录、更正——数据库自己的时间线）。**时态数据建模就是把这两条时间线都存下来**。

本文用一个 HR 工资表把这套东西完整落地：7 次写入、1 张双时态表、4 类查询、1 个由数据库
强制的"区间不重叠"约束，SQL 与 Java 两套实现给出同一组答案。

## 1. 两条时间线：valid time 与 transaction time

| | 有效时间（valid time） | 事务时间（transaction time） |
|---|---|---|
| 含义 | 事实在**现实世界**中为真的区间 | 数据库**相信**这条事实的区间 |
| 回答的问题 | 那一天实际拿多少钱？ | 那一天系统里记的是什么？ |
| 由谁决定 | 业务/人事规则，可以追溯修改 | 写入数据库的时刻，只能前进 |
| 本文粒度 | 日期 `daterange` | 时间戳 `tsrange` |
| 能不能事后改 | 能（补录、更正，产生**新版本**） | 不能（不允许改写过去） |

两条时间线在真实业务里经常**错位**。本文的 7 次写入就是照着这种错位设计的：

| # | 事务时间 tx（何时入库） | 员工 | 月薪 | 有效区间 valid（现实何时生效） | 现实里发生了什么 | 写操作 |
|---|---|---|---|---|---|---|
| 1 | 2021-01-01 | E1001 张伟 | 12000 | [2021-01-01, ∞) | 入职 | `append` |
| 2 | 2021-07-01 | E1002 李娜 | 10000 | [2021-07-01, ∞) | 入职 | `append` |
| 3 | 2022-04-01 | E1001 | 14000 | [2022-04-01, ∞) | 涨薪 | `setValueFrom` |
| 4 | 2024-01-05 | E1001 | 18000 | [2024-01-01, ∞) | 再涨薪 | `setValueFrom` |
| 5 | **2024-05-10** | E1001 | 16000 | **[2023-03-01, 2024-01-01)** | HR 补录追溯涨薪 | `setValueFrom`（自动截到下一次变化） |
| 6 | 2024-06-01 | E1001 | 14500 | [2022-04-01, 2023-03-01) | 更正 2022 年那次录入错误 | `updateForPortion` |
| 7 | 2024-07-01 | E1002 | 10000 | [2021-08-01, ∞) | 更正入职日期 | `deleteForPortion`（截掉错录段） |

第 5 行是重点：**现实 2023-03-01 就生效了，系统 2024-05-10 才知道**——两条时间线差了 14 个月。
如果只存 valid time，这个 14 个月的认知差就永远丢了；如果只存 tx time，又不知道"哪天实际拿多少钱"。

两个细节，后面会反复用到：

- **区间一律左闭右开**：`[2021-01-01, 2022-04-01)` 与 `[2022-04-01, 2024-01-01)` 首尾相接但**不重叠**。
- **"现在"是事务时间无上界**：当前信念 = `tx` 上界为 ∞ 的那些行；历史版本的上界会被后来的写入封住。

### 1.1 抽象概念落到这张表上

| 时态建模里的概念 | 本文的落地形式 |
|---|---|
| 有效时间（valid time） | `valid daterange` 列 |
| 事务时间（transaction time） | `tx tsrange` 列 |
| 双时态关系（bitemporal relation） | 一张 `temporal_salary` 表 |
| 一个版本 | 一行 `(emp_id, salary, valid, tx)` |
| 时态键：同一员工同一时刻只能有一个值 | `EXCLUDE USING gist (emp_id WITH =, valid WITH &&, tx WITH &&)` |
| 追溯更正 / 补录 | 把旧版本的 `tx` 上界封到"现在"，再插入新版本 |
| "当时系统怎么想" | `WHERE tx @> 某个时刻` |
| 逻辑删除 | 用 `deleteForPortion` 截掉区间，旧版本仍保留 |

后面第 4 节的 SQL 与第 8 节的 Java 类，都是这张对照表的实现。

## 2. 第一版：只存当前值（版 A）

最常见的建法，也是最容易把历史弄丢的建法：

```sql
CREATE TABLE emp_current (
    emp_id text PRIMARY KEY,
    salary int
);
```

| emp_id | salary |
|---|---|
| E1001 | 18000 |
| E1002 | 10000 |

问"2022-06-01 的工资是多少"，表里没有任何一列能回答这个问题：只能拿到 `18000`（现在的值）。
问"涨过几次薪"，同样无列可查。

> 只存当前值 = 只有"现在"，没有"历史"。

## 3. 第二版：加有效期（单时态，版 B）

给每行加一个有效区间，并让数据库保证"同一员工的有效期不重叠"：

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;   -- 让 text 的 = 也能进 GiST 索引

CREATE TABLE salary_valid_only (
    emp_id text NOT NULL,
    salary int NOT NULL,
    valid  daterange NOT NULL,
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    CONSTRAINT salary_valid_only_no_overlap
        EXCLUDE USING gist (emp_id WITH =, valid WITH &&)
);

INSERT INTO salary_valid_only (emp_id, salary, valid) VALUES
    ('E1001', 12000, daterange('2021-01-01', '2022-04-01')),
    ('E1001', 14000, daterange('2022-04-01', '2024-01-01')),
    ('E1001', 18000, daterange('2024-01-01', NULL)),
    ('E1002', 10000, daterange('2021-07-01', NULL));
```

`valid @> date '2022-06-01'` 查出来是 **14000**，这次答对了。但马上撞上两堵墙：

**墙一：没有 tx 列，答不出"当时系统怎么想"。**
"2023-07-15 那天，系统认为 2022-06-01 的工资是多少？"——表里只有一条时间线，没有可以比较的第二个维度。
而且当时系统里 2022-06-01 落在 `[2022-04-01, ∞) 14000` 这一段（2023-03 的涨薪还没补录），
这个"当时的当前信念"现在**已经无法重建**了。

**墙二：追溯更正会覆盖旧值，而且不可恢复。**

```sql
-- 发现 2022 年那次录入错了：应为 14500
UPDATE salary_valid_only
SET salary = 14500
WHERE emp_id = 'E1001' AND valid @> date '2022-06-01';
```

更新后表变成：

| emp_id | salary | valid |
|---|---|---|
| E1001 | 12000 | [2021-01-01, 2022-04-01) |
| E1001 | **14500** | [2022-04-01, 2024-01-01) |
| E1001 | 18000 | [2024-01-01, ∞) |
| E1002 | 10000 | [2021-07-01, ∞) |

14000 被覆盖，原来"我们曾相信 14000"这件事没有任何痕迹。更麻烦的是：**这次 UPDATE 到底是
"改错"还是"追溯调薪"，表里长得一模一样**——业务语义丢掉了。

> 单时间线解决了"事实会变"，没有解决"认知会变"。

## 4. 第三版：双时态（版 C）

每一行同时带 valid 和 tx 两个区间，再加一个由数据库强制的约束：

```sql
CREATE TABLE temporal_salary (
    emp_id text NOT NULL,
    salary int NOT NULL,
    valid  daterange NOT NULL,          -- 有效时间（现实世界）
    tx     tsrange   NOT NULL,          -- 事务时间（数据库认知）
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    CONSTRAINT temporal_salary_valid_not_empty CHECK (NOT isempty(valid)),
    CONSTRAINT temporal_salary_valid_bounds
        CHECK (lower(valid) IS NOT NULL
               AND (upper_inf(valid) OR lower(valid) < upper(valid))),
    CONSTRAINT temporal_salary_tx_not_empty CHECK (NOT isempty(tx)),
    CONSTRAINT temporal_salary_tx_bounds
        CHECK (lower(tx) IS NOT NULL
               AND (upper_inf(tx) OR lower(tx) < upper(tx))),
    -- 同一员工、valid 重叠、tx 也重叠 -> 拒绝；
    -- 同一 valid 的不同 tx 版本（tx 不重叠）是合法的，那正是版本历史。
    CONSTRAINT no_overlap_per_tx
        EXCLUDE USING gist (emp_id WITH =, valid WITH &&, tx WITH &&)
);
```

一条事实的含义是：

> **在事务时间 tx 内，数据库认为**「员工 emp_id 在有效时间 valid 内月薪为 salary」。

写操作只有两种动作：**把旧版本的事务时间上界封到"现在"**，再**以"现在"为起点插入新版本**。
工资值和有效区间不会被原地改写；每次更正只是对旧行的 `tx` 上界做一次 UPDATE（封存），再插入新版本。
逻辑上版本账本只增不减，等价于 append-only 的版本史；物理上被"封存"的那一行只是事务区间变了。

### 4.1 四个写操作

| 操作 | 对应 SQL:2011 | 业务语言 | 做什么 |
|---|---|---|---|
| `append` | `INSERT` | 新员工入职 / 记录一条新事实 | 插入 `valid=[from, ∞)`、`tx=[tx, ∞)` |
| `setValueFrom` | `UPDATE ... FOR PORTION OF` | 从某天起涨薪 | 找到覆盖该日的当前行，把"从那一天起、到下一次变化前"改成新值 |
| `updateForPortion` | `UPDATE ... FOR PORTION OF` | 更正某一段历史 | 只改 `[from, until)` 这一段，左右残余保留旧值 |
| `deleteForPortion` | `DELETE ... FOR PORTION OF` | 撤回录错的一段 | 只截掉 `[from, until)`，左右残余保留 |

第 5 个事件用 `setValueFrom(2024-05-10, 16000, from=2023-03-01)` 时，系统自动发现
2023-03-01 落在 `[2022-04-01, 2024-01-01) 14000` 里，于是把这刀**截止到 2024-01-01**，
只改 `[2023-03-01, 2024-01-01)`——这就是"补录一笔更早的涨薪，不要顺手把 2024 年的 18000 也改掉"。

### 4.2 7 次写入之后的当前信念

查询条件：`WHERE upper_inf(tx)`（事务时间无上界 = 现在仍然相信的行）。

| emp_id | salary | valid | tx |
|---|---|---|---|
| E1001 | 12000 | [2021-01-01, 2022-04-01) | [2022-04-01, ∞) |
| E1001 | **14500** | [2022-04-01, 2023-03-01) | [2024-06-01, ∞) |
| E1001 | 16000 | [2023-03-01, 2024-01-01) | [2024-05-10, ∞) |
| E1001 | 18000 | [2024-01-01, ∞) | [2024-01-05, ∞) |
| E1002 | 10000 | [2021-08-01, ∞) | [2024-07-01, ∞) |

共 5 行。而全表的**物理版本**是 10 行（E1001 8 行 + E1002 2 行）。多出来的就是被"封上事务时间上界"
的旧认知，它们不是垃圾，是"当时怎么想"的证据。

### 4.3 E1001 的 8 个版本（故事全貌）

按事务时间排序（SQL 为 `ORDER BY lower(tx), lower(valid), id`，与 Java 版 `versions()` 的排序一致）：

| # | salary | valid | tx | 怎么来的 |
|---|---|---|---|---|
| 1 | 12000 | [2021-01-01, ∞) | [2021-01-01, 2022-04-01) | 入职初始版本，被事件 3 封存 |
| 2 | 12000 | [2021-01-01, 2022-04-01) | [2022-04-01, ∞) | 事件 3 切出的左半（涨薪前的部分） |
| 3 | 14000 | [2022-04-01, ∞) | [2022-04-01, 2024-01-05) | 事件 3 的 14000，被事件 4 封存 |
| 4 | 14000 | [2022-04-01, 2024-01-01) | [2024-01-05, 2024-05-10) | 事件 4 切出的左半，被事件 5 封存 |
| 5 | 18000 | [2024-01-01, ∞) | [2024-01-05, ∞) | 事件 4 的 18000，仍是当前信念 |
| 6 | 14000 | [2022-04-01, 2023-03-01) | [2024-05-10, 2024-06-01) | 事件 5 切出的左半，被事件 6 更正 |
| 7 | 16000 | [2023-03-01, 2024-01-01) | [2024-05-10, ∞) | 事件 5 补录的 16000，仍是当前信念 |
| 8 | **14500** | [2022-04-01, 2023-03-01) | [2024-06-01, ∞) | 事件 6 更正后的 14500，仍是当前信念 |

看第 3、4、6 行：它们都是"曾经相信、现在不再相信"的版本，但都完整保留着。
第 6 行尤其能说明问题——它记录的是"在 2024-05-10 到 2024-06-01 这二十来天里，我们以为
2022 年那次涨薪是 14000"。没有 tx 维，这条信息无处可存。

## 5. 四类查询：同一个问题，看你问的是哪个时间

### 5.1 当前信念（现在是多少）

见 4.2 的表。SQL：`SELECT emp_id, salary, valid FROM temporal_salary WHERE upper_inf(tx);`

### 5.2 单时态 · 按有效日期（现在是哪天的多少钱）

| valid 日期 | 当前信念下的工资 |
|---|---|
| 2022-06-01 | 14500 |
| 2023-06-01 | 16000 |
| 2024-06-01 | 18000 |

### 5.3 单时态 · 按事务时刻（那一天系统相信什么）

`tx @> timestamp '2023-07-15 00:00'`：

| emp_id | salary | valid | tx（现在看，上界已被后来封住） |
|---|---|---|---|
| E1001 | 12000 | [2021-01-01, 2022-04-01) | [2022-04-01, ∞) |
| E1001 | 14000 | [2022-04-01, ∞) | [2022-04-01, 2024-01-05) |
| E1002 | 10000 | [2021-07-01, ∞) | [2021-07-01, 2024-07-01) |

3 行。注意此时 E1001 的当前工资是 **14000 且没有上界**——"当时以为会一直 14000"，
所以问 2024-06-01 也会得到 14000（旧信念的无限延伸）。

`tx @> timestamp '2024-05-10 00:00'`：

| emp_id | salary | valid | tx |
|---|---|---|---|
| E1001 | 12000 | [2021-01-01, 2022-04-01) | [2022-04-01, ∞) |
| E1001 | 14000 | [2022-04-01, 2023-03-01) | [2024-05-10, 2024-06-01) |
| E1001 | 16000 | [2023-03-01, 2024-01-01) | [2024-05-10, ∞) |
| E1001 | 18000 | [2024-01-01, ∞) | [2024-01-05, ∞) |
| E1002 | 10000 | [2021-07-01, ∞) | [2021-07-01, 2024-07-01) |

5 行。2024-05-10 正好是补录发生的那一刻：旧版本 tx 上界 `[.., 2024-05-10)` 与新版本
`[2024-05-10, ..)` **首尾相接**，因为左闭右开，这一刻算新版本。

### 5.4 双时态（两个时间都指定）

| valid \ tx | 2023-07-15 | 2024-05-10 | 2024-06-05 |
|---|---|---|---|
| 2022-06-01 | 14000 | 14000 | **14500** |
| 2023-06-01 | 14000 | 16000 | 16000 |
| 2024-06-01 | 14000 | 18000 | 18000 |

读法：**行 = 什么时候的事（valid），列 = 谁在什么时候问（tx）**。
- 第一行的 14500：更正发生在 2024-06-01，所以 2024-06-05 才看得到；
- 第二列 2024-05-10：补录刚入库、更正还没发生，所以 2023-06-01 是 16000 而 2022-06-01 还是 14000；
- 第三行第一列 14000：2023-07-15 时系统以为工资会一直是 14000（无限延伸）。

### 5.5 逻辑删除也保留认知

李娜的入职日期录错了一次（事件 7），`deleteForPortion` 只截掉 `[2021-07-01, 2021-08-01)`：

| 提问时刻 | valid 2021-07-15 在系统里的记录 |
|---|---|
| 2024-06-05（删除前） | 10000，有效区间 [2021-07-01, ∞)（入职日 2021-07-01） |
| 2024-07-05（删除后） | **查不到**（入职日已变成 2021-08-01） |

删除动作本身在版本史里留着（tx 从 `[2021-07-01, ∞)` 被封在 2024-07-01），所以"删之前系统怎么想"
照样答得出。**逻辑删除不是把行删掉，而是把认知的时间线封上。**

## 6. 关键约束：为什么 PRIMARY KEY 管不住"重叠"

需要保证的不变量是：

> 同一员工、同一事务时刻，**任何一天只能有一份工资**。

注意这句话不是"某个值唯一"，而是"两个**区间**不能重叠"。普通主键/唯一约束只能约束"点/组合相等"：

| 想插入的行（E1001 已有 `[2022-04-01, 2024-01-01)`） | `PRIMARY KEY (emp_id, valid)` | 业务需要 |
|---|---|---|
| `[2022-04-01, 2024-01-01)` 完全相同 | 拒绝 | 拒绝 |
| `[2022-06-01, 2022-09-01)` 部分重叠 | **放行** | 拒绝 |
| `[2022-04-01, 2023-01-01)` 被包含 | **放行** | 拒绝 |
| `[2024-01-01, 2024-06-01)` 首尾相接 | 放行 | 放行 |

所以要用**排除约束**（PostgreSQL 的 `EXCLUDE`，底层是 GiST 索引）：

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

ALTER TABLE temporal_salary
    ADD CONSTRAINT no_overlap_per_tx
    EXCLUDE USING gist (emp_id WITH =, valid WITH &&, tx WITH &&);
```

PostgreSQL 的排除约束语义是"**所有列对的条件同时成立才禁止**"：

- 同一 `emp_id` **且** `valid` 重叠 **且** `tx` 重叠 → 拒绝（同一时刻不可能有两个工资）；
- 同一 `valid`、不同 `tx` 的版本 → `tx` 不重叠 → **不冲突**，这正是版本历史。

实跑里故意插一条冲突记录，数据库自己拒绝（节选，完整原文见 `docs/temporal-sql-raw.txt` 第 382–383 行）：

```
ERROR:  conflicting key value violates exclusion constraint "no_overlap_per_tx"
DETAIL:  Key (emp_id, valid, tx)=(E1001, [2023-01-01,2023-06-01), ["2024-08-01 00:00:00",))
         conflicts with existing key (emp_id, valid, tx)=(E1001, [2023-03-01,2024-01-01), ["2024-05-10 00:00:00",)).
```

这条约束的价值：**应用层校验会被并发和"漏写 WHERE"打穿，数据库的约束不会。**
少了 `WHERE` 的 UPDATE、两个并发请求、脚本补数据——都过不去。

其他数据库的现状（一句话，别当成精确的兼容性矩阵）：

- MySQL 8 没有 range 类型和 `EXCLUDE`，"区间不重叠"只能靠触发器或应用层校验；
- SQL:2011 定义了系统版本时态表（`PERIOD FOR SYSTEM_TIME`）和 `FOR PORTION OF`，
  主流商用库大多有各自实现；
- **本文实测的 PostgreSQL 17.11 没有这些语法**，所以本文手写了 4 个 PL/pgSQL 函数来实现
  应用时间语义——这正是第 4.1 节那张表存在的原因；
- 版本脚注：PostgreSQL 18 已加入 `WITHOUT OVERLAPS` 时态约束（主键/唯一约束可以声明"区间不重叠"），
  上游也在推进 `FOR PORTION OF`。所以"17.11 没有"只是本文实测口径，不等于"PostgreSQL 永远没有"；
  真上生产前先确认目标版本支持到哪一步，再决定手写到什么程度。

## 7. 和前面 FD / 范式的关系

学到第 8 章时，函数依赖、BCNF、3NF、4NF 都在回答一个问题：**"什么样的表结构没有冗余"**。
但那些结论默认了一个前提：一个实体的属性**不随时间变**。

工资恰好是反例。普通写法 `emp_id → salary` 只在"工资永远不变"时成立；工资是**时变属性**。
时态化以后，键变成 `(emp_id, valid_time)`，依赖写成：

```
(emp_id, valid_time) → salary        -- 时态函数依赖的形式
```

教材在讲完函数依赖与范式（第 8 章末尾）专门转向时态数据建模，就是承认普通范式框架里
没有"时间"这一维（各印次节号/图号略有差异，按内容对齐即可）。落到实现上有三个坑：

1. **时间不是普通属性。** `valid` 是区间，不是两个独立的值。把起点/终点当普通列塞进主键，
   只能约束"点相等"，约束不了"区间不重叠"（第 6 节）。你按 BCNF 判定照做，会得到一张
   "形式上很规范、语义上漏约束"的表。
2. **tx 维让"同一个键"可以有多把值。** 同一个 `(emp_id, 2022-06-01)` 在 2023-07-15 是 14000、
   在 2024-06-05 是 14500——这不是函数依赖被破坏，而是"值依赖于认知时刻"。
   普通 FD 理论里没有这个维度。
3. **更新语义变了。** 普通关系模型假设 `UPDATE` 原地改；时态模型要求"封旧版本 + 插新版本"。
   这不是范式问题，是**更新协议**问题。

一句话概括：

> **范式管"重复"，时态约束管"重叠/矛盾"。两件事要一起做，不能互相替代。**

4NF 的多值依赖处理的是"一个键对应多组独立多值"的冗余；时态处理的是"一个键对应一条时间线"。
把"时间"错当普通属性时，时态表看起来也会有部分依赖/冗余的味道——但那不是范式能消掉的，
得靠时间维建模和区间约束。

## 8. 两套实现：SQL 管约束，Java 管推理

| | SQL 版 | Java 版 |
|---|---|---|
| 文件 | `src/main/resources/sql/temporal_modeling_demo.sql` | `src/main/java/com/ds/temporal/` |
| 表结构 | `temporal_salary` 表 + 排除约束 | `TemporalTable<V>` 内存行表 |
| 约束由谁保证 | 数据库（GiST 排除约束，并发安全） | `append` 显式检查 + `verify()` 5 条不变量 |
| 事务时间 | 调用方显式传入 `p_tx`（便于复现） | 调用方显式传入 `tx`（时钟只能前进） |
| 查询 | 4 类 SQL（第 5 节） | `current` / `valueAt` / `asOf` / `valueAsOf` |
| 对账 | 7 个事件、3×3 矩阵 | 同一组 7 个事件、同一张 3×3 矩阵 |
| 验证 | 两次连跑退出码 0；冲突被拒 | 17 个 JUnit 测试，`testsFound=17 succeeded=17 failed=0` |

Java 版的 `verify()` 检查 5 条不变量：区间非空、行的事务时间不晚于事务时钟、
同一员工且 tx 重叠的两个版本其 valid 不允许重叠、没有重复行、当前信念里 valid 两两不重叠。
其中第 3 条就是 SQL 排除约束在内存里的对应物——**同一套语义，两种强制方式**。

为什么写两遍？因为时态建模有两个常被混淆的层面：

- "交给数据库怎么做"——约束、索引、并发安全（SQL 版）；
- "自己写代码怎么保证"——内存模型、不变量、单元测试（Java 版）。

两者用同一组事件跑出同一组答案，才算真正理解了语义，而不是碰巧写对了一条 SQL。

## 9. 落地形态怎么选

| 方案 | 能回答的问题 | 成本 | 典型场景 |
|---|---|---|---|
| 只存当前值 | 现在多少 | 最低 | OLTP 主表 |
| 审计表（触发器/日志） | 谁在什么时候改了什么 | 中 | 合规、追责；查"某天的值"要回放 |
| 快照表（每天/每月全量） | 每个快照日的状态 | 高（行数 × 天数） | 报表、对账，粒度粗 |
| SCD2 / 拉链表（只有 valid） | 每个有效期的值 | 低 | 数据仓库维度；**答不出"当时认知"** |
| 双时态（本文） | valid × tx 两类问题全答 | 版本数 | 薪酬、保险、医疗、金融等需要追溯更正的业务 |
| 事件溯源 | 事件流 + 重放 | 中 | 需要完整因果链、可审计 |

选择的顺序应该是：**先列"要回答的问题清单"（第 0 节那张表），再选能回答这些问题的
最小方案。** 不要一上来就双时态——版本数膨胀、写入路径复杂，都是有代价的。

## 10. 十条自检清单

1. 能不能回答"某个有效日期"的问题？
2. 能不能回答"某个事务时刻，系统认为某个有效日期的值"？
3. 追溯更正是**封旧版本**还是原地 `UPDATE`？
4. 事务时间从哪来：数据库时钟、应用传入、还是导入时的时间？（本文显式传入，便于复现和测试）
5. "区间不重叠"由数据库保证，还是应用层"记得写 WHERE"？
6. 删除是逻辑删除吗？还能回答"删之前怎么想"吗？
7. 端点约定统一吗（左闭右开还是双闭）？跨年、月末、闰日怎么算？
8. "无上界"怎么表示（∞ / NULL / 9999-12-31）？三种混用迟早出 bug。
9. 事务时间用 `timestamp` 还是 `timestamptz`？跨时区系统必须用带时区的类型。
10. 版本数会膨胀多少？哪些旧版本可以归档、哪些必须保留？

## 12. 一句话收尾

时态数据建模不是"给表加两个日期列"，而是**同时保存现实的时间线和认知的时间线**，
并让数据库用区间约束替你守住"同一时刻只能有一个真相"。

- 只存当前值：答不出历史；
- 只加有效期：答得出"哪天多少钱"，答不出"当时怎么想"；
- 双时态：两个维度都在，四类问题全答得出，代价是行数是版本数。

而"涨薪"和"更正错误"在机制上是**同一个操作**：封掉旧版本、写一个新版本。区别只在故事里；
数据库不需要知道，也最好不要让数据库去猜。
